# BUILD PRO Drawing AI — 図面自動読み取りパイプライン (フェーズ0〜3)

## 1. 現状分析のまとめ

アップロードされた `BUILD_PRO_V13_5_6_DIRECT_START_WINDOWS.zip` を解析した結果:

- 中身は `system/app.html`(1.2MB)を中心とした Windows ローカル業務アプリ。案件管理・見積計算・スケジュール・印刷帳票・複数PC間同期(`hub_client.js`)などを備えた完成度の高い**業務システム**。
- AI接続は既に **LM Studio / OpenAI互換API**(`http://127.0.0.1:1234/v1`)方式で実装済み。オープンソースAIへの接続口そのものはすでにある。
- しかし **図面(PDF/DWG/DXF/JWW/画像)を実際に読み取るコードは存在しない**。添付ファイル処理 `fileText()` は `.txt/.csv/.md/.json/.xml/.html/.log` のみを読み、PDFや画像は空文字列を返す。OCR・画像認識・線/記号解析・寸法パースは未実装。
- 現状の「AI」は、担当者が図面を見て**手入力した数値・手書きメモ**をもとに文章生成・分析コメントを書くだけの役割。見積の数量根拠は完全に人力入力。

→ ユーザーの診断通り、**フェーズ1〜3(図面を読んで理解する部分)は実質ゼロ**。本パッケージはこの欠落部分を新規に埋めるもの。

## 2. 設計方針

ユーザーの要望どおり、以下の人間的な読み取りプロセスをそのままパイプラインの段階に対応させた:

| 人間の思考プロセス | パイプラインの段階 | 実装 |
|---|---|---|
| 図面一式をざっと見て「どんな工事か」を掴む | **フェーズ0: 概観(overview)** | シート単位で縮小画像を1回だけAIに見せ、種別分類+一言要約 |
| 敷地条件を正確に把握する | **フェーズ1: 敷地情報** | 配置図タイルから事実を1件ずつ抽出、100%精度目標のため個別に確信度採点 |
| 「何をしたいか」を読み取り文章化する | **フェーズ2: 意図の文章化** | 全タイルから工事意図を抽出→親AIが案件概要文に統合 |
| 数字・線・記号を正確に読み、意味を理解する | **フェーズ3: 詳細読み取り** | 最重要工程。タイルごとに複数回読み取り(アンサンブル)+OCR裏取り |
| 平面情報+高さ方向の情報を頭の中で立体化する | **フェーズ3補助: 立体統合** | 平面図の要素と立面/断面図の寸法を突き合わせ、室ごとの階高・壁高を推定 |

### 「子AI×多数 → 親AI」構成

- **子AI**: 図面を小さいタイル(既定 1024px、160pxオーバーラップ)に分割し、タイル1枚=1回の推論で読ませる。大きな図面を一度に読ませると精度が落ちる、という問題への直接対応。
- **親AI**: 全タイルの子AI出力を統合。まず決定的なロジックでタイル重複(オーバーラップ領域)の重複除去を行い、その後より大きいモデルに矛盾解消を依頼する(失敗時は決定的な統合結果にフォールバックし、パイプライン全体は止まらない)。

### 精度を上げるための具体的な工夫

1. **OCR裏取り**: 各タイルに対し独立のOCRエンジン(PaddleOCR/Tesseract)を走らせ、その原文をVLMのプロンプトに同梱。VLM単独では起きやすい数字の読み違いを、OCRとの突き合わせで検出・減点する(`detail_agent._ocr_grounding_bonus`)。
2. **アンサンブル読み取り**(フェーズ3): 同じタイルを既定2回、独立に読ませ、一致した読み取りは確信度を加点、一致しなかったものはそのまま残して低確信度フラグを立てる。
3. **フェーズ1は事実単位で個別採点**: 一つの文章にまとめず、「敷地面積」「前面道路幅員」等をキーごとに個別のオブジェクトとして出力させ、それぞれに確信度と根拠原文(`raw_evidence_text`)を持たせる。100%の精度が求められる以上、「だいたい合っている要約」ではなく「合っているか個別に検証できる事実のリスト」にした。
4. **未読取項目の可視化**: フェーズ1は期待される項目(敷地面積・前面道路幅員・用途地域・建蔽率・容積率・セットバック・所在地)のうち何が読み取れなかったかを `unresolved_questions` として明示する。

## 3. ディレクトリ構成

```
drawing_ai/
  config.py       # モデル接続先・タイルサイズ・時間予算などの設定(環境変数で上書き可)
  schemas.py      # 全フェーズの入出力データ契約 (pydantic)
  ingestion.py    # PDF/画像の読み込み・ページレンダリング・タイル分割
  ocr_engine.py   # OCRラッパー(PaddleOCR / Tesseract / フォールバック)
  vlm_client.py   # OpenAI互換API(Ollama/LM Studio/vLLM)への非同期クライアント
  prompts.py      # 各フェーズ用の日本語プロンプト
  orchestrator.py # フェーズ0→1→2→3の実行順序・並列実行・時間予算管理
  agents/
    overview_agent.py            # フェーズ0
    site_agent.py                # フェーズ1
    intent_agent.py               # フェーズ2
    detail_agent.py               # フェーズ3(アンサンブル込み)
    vertical_synthesis_agent.py  # フェーズ3補助(立体統合)
    parent_agent.py               # 親AI: 統合・重複除去・矛盾解消
  tests/          # モック(擬似)VLMによる結合テスト。実モデル無しで検証可能
app.py            # FastAPIサーバー(外部連携用エントリポイント)
requirements.txt
render.yaml
```

## 4. セットアップと実行方法

### 4.1 依存関係

```bash
pip install -r requirements.txt
```

OCRエンジンは既定で PaddleOCR を想定しているが、requirements.txt ではコメントアウトしてある(重量級のため)。有効化する場合:

```bash
pip install paddleocr paddlepaddle
```

軽量に済ませたい場合は Tesseract + 日本語データを使う(`pytesseract` は requirements.txt に含まれている):

```bash
# 例: Debian/Ubuntu
sudo apt-get install tesseract-ocr tesseract-ocr-jpn
export DRAWING_AI_OCR_ENGINE=tesseract
```

どちらも未導入の場合はOCR無し(ビジョンAI単独)で自動的に動作を続けるが、精度は落ちる。

### 4.2 オープンソースAIモデルの用意

このパイプラインは OpenAI互換API を話すサーバーであれば何でも接続できる(モデル非依存)。動作確認用の推奨構成:

```bash
# Ollamaの例(子AI用: 軽量な日本語対応VLM)
ollama pull qwen2.5vl:7b
ollama serve   # http://127.0.0.1:11434/v1 で待受

# 親AI用(テキストのみで良い、やや大きめのモデル)
ollama pull qwen2.5:32b
```

接続先はすべて環境変数で切り替え可能:

```bash
export DRAWING_AI_CHILD_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_CHILD_MODEL=qwen2.5vl:7b
export DRAWING_AI_PARENT_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_PARENT_MODEL=qwen2.5:32b
export DRAWING_AI_CHILD_CONCURRENCY=6   # 子AIの同時実行数。処理時間目標に直結
```

既存の BUILD PRO 側が LM Studio(`http://127.0.0.1:1234/v1`)を使っているなら、同じサーバーを両方から指すことも可能。

### 4.3 サーバー起動

```bash
uvicorn app:app --host 0.0.0.0 --port 8000
```

- `GET /health` — 接続先モデル・設定の確認
- `POST /analyze` — 図面ファイル(複数可、multipart/form-data)を送信し、フェーズ0〜3の統合結果(JSON)を取得

### 4.4 テスト実行(実モデル不要)

```bash
python3 -m pytest drawing_ai/tests -q
```

タイル分割の網羅性、アンサンブル統合ロジック、重複除去、フェーズ1の完全性スコア、パイプライン全体の異常系耐性(一部の子AI呼び出しが失敗してもパイプライン全体は止まらないこと)を、擬似VLM応答で検証している。実際の図面画像とモデルでの精度検証は別途、本物の図面サンプルで行う必要がある(セクション6参照)。

## 5. 性能目標(30万円クラス/10万文字規模の図面を15〜30分で処理)

- 図面をタイル単位に分割し、子AIの呼び出しを**全タイルに対して並列発行**する。実際の並列数は `DRAWING_AI_CHILD_CONCURRENCY` で制御され、これがボトルネックを解消する主要なレバー(GPU/レプリカを増やすほど線形に短縮できる設計)。
- フェーズ0(概観)とOCRは軽量なので先に実行し、フェーズ1の対象タイルを配置図系シートに絞り込むなど、後段の呼び出し回数を減らしている。
- フェーズ3の親AIによる矛盾解消はコストが高いため、統合対象が一定件数(既定250件)を超える場合は決定的な統合結果にフォールバックし、親AI呼び出しがボトルネックにならないようにしている。
- `orchestrator.py` は経過時間を計測し、目標(既定15分)・上限(既定30分)を超えた場合は `PipelineRun.warnings` に理由と対処法(並列数の引き上げ、タイルサイズの見直し等)を記録する。

## 6. 既知の制限事項・今後の課題

正直な現状評価として、以下は**未検証・未実装**であり、本物の図面での検証が必須:

1. **実図面での精度検証が未実施**: 本セッションにはGPU・実モデル・実際の図面サンプルが無いため、今回はモック(擬似)VLMによる結合テストのみ実施した。実際の図面(木造/RC、手書き含む)でのフェーズ1〜3の精度は、実モデルを繋いでから計測・チューニングが必要。
2. **モデル選定はプレースホルダー**: `qwen2.5vl:7b` 等はあくまで動作確認用のデフォルト値。日本語建築図面(特に手書き注記・JIS建築記号)での精度は、候補モデル(Qwen2.5-VL, InternVL2.5, MiniCPM-V 2.6 等)を実際に比較して選定すべき。
3. **DXF/DWG/JWWのベクターデータを直接使っていない**: 現状は画像としてラスタライズしてから読む設計。CADのベクターデータ(線分・レイヤー・寸法値そのもの)を直接パースできれば、フェーズ3の精度・速度は大きく向上する可能性が高く、次の改善候補。
4. **フェーズ4(数量拾い・利益率・見積書生成)は本パッケージのスコープ外**。ユーザーの要望通り「フェーズ1〜3が正しく機能してから」着手すべき部分で、`Phase3Result` を入力として消費する設計にしてある。
5. **BUILD PRO OS 見積欄との外部連携**は `POST /analyze` のJSON契約(`schemas.py` の `PipelineRun`)を想定しているが、実際の連携コード(既存 `system/app.html` 側からの呼び出し)は未着手。

## 7. 次のアクション(推奨)

1. 実際の図面サンプル(できれば10〜20件、木造/RC/手書き含む)を用意し、Ollama等で候補VLMを繋いで `POST /analyze` を実行、フェーズ1〜3の出力を人間がレビューして精度を測る。
2. フェーズ1(敷地情報)から着手し、100%精度に達するまでプロンプト・タイリング・OCR設定を調整する(ユーザーの指定通り、フェーズが進むほど前段の精度が重要になるため)。
3. 精度が安定した時点でDXF/DWGのベクター直接パースを検討。
4. フェーズ1〜3が安定してから、既存 `system/app.html` の資料台帳(`bpRegisterAttachments`)からこのAPIを呼び出す連携コードを追加する。
