# BUILD PRO Drawing AI — 図面自動読み取りパイプライン (フェーズ0〜3)

## 1. 現状分析のまとめ

アップロードされた `BUILD_PRO_V13_5_6_DIRECT_START_WINDOWS.zip` を解析した結果:

- 中身は `system/app.html`(1.2MB)を中心とした Windows ローカル業務アプリ。案件管理・見積計算・スケジュール・印刷帳票・複数PC間同期(`hub_client.js`)などを備えた完成度の高い**業務システム**。
- AI接続は既に **LM Studio / OpenAI互換API**(`http://127.0.0.1:1234/v1`)方式で実装済み。オープンソースAIへの接続口そのものはすでにある。
- しかし **図面(PDF/DWG/DXF/JWW/画像)を実際に読み取るコードは存在しない**。添付ファイル処理 `fileText()` は `.txt/.csv/.md/.json/.xml/.html/.log` のみを読み、PDFや画像は空文字列を返す。OCR・画像認識・線/記号解析・寸法パースは未実装。
- 現状の「AI」は、担当者が図面を見て**手入力した数値・手書きメモ**をもとに文章生成・分析コメントを書くだけの役割。見積の数量根拠は完全に人力入力。

→ ユーザーの診断通り、**フェーズ1〜3(図面を読んで理解する部分)は実質ゼロ**。本パッケージはこの欠落部分を新規に埋めるもの。

## 2. 設計方針

ユーザーの要望どおり、以下の人間的な読み取りプロセスをそのままパイプラインの段階に対応させた:

| 人間の思考プロセス | パイプラインの段階 | 実装 |
|---|---|---|
| 図面一式をざっと見て「どんな工事か」を掴む | **フェーズ0: 概観(overview)** | シート単位で縮小画像を1回だけAIに見せ、種別分類+一言要約 |
| 敷地条件を正確に把握する | **フェーズ1: 敷地情報** | 配置図タイルから事実を1件ずつ抽出、100%精度目標のため個別に確信度採点 |
| 「何をしたいか」を読み取り文章化する | **フェーズ2: 意図の文章化** | 全タイルから工事意図を抽出→親AIが案件概要文に統合 |
| 数字・線・記号を正確に読み、意味を理解する | **フェーズ3: 詳細読み取り** | 最重要工程。タイルごとに複数回読み取り(アンサンブル)+OCR裏取り |
| 平面情報+高さ方向の情報を頭の中で立体化する | **フェーズ3補助: 立体統合** | 平面図の要素と立面/断面図の寸法を突き合わせ、室ごとの階高・壁高を推定 |

### 「子AI×多数 → 親AI」構成

- **子AI**: 図面を小さいタイル(既定 1024px、160pxオーバーラップ)に分割し、タイル1枚=1回の推論で読ませる。大きな図面を一度に読ませると精度が落ちる、という問題への直接対応。
- **親AI**: 全タイルの子AI出力を統合。まず決定的なロジックでタイル重複(オーバーラップ領域)の重複除去を行い、その後より大きいモデルに矛盾解消を依頼する(失敗時は決定的な統合結果にフォールバックし、パイプライン全体は止まらない)。

### 精度を上げるための具体的な工夫

1. **根拠テキストによる裏取り**(`grounding.py`、詳細はセクション3): 各タイルに対し、可能ならPDFのベクター文字レイヤー(誤読ゼロ)、無ければOCR(PaddleOCR/Tesseract)の原文をVLMのプロンプトに同梱。VLM単独では起きやすい数字の読み違いを、この根拠との突き合わせで検出・加減点する。ベクター根拠との不一致は強い減点(-0.5)、一致は強い加点(+0.3)かつ `verified_by_vector=True` として親AIの書き換え対象から除外する。
2. **アンサンブル読み取り**(フェーズ1・フェーズ3): 同じタイルを既定3回、独立に読ませ、一致した読み取りは確信度を加点、一致しなかったものはそのまま残して低確信度フラグを立てる。フェーズ1は下流工程が無く100%精度が目標のため、全フェーズ中もっとも大きい加点幅を与えている。
3. **フェーズ1は事実単位で個別採点**: 一つの文章にまとめず、「敷地面積」「前面道路幅員」等をキーごとに個別のオブジェクトとして出力させ、それぞれに確信度と根拠原文(`raw_evidence_text`)を持たせる。100%の精度が求められる以上、「だいたい合っている要約」ではなく「合っているか個別に検証できる事実のリスト」にした。
4. **未読取項目の可視化**: フェーズ1は期待される項目(敷地面積・前面道路幅員・用途地域・建蔽率・容積率・セットバック・所在地)のうち何が読み取れなかったかを `unresolved_questions` として明示する。

## 3. 精度100倍化フォーメーション(ベクターPDF根拠層)

「基本設計(子AI×多数→親AI)は変えず、全項目に対して精度の基準を桁違いに引き上げ、立体を推論するフォーメーションを組む」という要望に対する実装。ポイントは、AIに「読ませて当てさせる」対象そのものを減らし、**読めるものはAIに読ませず断定的に確定させる**層を新設したこと。

### 3.1 発見: このクラスの図面はスキャン画像ではなくベクターPDFである

実際にユーザー提供の図面(石川県ホテル計画、A3・7枚)を調べたところ、CAD由来のPDFは寸法数字・室名・注記が**PDFの文字レイヤーに厳密な座標付きテキストとして埋め込まれている**ことが判明した(`page.get_text("words")` で1文字も誤らずに取得可能)。壁も塗りつぶしポリゴン(`page.get_drawings()`)として厳密な座標で埋め込まれている。つまりこの種の図面では、数字や文字を「画像から読み取る」必要が本来無く、**ファイルから直接、誤読の可能性ゼロで取り出せる**。

### 3.2 新設した層: `vector_extractor.py`

- **文字レイヤー抽出**: 座標付きの正確な文字列をタイル単位に切り出し(`words_in_bbox`)、子AIのOCR代わりの「根拠テキスト」として渡す。従来のOCR(Tesseract)は**タイルにベクター文字が無い場合のみ**のフォールバックに格下げ。
- **縮尺の自動特定**: 表題欄の「縮尺」ラベル近傍から「1/50」等のトークンを検出し、レンダリングDPIと組み合わせて `mm_per_px` を数式的に算出(`25.4×縮尺分母÷DPI`)。線分やテキストの実寸換算に使う。
- **壁ポリゴン抽出**: このCADベンダーが壁を一貫した灰色の塗りつぶしポリゴンで描画していることを実データで確認し、その色でフィルタして壁の輪郭をそのまま抽出(モデル推論ゼロ)。
- **寸法チェーン検算(加算検算)**: 人間が電卓で行う「内訳の合計=総寸法か」の確認を、テキスト座標のクラスタリングのみで機械的に実施。線分とのマッチングは実データで検証した結果、CADベンダーごとの描画流儀に依存しすぎて汎用的に信頼できないと判断し**採用を見送った**(判断根拠は本ファイル末尾のトレードオフ注記、および `vector_extractor.py` のモジュール docstring 参照)。空間的に無関係な数値を誤って合計候補にしないよう、チェーンの座標範囲でも候補を絞り込んでいる。

### 3.3 信頼度への反映(`grounding.py`)

読み取りソースの信頼階層を全フェーズで統一:

1. **ベクター根拠と一致** → 大きく加点(数値+0.3、ラベル+0.25)、`verified_by_vector=True` を明示
2. **ベクター根拠が存在するのに不一致** → 大きく減点(-0.5)。ハルシネーションの強いシグナル
3. **ベクター根拠が無く、OCRと一致/不一致** → 従来通りの小さな加減点(+0.1/-0.2)。OCRは実測で再現率が低いことが分かっているため

さらに、`verified_by_vector=True` の読み取りは**親AIによる矛盾解消の対象から除外**し、統合結果へそのまま無編集で反映する(`parent_agent.aggregate_phase3`)。根拠のある確定情報をモデル呼び出しの気まぐれで書き換えさせない、という原則を徹底した。

### 3.4 立体推論フォーメーション: `solid_model_agent.py`

平面×高さを頭の中で組み立てる、というユーザーの要望に対し、**AIの推測に頼らない最小限の立体モデル**を構築する:

- 壁: ベクター抽出した塗りつぶしポリゴンをそのまま実寸(mm)の壁フットプリントとして採用
- 天井高: 図面中の「CH=2500」等の表記をそのままの数値として抽出(誤読の余地なし)
- 両者の対応付け: 壁・室要素ごとに最も近いCH=ラベルを最近傍探索で割り当て、マッチ距離を `match_distance_px` として明示(この対応付けだけはヒューリスティックであることを隠さない)

フルBIMではないが、**壁の位置と高さの両方が実測値に紐づいた**最小限の立体表現になっている。

### 3.5 実図面での効果測定(石川県ホテル計画、7枚)

同一タイルを従来方式(OCR裏取り)と新方式(ベクター根拠)の両方で実際に処理し比較:

| 寸法 | 従来(OCR裏取り) | 新方式(ベクター根拠) |
|---|---|---|
| 2050mm | confidence 0.80 | confidence 1.00, verified_by_vector=True |
| 858mm | confidence 0.75 | confidence 1.00, verified_by_vector=True |
| 850mm | confidence 0.80 | confidence 1.00, verified_by_vector=True |
| 92mm(壁厚) | confidence 0.40(要確認) | confidence 0.90, verified_by_vector=True |

図面セット全体(7枚・105タイル)での実測:

- **92%のタイル(105枚中92枚)でベクター根拠が取得でき、OCR呼び出しを完全にスキップ**(精度向上と同時に処理時間も削減)
- 文字レイヤーから **641個の文字列**を誤読ゼロで抽出
- 壁ポリゴンを **168個**抽出、うち **92個**を天井高ラベルと対応付け
- 縮尺(mm/px)を7枚すべてで一貫して自動算出(5.773mm/px、1/50・220DPI相当)

### トレードオフに関する注記(線分マッチングを採用しなかった理由)

当初、寸法数字とその寸法線の実測長さを線分ジオメトリで直接突き合わせる案も検討したが、実データで試したところ寸法線・引出線・無関係な什器線が同系統の色を共有しており、汎用的な数値↔線分の対応付けは信頼できないと判断した。誤った「幾何学的検証」を出すくらいなら出さない方がよいという判断で、このアプローチは不採用とした(`ScaleConsistencyFlag` のスキーマは将来の拡張用に残してあるが、現状は常に空)。

### 3.6 仕様書読解AI(COAI-01: `agents/spec_agent.py`)

図面本体より先に読むべき最優先の精度投資対象として設計した工程。仕様書(仕上げ表・
内部仕上げ表・外部仕上げ表・仕様書一覧・特記仕様書・建具表など、名称は案件ごとに
異なるが「部屋や部位ごとの仕上げ・下地・製品仕様を一覧化し、工事全体を俯瞰できる
資料」であれば対象に含む — `SheetType.SPECIFICATION`)から、部屋単位で仕上げ・下地・
製品情報を読み取る。

Phase 1(敷地情報)と同じ精度の考え方を適用している:

- **ベクターground truthの適用**: 仕様書PDFがベクターネイティブな場合、`grounding.py`
  の信頼階層(ベクター文字 > OCR > モデル単独)をそのまま利用する。
- **アンサンブル**: `settings.spec_ensemble_size`(既定3)回、独立に読み取ってから
  照合する(Phase 1と同じ「ここは省略できない」という判断)。
- **テーブル構造を先に抽出してから意味推論する**: `vector_extractor.extract_table_rows()`
  がベクター文字を行単位にグルーピングし(`Tile.ground_truth_table_rows`)、モデルには
  「すでに行として整理された正確なテキスト」を優先的な手がかりとして渡す。仕上げ表の
  レイアウトは設計事務所ごとに大きく異なるため、構造把握と意味推論を1回のモデル呼び出しで
  同時にやらせるより頑健。
- **用語の正規化**(`terminology.py`): 「CL」「クロス」「ビニールクロス」のような
  表現揺れを公開基準寄りの用語に正規化しつつ、原文(`raw_finish_term`)も必ず保持する。

固定の3つの問い(基本情報 / 工事範囲を絞り込む言葉 / どうしたいか・変更点)を、
**見つからない場合も含めて毎回同じJSONスキーマで**モデルに投げる設計にしている。
これらの結果は独立した第4の構造として持たず、既存のPhase 1/2にそのまま合流させる
(基本情報→`SiteFact`として`aggregate_phase1`へ、変更点→`IntentStatement`として
`aggregate_phase2`へ)。役割の重複を防ぐため(建築一式工事AIを不採用にしたのと同じ
判断基準)であり、かつ仕様書由来の基本情報・意図はしばしば図面から読み取るより
高精度なため、Phase 1/2自体の精度向上にも直接寄与する。「工事範囲を絞り込む言葉」
だけは既存のどの構造にも対応物が無いため、`SpecResult.scope_target_terms`として
独立に保持する。

部屋単位の仕上げ詳細は`parent_agent.aggregate_spec()`でタイルをまたいで統合され、
同じ部屋・同じ仕上げで下地の既存/新規判定がタイル間で食い違った場合は`ambiguous_flags`
に正直に記録する(黙って片方を採用しない)。

### 3.7 面積の多段階フォールバック推論(`estimate_gross_footprint` / `area_parsing.py`)

実案件のブラインドテスト(KDX中野坂上ビル802号室、原価表非参照)で判明した実際の
限界: 壁ポリゴンが抽出できない図面(スキャン図面、現地実測annotated図、
`_WALL_FILL_COLOR`と一致しないCADベンダーの塗りつぶし規則等)では、床面積が
一律「不明」になっていた。これは一度きりの不具合ではなく、**単一の推論経路が
使えない場合は別の経路から逆算する、という段階的フォールバックが存在しなかった
という構造的な穴**だった。

面積の算出経路を、精度が高い順に以下のように多段階化した。いずれかが使えなければ
次の経路を試し、複数の経路から値が得られた場合は`aggregate_phase1`の統合ロジックが
自動的に「一致すれば確信度を上げる」「食い違えば`unresolved_questions`に残す」形で
整合性を取る(黙って片方を捨てない)。

1. **壁ポリゴン(`SolidModel`)** — ベクターPDFの塗りつぶしパスから直接算出。最も正確。
2. **印字された面積表記(`ElementReading.area_sqm`, `area_parsing.py`)** — 図面に
   「5.3m2」「12.5畳」等の面積が印字されていれば、フェーズ3の子AIがそれを`area_text`
   として書き写し、決定論的に数値化する(畳→m2は1畳=1.62m2で換算)。
3. **寸法チェーンからの外形概算(`estimate_gross_footprint`)** — シート上の最大の
   横方向・縦方向の寸法チェーンの合計値を「グリッド外形の概算」として採用する。
   **図面種別で絞り込まず、ベクター根拠がある全シートに対して実行する**(敷地図・
   平面図に限らず、電気図面等が同じ外形寸法チェーンをたまたま持っていることもある
   ため)。**実際のプロジェクト資料(KDX中野坂上ビル802号室、現地実測annotated図)で
   検証したところ、この経路は効かないケースがあることが判明した**: このロジックは
   CADが自動生成する一直線の寸法列が前提だが、現地実測annotated図は数字が壁ごとに
   個別に書き込まれており、58個の数値のうち3つ以上が整列していたのは1件のみ
   (しかもOCR誤読による偽の一致)だった。単一の経路を過信せず、実データで
   都度検証する必要があるという教訓として記録している。
4. **VLMによる幅・奥行の視覚判断(`width_text`/`depth_text`)** — 3が使えない
   非整列annotated図面のために追加した経路。面積の印字が無い場合、子AIが画像を見て
   「この部屋の横方向・縦方向の境界の数字はこれだ」と判断した2つの数字を書き写す
   (一直線に並んでいなくてもよい)。ベクター根拠がある場合は、両方の数字が原文と
   一致することを検証してから採用し、一致しなければ(ハルシネーションの疑い)
   不採用とする。KDX802の実データで、正しい組み合わせ(3375×2795)は面積9.43m2を
   正しく算出し、存在しない数字を与えた否定対照実験では正しく不採用になることを
   確認済み。ただし「画像を見てどの数字を選ぶか」というVLM自身の判断精度は、
   実モデルに接続できる環境でなければ検証できない。
5. どれも得られない場合のみ、正直に「不明」として残す。

### 3.8 実際の見積との突き合わせで見つかった誤りの修正

KDX802号室のブラインド推論(原価内訳書を見ずに図面+質疑書だけから推論)を、後から
実際の原価内訳書(24ページ)と突き合わせたところ、23項目中12項目(52%)は金額・数量まで
正しかった一方、明確な誤り1件・見落とし2件が見つかった(詳細は検証時のレポート参照)。
それぞれの根本原因に対して以下を実装した。

- **`reference_resolution.py`**: 質疑書(RFI)は「質疑No.6参照」のように回答が別の行を
  指すことがある。これを解決せず独立した行として読んだ結果、洗面化粧台の扱いを
  「既存利用」と誤読した(実際はNo.6が「撤去」と回答していた)。`resolve_references()`
  が質問No.をキーに1ホップだけ参照を解決し、参照の参照(多段階)は無理に追わず
  `unresolved_chained_reference`として明示する。`spec_agent`が読み取った`QAItem`に
  対して`parent_agent.aggregate_spec()`がタイルをまたいで統合した後に一度だけ実行する
  (参照先が別タイルで読まれている可能性があるため)。
- **`hvac_parsing.py`**: 空調系統の「1対1×2組、1対2×1組」のようなプロース記述を
  目算で室外機3台・室内機4台と解釈したが、実際に発注された機器(ダイキン
  「3M685AV」「2M535AV」)は室外機2台だった。`parse_daikin_branch_count()`が型番の
  先頭の数字(3M→3分岐)を機械的に読み取り、`check_prose_vs_equipment()`がプロース
  記述より型番ベースの値を優先しつつ、両者が食い違えば要確認フラグを立てる
  (型番ベースの室内機台数は「対応可能な最大分岐数」であり確定台数ではない旨の
  注記を必ず付与)。
- **`parent_agent.check_spec_dimensions_against_drawing()`**: 質疑書に記載された
  スライディングウォールの寸法(W3640×H2400)が、図面のベクター確定寸法
  (W3548×H2035、同一開口部)と食い違っていたのに気づかず質疑書側を採用し誤った。
  仕様書・質疑書の回答文に含まれるW×H形式の寸法を、Phase3のベクター確定寸法の
  集合と照合し、一致しなければ「図面を優先、ただし両方を要確認として記録する」
  フラグを立てる。COAI-01で暫定扱いのまま保留していた「図面との矛盾時の扱い」を
  この実例をもって確定させた。
- **部屋別面積のPhase1への合流**: グリッド外形からの概算(3.7節の経路3)は実際より
  低めに出る傾向が確認された(実際75.2m2に対し55〜65m2と推定)。Phase3で個々の
  部屋ごとに算出した面積(3.7節の経路2・4)の合計を、独立した情報源として
  `aggregate_phase1`の突き合わせプールに追加し、単一の経路だけに頼らないようにした。

すべて実際のKDX802号室のデータ(質疑書の文言、機器型番、図面のベクター確定寸法)を
使ったテストで検証済み(`tests/test_error_analysis_fixes.py`)。

### 3.9 読み取り工程の5段階分解と、そこで見つかったさらに根本的な2つの欠陥

3.8節の修正を振り返る中で、「文字認識」「意味理解」「計測・数量化」「深掘り推論」
「誤り検知」という5段階に分解して見直したところ、**段階1(文字認識)そのものに
見過ごせない欠陥**が見つかった。

- **OCR文字レイヤーをCADネイティブ文字と誤って同格に扱っていた**: `is_vector_native()`
  は「PDFに文字が1つでも取れればtrue」としか判定しておらず、KDX802号室の現地実測
  図面(ページ面積の78%を1枚のスキャン画像が占め、その上にOCRの文字レイヤーが
  乗っているだけの構成)を、CADが直接書き出した正確な文字列と同じ信頼度
  (`verified_by_vector=True`、confidence補正+0.3/-0.5)で扱ってしまっていた。
  実際にこの文字レイヤーには「ワ子」「江け」のようなOCR読み取り崩れが混じって
  おり、精度の面で明らかにCADネイティブと同格ではなかった。

  `vector_extractor._has_full_page_scan_image()`(埋め込み画像がページ面積の
  70%以上を占めるかで判定)を追加し、`SheetGroundTruth.text_trust_tier`
  (`"cad_native"` / `"ocr_layer_over_scan"`)として区別、`Tile.ground_truth_trust_tier`
  経由で`grounding.py`まで伝播させた。`grounding.is_cad_native(tile)`が
  falseの場合は、たとえ`has_vector_ground_truth=True`であっても通常のOCRと
  同じ弱い信頼度(+0.1/-0.2、verified_by_vector=False)にとどめる。壁ポリゴン
  抽出(`wall_segments_mm`)は実際のベクター図形(`get_drawings()`)を読むため
  スキャン画像の影響を受けず、この区別が不要な点も確認済み。

- **段階3(計測・数量化)の数え落としバグ**: `parent_agent._dedupe_elements()`が
  `(sheet_id, element_type, label_ja)`だけで同一物と判定していたため、同じ
  シート上に離れた位置で存在する同種の設備(例: ダウンライト3箇所)が、
  位置を見ずに1個へ潰されていた。タイル重複(`ingestion.py`の`tile_overlap_px`)
  による同一現物の重複読み取りと、単に同じラベルを持つ別々の現物とを、
  ラベルだけでは区別できていなかったのが原因。

  タイルの行・列が隣接する場合のみ「同一現物の可能性」として統合する
  Union-Find方式に変更(`_tiles_adjacent`)。位置情報が無い場合は統合しない
  (数え落としより数え過ぎの方が、人間が見て気付きやすく安全という判断)。

いずれも実データ・単体テストの両方で検証済み(`tests/test_error_analysis_fixes.py`)。

### 3.10 人間レビューゲート(`review_ui/`) — 精度が実用域に達するまでの一時的な確認工程

3.9節までの精度改善は、いずれも「バグを直したら実データで再テストする」という
反復でしか見つけられなかった。これは開発中に限った話ではなく、**運用開始後も
同じ反復(識別ミス・推論ミスを人間が指摘 → 原因を特定 → 直す → 再テスト)が
続く**という前提に立ち、その反復を効率化するための人間確認UIを`review_ui/`に
実装した。3.6〜3.9の全ての修正は、実際にこの形式のレビュー(最初は簡易スクリプト、
後にこのパッケージ)で見つかった問題への対応である。

**想定する運用フロー**(まだ実装されていないのは「orchestrator側のゲート制御と
FastAPI配信」の部分 — 下記「未実装」参照):

1. 見積作成者が図面を読み込ませる(初期設定 → Phase 0-3実行)
2. この画面(文字識別 → 数字識別 → 意味推論 → 3D理解、の4シート)が自動的に
   開き、認識ズレ・未識別・3D確認したい箇所を順番に確認する
3. 「確認完了」で初めて本推論(見積生成)が開始される
4. 本推論の出力(見積項目・数量・工数)に対しても、同じ形式の確認画面を
   もう一段用意し、「ここが分かりませんでした/推論しきれませんでした」を
   同様にフラグ→人間確認→再推論、という反復にする(出力側のレビュー画面は
   まだ未実装 — 現状あるのは入力(図面読み取り)側のみ)

**実装済み(`review_ui/`):**

- `character_review.py` — 文字/数字の識別結果を、パターン一致による透明な
  ヒューリスティック(`classify_word`)で確信/要確認/誤読疑いに分類。
  `KNOWN_VOCAB`は今回の2実データ(KDX802・アミューズメント施設)向けに
  校正した最小限の語彙であり、汎用辞書ではない — プロジェクト/CADベンダーが
  増えるごとに拡張が必要。
- `dimension_review.py` — **寸法・面積の整合性検証**。図面に印字された面積
  ラベル(㎡)は今回の2実データいずれにも存在しなかった(検索して確認済み)
  ため、外形寸法は`estimate_gross_footprint`(最大寸法チェーンからの概算)
  でしか出せない。この概算の裏付けとして`check_dimension_chains`
  (寸法の内訳を人間の電卓検算と同じ要領で再計算し、印字された合計と照合)
  を実データに対して実行したところ、**アミューズメント施設p.4だけで実際に
  3件の不一致を検出した**(例: 横方向の内訳 1700+800+4350+3000+1400+1800+
  3000+1400=17450mmに対し、近傍の合計表記は17225mm、225mmの差)。これは
  合成テストではなく実図面から見つかった本物の不一致であり、「計測・面積
  推論の誤りをどう検知するか」への直接の答えになっている。ただし
  `estimate_gross_footprint`自体は現状この不一致フラグを**参照していない**
  (`gross_footprint.sheet_has_unrelated_chain_mismatches`として存在は
  伝えているが、確信度を自動的に下げる処理はまだ無い) — 次の改善点。
- `solid_preview.py` — 3D復元(3.4節`solid_model_agent.py`の壁ポリゴン+
  天井高)を2D図面と並べて表示し、両者が一致するかを目視確認できるツール。
  アミューズメント施設の実データ(真のCADベクター図面、縮尺1/50)で実行し、
  36枚中23枚の壁に天井高(CH=2850mm)が正しく紐づいた状態を確認済み。
  KDX802のような「壁のベクター形状も縮尺表記も無いスキャン図面」では
  この3D復元は原理的に不可能であることも、同じ仕組みで確認済み
  (`SolidModel.warnings`に理由が出る)。
  **現状3Dに含まれていないもの**: 窓・ドア等の開口部の3D配置、
  「廊下」という概念区分、部屋ごとの床ポリゴン。これらは
  `solid_model_agent.build_solid_model`の出力に含まれていないため、
  この段階では検証しようがない — 次の拡張対象。
- `render.py` — 上記の抽出結果を、実際にドラッグ・ズーム操作できる
  自己完結HTMLページ(`templates/`)に埋め込む。テンプレートはプレース
  ホルダー(`__WORDS_JSON__`等)を持つ汎用テンプレートで、特定プロジェクト
  専用のスナップショットではない(`tests/test_review_ui.py`で合成PDFに
  対して実行し、正しく埋め込まれることを確認済み)。

**未実装(次のアクション):**

- `app.py`(FastAPI)からこれらのページを配信するエンドポイント、および
  orchestrator側で「人間確認が完了するまでPhase 4(本推論)に進まない」
  というゲートそのもの — 現状はレビューページを個別に生成・確認できる
  段階で止まっており、実行フローには未接続。
- 出力(見積結果)側のレビュー画面 — 入力(図面読み取り)側の3形式
  (文字/数字/3D)と同じ考え方を、生成された見積項目・数量・工数にも
  適用する。
- 「重なり合う工事」(壁下地→クロス→コンセント→空調、という同一座標での
  多工程の積層)の検証: これは3D復元(壁がどこにどの高さで立っているか)
  を土台として、その上に「この座標・この高さには、この順番でこの工種が
  乗る」という層情報を重ねる仕組みが必要で、土台となる3D復元の精度が
  実用域に達してから着手するのが妥当と判断し、現時点では未着手。

### 3.11 長さ・面積の推論検証(`measurement.py`) — 「三角スケール」と「外形寸法からの投影」

3.10節の最後に見つかった課題(「数字を読み取って面積・長さを推論するロジックが
実際に機能するか」の検証手段が無い)に対応した。人間の見積作成者が実際に図面を
読む際に使う、次の2つの技術をそのままコード化した:

1. **外形寸法チェーンからの投影**: 実際の図面は、間取りの壁1枚1枚に個別の寸法を
   振っているとは限らない。多くの場合、寸法は図面の外周(通り芯)にしか書かれて
   おらず、内部の壁の寸法は、その壁の位置から外周の寸法チェーンへ水平/垂直に
   たどって(投影して)読み取る。`vector_extractor.find_dimension_chains`で
   チェーンを取り出し、`measurement.project_span_mm`で対象の座標範囲に
   収まるラベルを合計する。
2. **三角スケール**: 寸法の記載が無くても、印刷縮尺が分かっていれば、紙の上の
   長さを物差しで測って実寸に換算できる。`measurement.pixel_distance_to_mm`
   (2点間の距離)と`measurement.polygon_area_sqm`(閉多角形の面積、シューレース
   公式)がこれに相当する。

**実データでの検証結果(正直に報告する):**

初回実装をアミューズメント施設p.4の実データ(壁のCADベクター実寸という正解が
既に分かっている)に対して走らせたところ、**重大な誤判定を自ら発見した**。
4本の柱すべてで「投影成功」と出たが、実際には目的の寸法チェーンがその柱から
垂直方向に約1000px(約6m)も離れた、無関係な場所のチェーンだった
(X座標がたまたま重なっていただけ)。`project_span_mm`が投影対象の軸方向の
位置しか見ておらず、チェーンとの垂直方向の距離を一切考慮していなかったのが
原因。`perp_px`(投影対象の垂直軸位置)と`max_perp_distance_px`
(既定400px)による絞り込みを追加して修正し、再検証した。

修正後、実際に近傍にチェーンがある7本の壁で再テストした結果:
**2本は投影による逆算値が実寸と一致(0mm差・3mm差)、5本は「関連するチェーンが
見つからない」という正直な失敗を報告**(推測値を出さない設計)。検証結果は
実データで公開ツールとして確認できる(下記)。

これに加えて、3.10節で見つかった寸法チェーンの内訳不一致(check_dimension_chains)
も同じページで実際に3件検出されており(`review_ui/dimension_review.py`の
docstring参照)、両方を1つの確認画面(`review_ui/dimension_review.py`の
拡張データ)にまとめてある。

いずれも`tests/test_measurement.py`・`tests/test_review_ui.py`で単体テスト済み
(投影の垂直距離フィルタが偽陽性を正しく除外することの回帰テストを含む)。

### 3.12 基準点による自己較正(「桝目」技術) — 実装したが、実データでは要注意という結論

3.11節の技術は「外形の寸法チェーンをそのまま合計する/そのままラベル位置で
照合する」ものだったが、ユーザーから「印字された縮尺自体が信用できない場合でも、
切りのいい(誤読しにくい)数字が明確に読める2箇所以上を基準点にして、そこから
実際のpx/mm比を逆算し、細かい基準線の桝目を作れば、寸法の書かれていない箇所でも
精度良く推定できるはず」という具体的な技術指摘を受けた。人間の見積作成者が実際に
行っている技術であり、実装した。

`measurement.calibrate_axis_from_anchors`: 2点以上の(ピクセル位置, 実寸mm)の
組から最小二乗法で`px_per_mm`と原点を求める。基準点が増えるほど(桝目が細かく
なるほど)ノイズが平均化される、という考え方をそのまま実装している。
合成データでの単体テストでは、既知の正解に対して正しく較正できることを確認済み
(`tests/test_measurement.py`)。

**実データでの検証結果(正直に報告する):** アミューズメント施設p.4の外形寸法
チェーン(3.11節で使ったものと同じ)に対して、ラベルが「区間の始点」「区間の
終点」「区間の中点」のどこに描画されているかという3通りの仮定でそれぞれ較正を
試したが、**いずれも大きくばらつき(残差の標準偏差62〜147px = 約360〜850mm)、
かつ最良のケースでも、このシートで既に実壁の座標から独立に検証済みの正しい
縮尺(px/mm=0.1732)と約20%もずれた**(最良の推定は0.1446)。

これは、この特定のチェーンの8個のラベルが、実は単純な1本の直線的な寸法線
ではない(hand-markupされた改修図面によくある、複数の寸法線が同じ高さに
バラバラに配置されている、または一部が別の基準に属している等)可能性を示して
いる。較正関数自体の実装・数式は合成データで正しさを確認済みだが、**どの実際の
寸法チェーンが「1本の直線として信頼して較正に使ってよいものか」を見分ける
判定はまだ実装していない** — 現状は残差(`residual_stdev_px`)の大きさを見て
人間が判断する必要がある。この判定を自動化するには、テキスト位置だけでなく、
実際の寸法線・引出線のベクター形状(`page.get_drawings()`の線分)を検出する
必要があると考えられ、次の課題として記録する。

なお、この技術が本領を発揮するのは「印字された縮尺が無い、または信用できない」
図面(例: KDX802のような現地調査スケッチ)においてだが、KDX802は逆に
そもそも共線の寸法チェーンが少なく(3.7節参照)、今回の2つの実データのどちらも
「基準点による自己較正」を実際にフルで検証できる理想的な条件(信頼できる基準点+
縮尺不明)を備えていない。より適したテストデータが見つかり次第、再検証する。

### 3.13 千倉相川邸(ベクターテキスト0件)での実パイプライン実行 — OCRエンジン自身の信頼度をtierに反映

千倉相川邸のPDF(26ページ)は完全に画像化されており、`vector_extractor`が
抽出できるベクターテキストが0件(すべてのページで`extract_ground_truth`が
`None`)。このため文字・数字・記号のPhase 1読み取りはOCRエンジンだけが
唯一の経路になる。

このサンドボックス環境には`config.py`が想定するローカルVLMサーバー
(Ollama等、`http://127.0.0.1:11434`)が実行されておらず(`curl`で
`Connection refused`を確認済み)、child/parent VLMエージェントは実行できない。
一方Tesseract+`jpn`トレーニングデータは実際にインストール済みで動作することを
確認したため、`DRAWING_AI_OCR_ENGINE=tesseract`で`ingestion.load_drawing_set`
→`tile_sheet`→`ocr_engine.ocr_tile`という実際のリポジトリのコードをそのまま
実行した(人間による手動読み取りは一切行っていない)。

**最初の実行で見つかった問題:** p.1の最初のタイル(113語、実際には印刷された
変更履歴メモで、目視確認の結果ほぼ全て正しくOCRされていた)を`classify_word`に
通したところ、**113語中113語が"red"に分類された**。原因は`classify_word`の
パターン辞書がCADの短い寸法トークン(プレーン数字・W/H/CH接頭辞・凡例語彙)
向けに較正されており、自由文の日本語文章(単漢字・助詞など)を一切想定して
いなかったこと。つまりOCR自体は機能していたが、レビューゲート側の分類器が
バグっていた。

**修正:** Tesseractは単語ごとに自身の信頼度スコアを返す
(`ocr_engine.OcrWord.confidence`)。実データで検証したところ、正しく読めた
112語は信頼度0.85〜0.97、唯一の誤読("畳"を"辿"と誤認識した箇所)は信頼度
0.00と、非常に強い実信号だった。そこで`GroundTruthWord`に`confidence`
フィールドを追加し(ベクター抽出テキストでは`None`のまま、意味を持たない)、
`classify_word(text, ocr_confidence=...)`はパターン辞書に一致しない語について
OCR信頼度が0.85以上なら green、0.5未満なら red、その間は amber と判定する
ように変更した(パターン一致がある場合はそちらを優先— 低信頼度でも既知の
寸法パターンなら green のまま)。

**修正後の再実行結果(p.1、タイル2枚、ユーザー指示通り確認対象10件超過で停止):**
136語中124語green(91.2%)、flagged 12件(amber 4 + red 8)。flagged項目は
実際に信頼度が低い(0-53%)語で、目視確認でも「辿→畳の誤読」「タイル境界での
部分的な誤読」など妥当な理由が付いていた。人間レビューUI(`review_ui`)を
実データで生成し、Artifactとして確認画面を公開した。

**まだ実施していないこと(正直に記録):** VLMエージェント(ensemble読み取り・
overview分類・spec/site/intent/detail agent)は依然としてローカルVLMサーバーが
無いため未実行。Tesseractは今回p.1の印刷文章では高精度だったが、これは
CADの微小な寸法数値・回転した注記・図面記号を含む密度の高い平面図ページでは
まだ検証していない(ocr_engine.pyのdocstring通り、OCR単体はVLMのgrounding
信号として設計されており、単独での小数字・記号の読み取り精度は未保証)。

### 3.14 タイル重複帯の未マージによる誤読ノイズ、およびPaddleOCRが使えない環境的制約

3.13節の結果をユーザーが目視確認したところ、「読みやすい簡単な文章でも
誤読が多数ある」という指摘を受けた。調査の結果、2つの独立した問題が
見つかった。

**問題1: タイル重複帯の未マージ(実際のバグ)。** `tile_sheet`は隣接タイルを
160px重複させて生成するが、各タイルは独立にOCRされるだけで、重複帯に
入った単語がどちらのタイルでも二重に読まれる、という統合処理が無かった。
重複帯のちょうど中間あたりで文字がクロップされると、そのタイル単体では
文字の一部しか見えないため誤読・ノイズ("A"、"を"、"に"、"-"等の孤立した
1〜2文字)が生成される。一方で隣接タイル側ではその文字が欠けずに完全に
写っているため正しく読める。つまり「読みやすい文章が誤読されている」ように
見えた箇所の多くは、実際には**同じ文字が別のタイルで既に正しく読まれている
のに、重複クロップ側の破片ノイズが未統合のまま結果に混入していた**のが
原因だった。

`ocr_engine.merge_tile_words`を追加して修正: 各タイルについて、隣接タイルとの
中間線までを「そのタイルが専有する領域」とみなし、単語の中心点がその領域に
入っている場合のみ採用する(`_tile_core_rect`)。これにより重複帯で二重読み
された単語は必ず「クロップの端ではなく中央寄りで読めたほう」に一本化される。
テスト(`tests/test_ocr_merge.py`)で合成データによる正しさを確認済み。

実データでの効果: p.1(15タイル)で修正前422語→修正後347語(75語が重複
ノイズとして除去)、green比率は0%(3.13節の最初の実行、パターン辞書バグ込み)
から87.9%(305/347)まで改善。残るflagged 42件は、実際に小さく密集した印刷
(表題欄の住所・電話番号・著作権表示など8〜10pt相当の細字)に集中しており、
目視確認でも"anchordesignAll"(複数行が結合)、"3-7-15-102/TEL/FAX:042-449-042t"
(末尾"9"を"t"と誤読)など、妥当な誤読だった。

**問題2: PaddleOCR(このプロジェクトの既定OCRエンジン)がこの環境では
実行不可能(環境的制約、コードの問題ではない)。** `config.py`の既定
`DRAWING_AI_OCR_ENGINE="paddleocr"`を実際に試すため、システムパッケージと
競合しない専用venvにインストールを試みたところ、パッケージのインストール
自体は成功した。しかし実行時、PaddleOCR 3.xはモデル重みを初回実行時に
huggingface.co/modelscope.cn/aistudio.baidu.com/bosのいずれかからダウンロード
する設計だが、**このサンドボックス環境のプロキシがこれら4ホスト全てへの
接続を組織ポリシーで拒否している**(`curl`で`connect_rejected`を確認済み)。
モデル重みを別経路で用意しない限り、この環境ではPaddleOCRは原理的に動作
しない。これはコードの不具合ではなく、ネットワークポリシーによる制約として
正直に記録する。

**現時点で選べる現実的な選択肢:**
1. Tesseract + `merge_tile_words`のまま、密集した細字領域はflagged件数が
   増えることを許容しつつ人間確認で補う(現在この方針で進行中)。
2. PaddleOCRのモデル重み配布元へのネットワークアクセスを許可する、または
   モデル重みファイルを別の経路(組織内ミラー等)で用意する。
3. ローカルVLMサーバー(Ollama等)を実際に起動し、`DRAWING_AI_CHILD_BASE_URL`
   等を向ける -- これが本来このプロジェクトが設計されたフル精度の経路。

### 3.15 見積作成アプリ(`phase1_service.py` + `ESTIMATE_TAB.html`) -- BUILD PRO OS本体への統合

3.13/3.14節のPhase1(文字・数字・記号)検証を、使い捨てのスクラッチスクリプト
ではなく、実際にBUILD PRO OS本体(PC版)から使える機能として恒久化した。

スクリプトで検証済みだったロジック(ingestion.load_drawing_set→tile_sheet→
ocr_tile→merge_tile_words→character_review.classify_word、stop_after_flagged

**`app.py`(拡張)**: `POST /phase1/analyze`(multipart、VLMサーバー不要で

本体アプリの巨大単一HTMLファイル(15000行超、80回近い継ぎ足し)へこれ以上
重い機能を直接書き足すリスクを避けるため、iframeで読み込む別ファイルとした。

## 5. セットアップと実行方法

### 5.1 依存関係

```bash
pip install -r requirements.txt
```

OCRエンジンは既定で PaddleOCR を想定しているが、requirements.txt ではコメントアウトしてある(重量級のため)。有効化する場合:

```bash
pip install paddleocr paddlepaddle
```

軽量に済ませたい場合は Tesseract + 日本語データを使う(`pytesseract` は requirements.txt に含まれている):

```bash
# 例: Debian/Ubuntu
sudo apt-get install tesseract-ocr tesseract-ocr-jpn
export DRAWING_AI_OCR_ENGINE=tesseract
```

どちらも未導入の場合はOCR無し(ビジョンAI単独)で自動的に動作を続けるが、精度は落ちる。

### 5.2 オープンソースAIモデルの用意

このパイプラインは OpenAI互換API を話すサーバーであれば何でも接続できる(モデル非依存)。動作確認用の推奨構成:

```bash
# Ollamaの例(子AI用: 軽量な日本語対応VLM)
ollama pull qwen2.5vl:7b
ollama serve   # http://127.0.0.1:11434/v1 で待受

# 親AI用(テキストのみで良い、やや大きめのモデル)
ollama pull qwen2.5:32b
```

接続先はすべて環境変数で切り替え可能:

```bash
export DRAWING_AI_CHILD_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_CHILD_MODEL=qwen2.5vl:7b
export DRAWING_AI_PARENT_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_PARENT_MODEL=qwen2.5:32b
export DRAWING_AI_CHILD_CONCURRENCY=6   # 子AIの同時実行数。処理時間目標に直結
```

既存の BUILD PRO 側が LM Studio(`http://127.0.0.1:1234/v1`)を使っているなら、同じサーバーを両方から指すことも可能。

### 5.3 サーバー起動

```bash
uvicorn app:app --host 0.0.0.0 --port 8000
```

- `GET /health` — 接続先モデル・設定の確認
- `POST /analyze` — 図面ファイル(複数可、multipart/form-data)を送信し、フェーズ0〜3の統合結果(JSON)を取得

### 5.4 テスト実行(実モデル不要)

```bash
python3 -m pytest drawing_ai/tests -q
```

タイル分割の網羅性、アンサンブル統合ロジック、重複除去、フェーズ1の完全性スコア、パイプライン全体の異常系耐性(一部の子AI呼び出しが失敗してもパイプライン全体は止まらないこと)を、擬似VLM応答で検証している。実際の図面画像とモデルでの精度検証は別途、本物の図面サンプルで行う必要がある(セクション7参照)。

## 6. 性能目標(30万円クラス/10万文字規模の図面を15〜30分で処理)

- 図面をタイル単位に分割し、子AIの呼び出しを**全タイルに対して並列発行**する。実際の並列数は `DRAWING_AI_CHILD_CONCURRENCY` で制御され、これがボトルネックを解消する主要なレバー(GPU/レプリカを増やすほど線形に短縮できる設計)。
- フェーズ0(概観)とOCRは軽量なので先に実行し、フェーズ1の対象タイルを配置図系シートに絞り込むなど、後段の呼び出し回数を減らしている。
- フェーズ3の親AIによる矛盾解消はコストが高いため、統合対象が一定件数(既定250件)を超える場合は決定的な統合結果にフォールバックし、親AI呼び出しがボトルネックにならないようにしている。
- `orchestrator.py` は経過時間を計測し、目標(既定15分)・上限(既定30分)を超えた場合は `PipelineRun.warnings` に理由と対処法(並列数の引き上げ、タイルサイズの見直し等)を記録する。

## 7. 既知の制限事項・今後の課題

正直な現状評価として、以下は**未検証・未実装**であり、本物の図面での検証が必須:

1. **AI(VLM)自体の精度検証は依然未実施**: セクション3のベクター根拠層により、ベクターPDFに含まれる文字・寸法・壁形状は誤読ゼロで確定できるようになったが、それでも判断が必要な部分(記号の意味解釈、手書き注記、スキャン画像図面、CADに埋め込まれていない情報)は依然としてVLM任せであり、そこの精度は本セッションにはGPU・実モデルが無いため未検証。実モデルを繋いでから計測・チューニングが必要。
2. **モデル選定はプレースホルダー**: `qwen2.5vl:7b` 等はあくまで動作確認用のデフォルト値。日本語建築図面(特に手書き注記・JIS建築記号)での精度は、候補モデル(Qwen2.5-VL, InternVL2.5, MiniCPM-V 2.6 等)を実際に比較して選定すべき。
3. **ベクター根拠層はPDFのみ対応**: DWG/DXF/JWWが本パイプラインに届く前に(BUILD PRO側や変換ツールで)PDF化される想定。JWW/DWGを直接パースしてベクター根拠を取得できれば、CADから一度もラスタライズせずに済む分、さらに精度・速度が上がる可能性がある(次の改善候補)。またベクターPDFであっても壁の塗りつぶし色は今回実データで観測した1ベンダーの流儀に基づく値なので、他のCADベンダー・他の会社のテンプレートでは色のキャリブレーションが別途必要になる。
4. **寸法チェーン検算・立体モデルの空間対応付けはヒューリスティック**: セクション3.2/3.4で述べた通り、チェーンの「総和候補」探索や壁↔天井高の対応付けは最近傍探索ベースであり、完全ではない(`match_distance_px` を必ず確認すること)。線分ジオメトリによる寸法数値の直接検証は実データで信頼性が低いと判断し、あえて実装していない。
5. **フェーズ4(数量拾い・利益率・見積書生成)は本パッケージのスコープ外**。ユーザーの要望通り「フェーズ1〜3が正しく機能してから」着手すべき部分で、`Phase3Result`(`solid_model` を含む)を入力として消費する設計にしてある。
6. **BUILD PRO OS 見積欄との外部連携**は `POST /analyze` のJSON契約(`schemas.py` の `PipelineRun`)を想定しているが、実際の連携コード(既存 `system/app.html` 側からの呼び出し)は未着手。

## 8. 次のアクション(推奨)

1. 実際の図面サンプル(できれば10〜20件、木造/RC/手書き含む、ベクターPDFとスキャン画像の両方)を用意し、Ollama等で候補VLMを繋いで `POST /analyze` を実行、フェーズ1〜3の出力(特に `verified_by_vector=False` の項目)を人間がレビューして精度を測る。
2. フェーズ1(敷地情報)から着手し、100%精度に達するまでプロンプト・タイリング・OCR設定を調整する(ユーザーの指定通り、フェーズが進むほど前段の精度が重要になるため)。
3. 他社・他CADベンダーの図面で `vector_extractor._WALL_FILL_COLOR` 等のキャリブレーション値を再検証する。
4. フェーズ1〜3が安定してから、既存 `system/app.html` の資料台帳(`bpRegisterAttachments`)からこのAPIを呼び出す連携コードを追加する。

### 3.16 本番運用の推奨構成(ホスティング・認識エンジン・データ保存)

見積作成タブを実際に使うために必要な3つの意思決定について、ユーザーから
「詳しくないので推奨を決めて指示してほしい」との依頼があったため、以下の
通り決定し、`render.yaml`へ反映した。

**認識エンジン: Claude API(Anthropic)をVLMとして使用。** 3.13/3.14節で
実施した通り、このセッションのサンドボックス環境ではローカルVLMサーバーが
無くPaddleOCRもネットワーク制限で使えず、Tesseract単体では小さい寸法数字・
密集した細字の精度が実用に届かなかった(README 3.13/3.14)。一方
`vlm_client.py`は元々「OpenAI互換のchat/visionエンドポイントなら何でも
繋げる」設計だったため、Anthropicが公式に提供している「OpenAI SDK互換
レイヤー」(`https://api.anthropic.com/v1/`、
[platform.claude.com/docs](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk)
で確認済み)を指すよう`render.yaml`の環境変数を設定するだけで、コード変更
ゼロのままPhase0〜3のフルパイプライン(child/parent エージェント、
アンサンブル、エスカレーション)が実際のClaudeモデルで動く。画像入力
(`image_url`+base64データURL)は「Fully supported」と公式ドキュメントに
明記されており、`vlm_client.py`が既に送っている形式とそのまま一致する。

- child_vlm(タイル画像を読む、visionが必要): `claude-sonnet-5`
- parent_llm(既に抽出済みのテキストを集約するだけ、visionは不要): `claude-haiku-4-5-20251001`(軽量・低コスト)

**正直な限界:** このOpenAI互換レイヤーはAnthropic公式ドキュメントで
「本番の長期利用は非推奨、モデル比較・検証用」と明記されている。まず
これで実際の精度を検証し、良好であれば将来的にAnthropic純正SDK
(Messages API)へ移行するのが望ましい(移行にはvlm_client.pyの書き換えが
必要になる)。またAPIキーは未設定(`sync: false`)のため、Render側の
環境変数画面で貼り付けが必要 -- ユーザーへの指示として案内済み。

**ホスティング: Render(`render.yaml`が既にこのリポジトリに存在)。**
Renderアカウントの作成・GitHub連携・環境変数の入力はこちらから代行できない
