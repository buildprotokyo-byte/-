# BUILD PRO Drawing AI — 図面自動読み取りパイプライン (フェーズ0〜3)

## 1. 現状分析のまとめ

アップロードされた `BUILD_PRO_V13_5_6_DIRECT_START_WINDOWS.zip` を解析した結果:

- 中身は `system/app.html`(1.2MB)を中心とした Windows ローカル業務アプリ。案件管理・見積計算・スケジュール・印刷帳票・複数PC間同期(`hub_client.js`)などを備えた完成度の高い**業務システム**。
- AI接続は既に **LM Studio / OpenAI互換API**(`http://127.0.0.1:1234/v1`)方式で実装済み。オープンソースAIへの接続口そのものはすでにある。
- しかし **図面(PDF/DWG/DXF/JWW/画像)を実際に読み取るコードは存在しない**。添付ファイル処理 `fileText()` は `.txt/.csv/.md/.json/.xml/.html/.log` のみを読み、PDFや画像は空文字列を返す。OCR・画像認識・線/記号解析・寸法パースは未実装。
- 現状の「AI」は、担当者が図面を見て**手入力した数値・手書きメモ**をもとに文章生成・分析コメントを書くだけの役割。見積の数量根拠は完全に人力入力。

→ ユーザーの診断通り、**フェーズ1〜3(図面を読んで理解する部分)は実質ゼロ**。本パッケージはこの欠落部分を新規に埋めるもの。

## 2. 設計方針

ユーザーの要望どおり、以下の人間的な読み取りプロセスをそのままパイプラインの段階に対応させた:

| 人間の思考プロセス | パイプラインの段階 | 実装 |
|---|---|---|
| 図面一式をざっと見て「どんな工事か」を掴む | **フェーズ0: 概観(overview)** | シート単位で縮小画像を1回だけAIに見せ、種別分類+一言要約 |
| 敷地条件を正確に把握する | **フェーズ1: 敷地情報** | 配置図タイルから事実を1件ずつ抽出、100%精度目標のため個別に確信度採点 |
| 「何をしたいか」を読み取り文章化する | **フェーズ2: 意図の文章化** | 全タイルから工事意図を抽出→親AIが案件概要文に統合 |
| 数字・線・記号を正確に読み、意味を理解する | **フェーズ3: 詳細読み取り** | 最重要工程。タイルごとに複数回読み取り(アンサンブル)+OCR裏取り |
| 平面情報+高さ方向の情報を頭の中で立体化する | **フェーズ3補助: 立体統合** | 平面図の要素と立面/断面図の寸法を突き合わせ、室ごとの階高・壁高を推定 |

### 「子AI×多数 → 親AI」構成

- **子AI**: 図面を小さいタイル(既定 1024px、160pxオーバーラップ)に分割し、タイル1枚=1回の推論で読ませる。大きな図面を一度に読ませると精度が落ちる、という問題への直接対応。
- **親AI**: 全タイルの子AI出力を統合。まず決定的なロジックでタイル重複(オーバーラップ領域)の重複除去を行い、その後より大きいモデルに矛盾解消を依頼する(失敗時は決定的な統合結果にフォールバックし、パイプライン全体は止まらない)。

### 精度を上げるための具体的な工夫

1. **根拠テキストによる裏取り**(`grounding.py`、詳細はセクション3): 各タイルに対し、可能ならPDFのベクター文字レイヤー(誤読ゼロ)、無ければOCR(PaddleOCR/Tesseract)の原文をVLMのプロンプトに同梱。VLM単独では起きやすい数字の読み違いを、この根拠との突き合わせで検出・加減点する。ベクター根拠との不一致は強い減点(-0.5)、一致は強い加点(+0.3)かつ `verified_by_vector=True` として親AIの書き換え対象から除外する。
2. **アンサンブル読み取り**(フェーズ1・フェーズ3): 同じタイルを既定3回、独立に読ませ、一致した読み取りは確信度を加点、一致しなかったものはそのまま残して低確信度フラグを立てる。フェーズ1は下流工程が無く100%精度が目標のため、全フェーズ中もっとも大きい加点幅を与えている。
3. **フェーズ1は事実単位で個別採点**: 一つの文章にまとめず、「敷地面積」「前面道路幅員」等をキーごとに個別のオブジェクトとして出力させ、それぞれに確信度と根拠原文(`raw_evidence_text`)を持たせる。100%の精度が求められる以上、「だいたい合っている要約」ではなく「合っているか個別に検証できる事実のリスト」にした。
4. **未読取項目の可視化**: フェーズ1は期待される項目(敷地面積・前面道路幅員・用途地域・建蔽率・容積率・セットバック・所在地)のうち何が読み取れなかったかを `unresolved_questions` として明示する。

## 3. 精度100倍化フォーメーション(ベクターPDF根拠層)

「基本設計(子AI×多数→親AI)は変えず、全項目に対して精度の基準を桁違いに引き上げ、立体を推論するフォーメーションを組む」という要望に対する実装。ポイントは、AIに「読ませて当てさせる」対象そのものを減らし、**読めるものはAIに読ませず断定的に確定させる**層を新設したこと。

### 3.1 発見: このクラスの図面はスキャン画像ではなくベクターPDFである

実際にユーザー提供の図面(石川県ホテル計画、A3・7枚)を調べたところ、CAD由来のPDFは寸法数字・室名・注記が**PDFの文字レイヤーに厳密な座標付きテキストとして埋め込まれている**ことが判明した(`page.get_text("words")` で1文字も誤らずに取得可能)。壁も塗りつぶしポリゴン(`page.get_drawings()`)として厳密な座標で埋め込まれている。つまりこの種の図面では、数字や文字を「画像から読み取る」必要が本来無く、**ファイルから直接、誤読の可能性ゼロで取り出せる**。

### 3.2 新設した層: `vector_extractor.py`

- **文字レイヤー抽出**: 座標付きの正確な文字列をタイル単位に切り出し(`words_in_bbox`)、子AIのOCR代わりの「根拠テキスト」として渡す。従来のOCR(Tesseract)は**タイルにベクター文字が無い場合のみ**のフォールバックに格下げ。
- **縮尺の自動特定**: 表題欄の「縮尺」ラベル近傍から「1/50」等のトークンを検出し、レンダリングDPIと組み合わせて `mm_per_px` を数式的に算出(`25.4×縮尺分母÷DPI`)。線分やテキストの実寸換算に使う。
- **壁ポリゴン抽出**: このCADベンダーが壁を一貫した灰色の塗りつぶしポリゴンで描画していることを実データで確認し、その色でフィルタして壁の輪郭をそのまま抽出(モデル推論ゼロ)。
- **寸法チェーン検算(加算検算)**: 人間が電卓で行う「内訳の合計=総寸法か」の確認を、テキスト座標のクラスタリングのみで機械的に実施。線分とのマッチングは実データで検証した結果、CADベンダーごとの描画流儀に依存しすぎて汎用的に信頼できないと判断し**採用を見送った**(判断根拠は本ファイル末尾のトレードオフ注記、および `vector_extractor.py` のモジュール docstring 参照)。空間的に無関係な数値を誤って合計候補にしないよう、チェーンの座標範囲でも候補を絞り込んでいる。

### 3.3 信頼度への反映(`grounding.py`)

読み取りソースの信頼階層を全フェーズで統一:

1. **ベクター根拠と一致** → 大きく加点(数値+0.3、ラベル+0.25)、`verified_by_vector=True` を明示
2. **ベクター根拠が存在するのに不一致** → 大きく減点(-0.5)。ハルシネーションの強いシグナル
3. **ベクター根拠が無く、OCRと一致/不一致** → 従来通りの小さな加減点(+0.1/-0.2)。OCRは実測で再現率が低いことが分かっているため

さらに、`verified_by_vector=True` の読み取りは**親AIによる矛盾解消の対象から除外**し、統合結果へそのまま無編集で反映する(`parent_agent.aggregate_phase3`)。根拠のある確定情報をモデル呼び出しの気まぐれで書き換えさせない、という原則を徹底した。

### 3.4 立体推論フォーメーション: `solid_model_agent.py`

平面×高さを頭の中で組み立てる、というユーザーの要望に対し、**AIの推測に頼らない最小限の立体モデル**を構築する:

- 壁: ベクター抽出した塗りつぶしポリゴンをそのまま実寸(mm)の壁フットプリントとして採用
- 天井高: 図面中の「CH=2500」等の表記をそのままの数値として抽出(誤読の余地なし)
- 両者の対応付け: 壁・室要素ごとに最も近いCH=ラベルを最近傍探索で割り当て、マッチ距離を `match_distance_px` として明示(この対応付けだけはヒューリスティックであることを隠さない)

フルBIMではないが、**壁の位置と高さの両方が実測値に紐づいた**最小限の立体表現になっている。

### 3.5 実図面での効果測定(石川県ホテル計画、7枚)

同一タイルを従来方式(OCR裏取り)と新方式(ベクター根拠)の両方で実際に処理し比較:

| 寸法 | 従来(OCR裏取り) | 新方式(ベクター根拠) |
|---|---|---|
| 2050mm | confidence 0.80 | confidence 1.00, verified_by_vector=True |
| 858mm | confidence 0.75 | confidence 1.00, verified_by_vector=True |
| 850mm | confidence 0.80 | confidence 1.00, verified_by_vector=True |
| 92mm(壁厚) | confidence 0.40(要確認) | confidence 0.90, verified_by_vector=True |

図面セット全体(7枚・105タイル)での実測:

- **92%のタイル(105枚中92枚)でベクター根拠が取得でき、OCR呼び出しを完全にスキップ**(精度向上と同時に処理時間も削減)
- 文字レイヤーから **641個の文字列**を誤読ゼロで抽出
- 壁ポリゴンを **168個**抽出、うち **92個**を天井高ラベルと対応付け
- 縮尺(mm/px)を7枚すべてで一貫して自動算出(5.773mm/px、1/50・220DPI相当)

### トレードオフに関する注記(線分マッチングを採用しなかった理由)

当初、寸法数字とその寸法線の実測長さを線分ジオメトリで直接突き合わせる案も検討したが、実データで試したところ寸法線・引出線・無関係な什器線が同系統の色を共有しており、汎用的な数値↔線分の対応付けは信頼できないと判断した。誤った「幾何学的検証」を出すくらいなら出さない方がよいという判断で、このアプローチは不採用とした(`ScaleConsistencyFlag` のスキーマは将来の拡張用に残してあるが、現状は常に空)。

### 3.6 仕様書読解AI(COAI-01: `agents/spec_agent.py`)

図面本体より先に読むべき最優先の精度投資対象として設計した工程。仕様書(仕上げ表・
内部仕上げ表・外部仕上げ表・仕様書一覧・特記仕様書・建具表など、名称は案件ごとに
異なるが「部屋や部位ごとの仕上げ・下地・製品仕様を一覧化し、工事全体を俯瞰できる
資料」であれば対象に含む — `SheetType.SPECIFICATION`)から、部屋単位で仕上げ・下地・
製品情報を読み取る。

Phase 1(敷地情報)と同じ精度の考え方を適用している:

- **ベクターground truthの適用**: 仕様書PDFがベクターネイティブな場合、`grounding.py`
  の信頼階層(ベクター文字 > OCR > モデル単独)をそのまま利用する。
- **アンサンブル**: `settings.spec_ensemble_size`(既定3)回、独立に読み取ってから
  照合する(Phase 1と同じ「ここは省略できない」という判断)。
- **テーブル構造を先に抽出してから意味推論する**: `vector_extractor.extract_table_rows()`
  がベクター文字を行単位にグルーピングし(`Tile.ground_truth_table_rows`)、モデルには
  「すでに行として整理された正確なテキスト」を優先的な手がかりとして渡す。仕上げ表の
  レイアウトは設計事務所ごとに大きく異なるため、構造把握と意味推論を1回のモデル呼び出しで
  同時にやらせるより頑健。
- **用語の正規化**(`terminology.py`): 「CL」「クロス」「ビニールクロス」のような
  表現揺れを公開基準寄りの用語に正規化しつつ、原文(`raw_finish_term`)も必ず保持する。

固定の3つの問い(基本情報 / 工事範囲を絞り込む言葉 / どうしたいか・変更点)を、
**見つからない場合も含めて毎回同じJSONスキーマで**モデルに投げる設計にしている。
これらの結果は独立した第4の構造として持たず、既存のPhase 1/2にそのまま合流させる
(基本情報→`SiteFact`として`aggregate_phase1`へ、変更点→`IntentStatement`として
`aggregate_phase2`へ)。役割の重複を防ぐため(建築一式工事AIを不採用にしたのと同じ
判断基準)であり、かつ仕様書由来の基本情報・意図はしばしば図面から読み取るより
高精度なため、Phase 1/2自体の精度向上にも直接寄与する。「工事範囲を絞り込む言葉」
だけは既存のどの構造にも対応物が無いため、`SpecResult.scope_target_terms`として
独立に保持する。

部屋単位の仕上げ詳細は`parent_agent.aggregate_spec()`でタイルをまたいで統合され、
同じ部屋・同じ仕上げで下地の既存/新規判定がタイル間で食い違った場合は`ambiguous_flags`
に正直に記録する(黙って片方を採用しない)。

### 3.7 面積の多段階フォールバック推論(`estimate_gross_footprint` / `area_parsing.py`)

実案件のブラインドテスト(KDX中野坂上ビル802号室、原価表非参照)で判明した実際の
限界: 壁ポリゴンが抽出できない図面(スキャン図面、現地実測annotated図、
`_WALL_FILL_COLOR`と一致しないCADベンダーの塗りつぶし規則等)では、床面積が
一律「不明」になっていた。これは一度きりの不具合ではなく、**単一の推論経路が
使えない場合は別の経路から逆算する、という段階的フォールバックが存在しなかった
という構造的な穴**だった。

面積の算出経路を、精度が高い順に以下のように多段階化した。いずれかが使えなければ
次の経路を試し、複数の経路から値が得られた場合は`aggregate_phase1`の統合ロジックが
自動的に「一致すれば確信度を上げる」「食い違えば`unresolved_questions`に残す」形で
整合性を取る(黙って片方を捨てない)。

1. **壁ポリゴン(`SolidModel`)** — ベクターPDFの塗りつぶしパスから直接算出。最も正確。
2. **印字された面積表記(`ElementReading.area_sqm`, `area_parsing.py`)** — 図面に
   「5.3m2」「12.5畳」等の面積が印字されていれば、フェーズ3の子AIがそれを`area_text`
   として書き写し、決定論的に数値化する(畳→m2は1畳=1.62m2で換算)。
3. **寸法チェーンからの外形概算(`estimate_gross_footprint`)** — 上記が両方とも
   使えない場合、シート上の最大の横方向・縦方向の寸法チェーンの合計値を「グリッド
   外形の概算」として採用する。**図面種別で絞り込まず、ベクター根拠がある全シートに
   対して実行する**(敷地図・平面図に限らず、電気図面等が同じ外形寸法チェーンを
   たまたま持っていることもあるため — 「1つの資料だけが答えを持っているとは限らない」
   という考え方をそのまま実装したもの)。
4. どれも得られない場合のみ、正直に「不明」として残す。

## 4. ディレクトリ構成

```
drawing_ai/
  config.py           # モデル接続先・タイルサイズ・時間予算・アンサンブル数などの設定(環境変数で上書き可)
  schemas.py          # 全フェーズの入出力データ契約 (pydantic)
  ingestion.py        # PDF/画像の読み込み・ページレンダリング・タイル分割
  vector_extractor.py # ベクターPDFの文字レイヤー・壁ポリゴン・縮尺・寸法チェーン検算・テーブル行抽出(モデル呼び出しゼロ)
  grounding.py        # ベクター根拠/OCRの信頼階層を全フェーズで統一する共通ロジック
  terminology.py       # 仕様書の仕上げ用語の表記揺れを公開基準寄りの用語に正規化する辞書
  area_parsing.py      # 図面に印字された面積表記(5.3m2/12.5畳等)を数値化する決定論的パーサー
  ocr_engine.py        # OCRラッパー(PaddleOCR / Tesseract / フォールバック。ベクター根拠が無いタイルのみ使用)
  vlm_client.py        # OpenAI互換API(Ollama/LM Studio/vLLM)への非同期クライアント
  prompts.py            # 各フェーズ用の日本語プロンプト
  orchestrator.py       # 仕様書→フェーズ0→1→2→3の実行順序・並列実行・時間予算管理・幾何チェック呼び出し
  agents/
    overview_agent.py            # フェーズ0
    spec_agent.py                 # COAI-01: 仕様書読解AI(アンサンブル+ベクター根拠+テーブル構造抽出込み)
    site_agent.py                # フェーズ1(アンサンブル込み)
    intent_agent.py               # フェーズ2
    detail_agent.py               # フェーズ3(アンサンブル+ベクター根拠込み)
    vertical_synthesis_agent.py  # フェーズ3補助(立体統合、テキストベース)
    solid_model_agent.py          # フェーズ3補助(立体推論フォーメーション、幾何ベース・モデル呼び出しゼロ)
    parent_agent.py               # 親AI: 統合・重複除去・矛盾解消(ベクター確定情報は除外)
  tests/          # モック(擬似)VLMによる結合テスト+ベクター抽出の実PDFテスト。実モデル無しで検証可能
app.py            # FastAPIサーバー(外部連携用エントリポイント)
requirements.txt
render.yaml
```

## 5. セットアップと実行方法

### 5.1 依存関係

```bash
pip install -r requirements.txt
```

OCRエンジンは既定で PaddleOCR を想定しているが、requirements.txt ではコメントアウトしてある(重量級のため)。有効化する場合:

```bash
pip install paddleocr paddlepaddle
```

軽量に済ませたい場合は Tesseract + 日本語データを使う(`pytesseract` は requirements.txt に含まれている):

```bash
# 例: Debian/Ubuntu
sudo apt-get install tesseract-ocr tesseract-ocr-jpn
export DRAWING_AI_OCR_ENGINE=tesseract
```

どちらも未導入の場合はOCR無し(ビジョンAI単独)で自動的に動作を続けるが、精度は落ちる。

### 5.2 オープンソースAIモデルの用意

このパイプラインは OpenAI互換API を話すサーバーであれば何でも接続できる(モデル非依存)。動作確認用の推奨構成:

```bash
# Ollamaの例(子AI用: 軽量な日本語対応VLM)
ollama pull qwen2.5vl:7b
ollama serve   # http://127.0.0.1:11434/v1 で待受

# 親AI用(テキストのみで良い、やや大きめのモデル)
ollama pull qwen2.5:32b
```

接続先はすべて環境変数で切り替え可能:

```bash
export DRAWING_AI_CHILD_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_CHILD_MODEL=qwen2.5vl:7b
export DRAWING_AI_PARENT_BASE_URL=http://127.0.0.1:11434/v1
export DRAWING_AI_PARENT_MODEL=qwen2.5:32b
export DRAWING_AI_CHILD_CONCURRENCY=6   # 子AIの同時実行数。処理時間目標に直結
```

既存の BUILD PRO 側が LM Studio(`http://127.0.0.1:1234/v1`)を使っているなら、同じサーバーを両方から指すことも可能。

### 5.3 サーバー起動

```bash
uvicorn app:app --host 0.0.0.0 --port 8000
```

- `GET /health` — 接続先モデル・設定の確認
- `POST /analyze` — 図面ファイル(複数可、multipart/form-data)を送信し、フェーズ0〜3の統合結果(JSON)を取得

### 5.4 テスト実行(実モデル不要)

```bash
python3 -m pytest drawing_ai/tests -q
```

タイル分割の網羅性、アンサンブル統合ロジック、重複除去、フェーズ1の完全性スコア、パイプライン全体の異常系耐性(一部の子AI呼び出しが失敗してもパイプライン全体は止まらないこと)を、擬似VLM応答で検証している。実際の図面画像とモデルでの精度検証は別途、本物の図面サンプルで行う必要がある(セクション7参照)。

## 6. 性能目標(30万円クラス/10万文字規模の図面を15〜30分で処理)

- 図面をタイル単位に分割し、子AIの呼び出しを**全タイルに対して並列発行**する。実際の並列数は `DRAWING_AI_CHILD_CONCURRENCY` で制御され、これがボトルネックを解消する主要なレバー(GPU/レプリカを増やすほど線形に短縮できる設計)。
- フェーズ0(概観)とOCRは軽量なので先に実行し、フェーズ1の対象タイルを配置図系シートに絞り込むなど、後段の呼び出し回数を減らしている。
- フェーズ3の親AIによる矛盾解消はコストが高いため、統合対象が一定件数(既定250件)を超える場合は決定的な統合結果にフォールバックし、親AI呼び出しがボトルネックにならないようにしている。
- `orchestrator.py` は経過時間を計測し、目標(既定15分)・上限(既定30分)を超えた場合は `PipelineRun.warnings` に理由と対処法(並列数の引き上げ、タイルサイズの見直し等)を記録する。

## 7. 既知の制限事項・今後の課題

正直な現状評価として、以下は**未検証・未実装**であり、本物の図面での検証が必須:

1. **AI(VLM)自体の精度検証は依然未実施**: セクション3のベクター根拠層により、ベクターPDFに含まれる文字・寸法・壁形状は誤読ゼロで確定できるようになったが、それでも判断が必要な部分(記号の意味解釈、手書き注記、スキャン画像図面、CADに埋め込まれていない情報)は依然としてVLM任せであり、そこの精度は本セッションにはGPU・実モデルが無いため未検証。実モデルを繋いでから計測・チューニングが必要。
2. **モデル選定はプレースホルダー**: `qwen2.5vl:7b` 等はあくまで動作確認用のデフォルト値。日本語建築図面(特に手書き注記・JIS建築記号)での精度は、候補モデル(Qwen2.5-VL, InternVL2.5, MiniCPM-V 2.6 等)を実際に比較して選定すべき。
3. **ベクター根拠層はPDFのみ対応**: DWG/DXF/JWWが本パイプラインに届く前に(BUILD PRO側や変換ツールで)PDF化される想定。JWW/DWGを直接パースしてベクター根拠を取得できれば、CADから一度もラスタライズせずに済む分、さらに精度・速度が上がる可能性がある(次の改善候補)。またベクターPDFであっても壁の塗りつぶし色は今回実データで観測した1ベンダーの流儀に基づく値なので、他のCADベンダー・他の会社のテンプレートでは色のキャリブレーションが別途必要になる。
4. **寸法チェーン検算・立体モデルの空間対応付けはヒューリスティック**: セクション3.2/3.4で述べた通り、チェーンの「総和候補」探索や壁↔天井高の対応付けは最近傍探索ベースであり、完全ではない(`match_distance_px` を必ず確認すること)。線分ジオメトリによる寸法数値の直接検証は実データで信頼性が低いと判断し、あえて実装していない。
5. **フェーズ4(数量拾い・利益率・見積書生成)は本パッケージのスコープ外**。ユーザーの要望通り「フェーズ1〜3が正しく機能してから」着手すべき部分で、`Phase3Result`(`solid_model` を含む)を入力として消費する設計にしてある。
6. **BUILD PRO OS 見積欄との外部連携**は `POST /analyze` のJSON契約(`schemas.py` の `PipelineRun`)を想定しているが、実際の連携コード(既存 `system/app.html` 側からの呼び出し)は未着手。

## 8. 次のアクション(推奨)

1. 実際の図面サンプル(できれば10〜20件、木造/RC/手書き含む、ベクターPDFとスキャン画像の両方)を用意し、Ollama等で候補VLMを繋いで `POST /analyze` を実行、フェーズ1〜3の出力(特に `verified_by_vector=False` の項目)を人間がレビューして精度を測る。
2. フェーズ1(敷地情報)から着手し、100%精度に達するまでプロンプト・タイリング・OCR設定を調整する(ユーザーの指定通り、フェーズが進むほど前段の精度が重要になるため)。
3. 他社・他CADベンダーの図面で `vector_extractor._WALL_FILL_COLOR` 等のキャリブレーション値を再検証する。
4. フェーズ1〜3が安定してから、既存 `system/app.html` の資料台帳(`bpRegisterAttachments`)からこのAPIを呼び出す連携コードを追加する。
