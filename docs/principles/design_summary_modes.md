## 1. 【最重要】名前がぶつかっている

**`killer_question/precision_mode.py` に、すでに `PrecisionMode`(精密/標準/概算)がある。**
名前も日本語の呼び名も同じだが、**決めているものが違う。**

| | 既にあるもの | 今回おーちゃんが決めたもの |
| --- | --- | --- |
| 何を切り替えるか | **どこまで質問を続けるか**(キラークエスチョンの打ち切り条件) | **図面をどう読むか**(範囲の絞り込みと、概算の数量を出してよいか) |
| 段の数 | 3つ(精密/標準/概算) | 2つ(精密/概算) |
| 既定 | **標準** | **精密** |
| いま本番で効くか | **効かない**(`killer_question/engine.py` と `benchmarks/` だけ。`read_drawing()` からは呼ばれない) | まだ無い |

**同じ名前にしてはいけない。** 「概算モードにして」と言われたときに、
質問を早く打ち切る話なのか、概算の数量を出してよい話なのかが決まらなくなる。

**提案する名前: `ReadingMode`(`PRECISE` / `ROUGH`)**、置き場所は `intake/reading_mode.py`。
日本語の呼び名は原文どおり「精密モード」「概算モード」のまま使い、
**既存の `PrecisionMode` は「質問モード」と呼び分ける。**
→ これも判断待ち(下の4)。

## 2. いまどうなっているか(現物で確認)

  `estimating/` を import していない)。
- **「確かめるべき問い」を持つ場所が無い。** 人に聞く経路は3つあるが、どれも
  「あるはずのものが見つからない」を起点にしていない
  (`docs/principles/principle_conformance_review.md` 項目26〜29)。
- **仕上表を読む経路はある。** `axes/image_axis/schedule_tables.py` が内装仕上表を

## 3. 設計

### 3-1. メニュー(要約資料の項目の一覧)

```
MenuItem
  item_id        … この一覧の中で一意。根拠を指すのに使う
  text           … 資料に書かれていた言葉そのまま。言い換えない
  where          … どの資料のどのページのどこか(位置つき)
  work           … 工事の項目(読めた範囲。読めなければ空)
  place          … 場所と範囲(同上)
  existing       … 既存の扱い(同上)
  product        … 品番(同上)
  spec           … 仕様(同上)
  confidence     … 読み取りの確かさ。OCR なら化けるので必須
```

**読めなかった欄は空にする。既定値で埋めない。**
`text` は**必ず原文のまま**残す。言い換えた時点で、後から答え合わせができなくなる。

### 3-2. 強い問い

各 `MenuItem` から `StrongQuestion` を1件作る。

- **「必ず図面を探し切る」は、探索を打ち切らないという意味に限る。**
  見つからなかったことを、見つかったことにはしない。
- **数量は観測からしか出さない。** `StrongQuestion` は数量を持たない。
  持つのは「何を探すか」と「探した結果」だけ。
- 結果は3つのどれかになる。
  - `found` … 図面の観測に結びついた。**結びつけた根拠を必ず持つ**(3-4)
  - `not_found` … 探し切って見つからなかった → **人への重要な確認事項として出す**
  - `not_searched` … 探せなかった(スキャンで読めない、対象のページが無い等)。
    **`not_found` と混ぜない。** 「探したが無い」と「探せていない」は意味が違う

### 3-3. メニュー外

図面の観測のうち、どの `MenuItem` にも結びつかなかったものを `off_menu` として出す。
**捨てない。** これが「メニューは読む範囲を狭めない」(第2層1行目)の担保になる。

### 3-4. 同一視の根拠

メニューの言葉と、図面や見積の言葉が違うときに同じとみなしたなら、その判断を残す。

```
Identification
  menu_item_id      … どのメニュー項目か
  observed_target   … どの観測か
  basis             … 同じとみなした理由(完全一致/品番の一致/言い換え表の項目/…)
  basis_source      … その理由の出どころ。言い換え表なら、その表のどの行か
```

**言い換え表はコードに埋め込まず、差し替えられる設定として持つ**
(`estimating/rules.py` が会社の積算ルールをそうしているのと同じ形)。

### 3-5. 2つのモード

```
ReadingMode = PRECISE | ROUGH     # 既定は PRECISE
```

| | 精密モード(既定) | 概算モード |
| --- | --- | --- |
| メニューの使い方 | 強い問いとして使う | **工事範囲を先に絞り**、その範囲を重点的に読む |
| 数量 | **観測からだけ** | 部屋の面積などからの概算も出してよい |
| 概算で出した数量の扱い | ― | **必ず「仮説に基づく」。自動確定させない** |
| メニュー外 | 出す | **出す**(絞り込んでも捨てない) |

**精密モードの既存の推論を壊さないための約束:**

1. **`ReadingMode` を渡さなければ精密モードになり、その経路は今までと1行も変わらない。**
   概算モードの処理は、精密モードの経路に `if` を挟むのではなく、**別の関数に分ける。**
2. 概算で出した数量は、**`derivation="assumed"` 相当の由来を必ず持つ。**
   `axes/reading/protocol.py` が既に持っている「一般則で補った」の扱いに乗せる
   (`is_hard_eligible` が1箇所で落とすので、階層1には原理的に上がらない)。
3. **概算モードでもメニュー外は出す。** 絞り込みを捨てる理由にしない。

## 4. 判断待ち(おーちゃんに決めてほしい)

1. **名前をどうするか。** 提案は `ReadingMode`(精密/概算)と、既存の `PrecisionMode` を
   「質問モード」と呼び分けること。**推奨する理由: 同じ言葉で別のものを指すと、
   後から読む人が必ず取り違える。**
2. **先に何を作るか。** 推奨は**要約資料を項目の一覧として読む実装**。
   モードの切り替えは、切り替える中身ができてからのほうが早い。
   **仕上表は既に読めるので、そこから始めるのが一番近い。**
3. **「必ず図面を探し切る」をどこまでやるか。** 全ページを毎回見るのか、
   メニューの `place` が指すページから始めるのか。前者は時間がかかり、
   後者は **`place` を信じることになるので、第2層の「読む範囲を狭めない」と擦れる。**
   推奨は**全ページを見て、`place` は探す順番にだけ使う**(見つからなければ他も見る)。
4. **概算モードの数量を、どの単位まで出すか。** 部屋の面積が要るが、
   **室の輪郭を取る実装がまだ無い**(面積25項目中22項目がここで止まっている)。
   概算モードは、それができるまで動かない可能性がある。
