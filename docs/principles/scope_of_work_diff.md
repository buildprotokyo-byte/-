## 0. 要点だけ先に

1. **工事内容を作る層が1つも無い**ことを確認した([一覧](./principle_conformance_review.md) の21番のとおり)。
   `PagePairing` はページの対応を記録するだけで、差分を作らない。`estimating/` にも撤去・新設が無い。
2. **差分は、読み取りの層でも当てはめの層でもなく、その間に置く。**
   新しい層 `estimating/scope_diff.py` を提案する。入力も出力も `QuantityItem` なので、
   `map_quantities()` と規則ファイルの仕組みは**変えずに済む**。
3. **差分を引き算で作らない。** 現況3件・計画2件から「撤去1件」を自動で出さない。
   1件撤去したのか、3件撤去して2件新設したのかは、数の差では決まらない。
4. **現況が不明なとき、既定の仮説は「現況は不明のまま」である。**
   「現況は無い(＝全部新設)」も「現況は計画と同じ(＝既存のまま)」も置かない。どちらも黙って嘘をつく。
5. この設計が届くために、**既存の2か所を直す必要がある**(3-1節・3-2節)。
   どちらも**既存の判定のしかたを変える変更**なので、実装したら PR のまま待つ側に入る。
6. **原則と既存のテストが2件食い違っている**(8節)。テストは書き換えず、食い違いとして報告する。

## 1. 差分の層をどこに置くか

### 1-1. いまの流れ

```
PDF ─→ intake/drawing_intake.py ─→ arbitration/(仲裁層) ─→ estimating/from_intake.py
                                                                    │
                                                            QuantityItem の並び
                                                                    │
                                                        estimating/mapping.py ─→ 見積の行
```

`開き戸::現況::ページ1` と `開き戸::計画::ページ2` は、この流れを**最後まで別々の数量として通る。**
同じ行に当たれば `estimating/mapping.py` が衝突として人へ回す(足さない)。
**足さないのは正しいが、それは差分ではない。** 「同じ建具を二重に数えない」という
安全側の処理であって、「現況にあったものが計画で無くなった＝撤去」という**意味**はどこにも作られない。

### 1-2. 差分を置く位置

```
… ─→ estimating/from_intake.py ─→ QuantityItem の並び(現況のもの・計画のもの)
                                          │
                              ★ estimating/scope_diff.py(この設計)
                                          │
                                  QuantityItem の並び(工事内容)
                                          │
                              estimating/mapping.py ─→ 見積の行
```

**入力も出力も `QuantityItem` にする**のが、この設計でいちばん効いている判断である。理由は3つ。

- `estimating/mapping.py` と `estimating/rules.py` を**1行も変えずに**差分が見積の行になる。
  規則は新しい属性 `工事区分` を条件に書くだけでよい(`rules.py` の `attributes` にそのまま乗る)。
- `QuantityItem` は既に `basis` / `premise_ids` / `hypothesis_premise_ids` /
  `site_survey_reason` / `derivation` を持っている(PR #29)。**差分の層が原則5の仕組みを作り直さずに済む。**
- 差分を作らなかった数量(対応する相手が無いもの)を、**そのまま素通しで下流へ流せる。**
  層を入れたせいで数量が消えることが無い。

### 1-3. この層がしないこと

- **確定を作らない。** `is_confirmed` は仲裁層の `action` と `confirmed_range` から来る値で、
  差分の層はそれを**運ぶだけ**である。差分は現況と計画という2つの読みを突き合わせるので、
  「独立した2つの根拠が揃った」ように見えるが、**同じ1つの PDF から読んだ2つのページは独立ではない**
  (`intake/start_kit.py` の「独立性についての但し書き」と同じ理由)。**差分から階層1へ上げてはいけない。**
- **足さない・引かない。** 4-3節。
- 単価も金額も持たない(`estimating/rules.py` の約束のまま)。

## 2. 現況と計画の図面の対応づけ

### 2-1. 対応は3段あり、いま実装があるのは1段目だけ

| 段 | 何の対応か | いまの実装 |
| --- | --- | --- |
| 1. 範囲の対応 | 現況のページ ⟷ 計画のページ | `intake/start_kit.py:285` の `PagePairing` |
| 2. 対象の対応 | 現況の数量 ⟷ 計画の数量 | **無い** |
| 3. 個体の対応 | 現況の建具1枚 ⟷ 計画の建具1枚 | **無い。当面つくらない**(2-4節) |

差分に要るのは2段目である。`PagePairing` はその手がかりにすぎない。

### 2-2. 対象の対応をどう作るか

照合の鍵は、原則2の「意味」の4欄のうちの2つである。

```
照合鍵 = (what: それは何か, where: どこのものか)
```

`phase`(現況か計画か)は**鍵ではなく、突き合わせる相手を分ける軸**である。
`purpose_link`(目的にどう関係するか)は照合に使わない(目的を受け取る場所がまだ無く、
入っても照合の鍵にすると目的の書き方で対応が変わってしまう)。

**いま `where` が取れない。** 室の輪郭を取る実装がリポジトリに無いので、
開き戸の対象名は `開き戸::ページN` どまりである([一覧](./principle_conformance_review.md) の A-2)。
そこで**当面は、`PagePairing` が結んだページの組を `where` の代役にする。**

```
where の代役 = PagePairing が結んだ範囲の識別子(pairing_id)
```

- 現況ページ1 と 計画ページ2 が `PagePairing` で結ばれていれば、
  `開き戸::ページ1`(現況) と `開き戸::ページ2`(計画) は**同じ `where`** とみなす。
- **これは粗い。** 1枚の平面図に台所と浴室が両方描かれていれば、その2つは区別されない。
  台所の建具を撤去して浴室に新設した場合、この粒度では「既存のまま」に見える。
  **この限界は差分の結果そのものに注記として残す**(4-4節)。室の輪郭が入ったら `where` を
  部屋に差し替え、代役をやめる。

### 2-3. 対応の状態は4つ。**「計画だけ」と「対応が無い」を絶対に混同しない**

| 状態 | 意味 | 差分 |
| --- | --- | --- |
| `matched` | 現況にも計画にも、同じ照合鍵の数量がある | 作る(3節の表) |
| `existing_only` | **対応する計画の範囲はあるのに**、計画側に同じ鍵の数量が無い | 撤去の候補 |
| `planned_only` | **対応する現況の範囲はあるのに**、現況側に同じ鍵の数量が無い | 新設の候補 |
| `unpaired` | **そもそも対応する範囲が無い**(現況図が無い、対応が申告されていない) | **作らない**(5節へ) |

**これがこの設計でいちばん壊れやすいところである。** `planned_only` と `unpaired` を
同じ「新設」にすると、**現況図が1枚も無い案件で、計画側の数量が全部「新設」になる。**
工事が無い部分まで新設として見積に載り、数量が実際の何倍にも膨らむ。
現況図が無いことは「現況に何も無い」ではない。

対応が無いものは差分を作らず、**5節の「現況が不明なとき」の扱いへ回す。**

### 2-4. 個体の対応(3段目)はつくらない

建具1枚ずつを現況と計画で結ぶ照合は、この設計では**やらない**。
そのために要る情報(1枚ごとの位置、建具番号の現況と計画の対応)が図面から取れていないので、
結んだとしても根拠が無い。**数で突き合わせるところまでにする。** その帰結が4-3節である。

### 2-5. 対応づけを誰が作るか

原則4「人が先に入力してよいのは基準点だけ」に照らすと、`PagePairing` は
**人が先に入力させてよいものではない**([一覧](./principle_conformance_review.md) の C-11)。
おーちゃんの回答で**混合方式(基準点だけ人が先、残りは AI が先)を既定**にすることが決まっているので、
対応づけは次の順で作る。

1. **AI が先に推論する。** 手がかりは、ページの表題(「現況平面図」「計画平面図」)、
   同じ縮尺・同じ用紙・同じ輪郭のページ、ページの並び順。
   **この推論の実装はまだ無い**(`content_kind` はベクター/ラスター/空の区別だけ)。
   実装するまでは、推論結果は常に「対応を作れなかった」になる。
2. **推論が割れたところだけを人に聞く(ゲート)。** 「このページの現況はどれですか」を候補から選ばせる。
3. **人が `PagePairing` で先に申告していれば、それを使う。ただし無条件の正解にしない。**
   原則5「人が与えた情報も、図面の中身と突き合わせて矛盾を探す」に従い、
   人の対応と AI の推論が食い違ったら**どちらも採らず、食い違いとして人に示す**
   (おーちゃんの回答17「どちらかを選ばず、食い違いとして人に示す」と同じ形)。

推論が無い間の振る舞いを決めておく: **人の申告があればそれを使い、無ければ `unpaired`。**
**黙ってページ順で対応させない。**

## 3. 届くために直す必要がある2か所

差分を作るには、いまの読み取りが**現況と計画を分けて出していない**2か所が直っていないといけない。
どちらも[一覧](./principle_conformance_review.md) に挙がっているもので、
**既存の判定のしかたを変える変更**なので、実装したら PR のまま待つ側に入る。

### 3-1. 建具表の数量が、現況と計画を1つのレンジに混ぜている(A-3)

`intake/drawing_intake.py:1321` の `_door_quantity_findings` は、同じ建具番号が
ページによって違う数量だったときレンジにする。コード中のコメント自身が
「既存と新設の建具表が両方ある」場合を想定している。**それは値の幅ではなく、意味の違いである。**

現況2件・計画5件が `(2.0, 5.0)` という1つのレンジになると、**差分の層からは現況も計画も見えない。**
この形のまま差分を作ることはできない。

**直し方(提案):** まとめる鍵を「建具番号」から「建具番号と `phase`」に変える。

```
いま:   建具数量::WD-01            → (2.0, 5.0)   ← 現況と計画が混ざっている
提案:   建具数量::WD-01 (phase=現況) → (2.0, 2.0)
        建具数量::WD-01 (phase=計画) → (5.0, 5.0)
```

`phase` はページの宣言(`PageDeclaration.phase`)から来る。**宣言が無いページは `不明` の別対象にする**
(`計画` に寄せない。`tests/test_intake_start_kit.py:425` の
`test_an_unknown_phase_does_not_invent_a_label` が守っている向きと同じ)。
同じ `phase` の中でページによって数量が違ったときは、**今までどおりレンジにする。**
そこは本当に値の幅だからである。

### 3-2. 規則も差分も `phase` を条件にできない(A-4)

`estimating/quantities.py:176` の `kind` は対象名の最初の `::` より前しか見ない。
`開き戸::現況::ページ1` の `現況` は鍵の側に入るので、規則からも差分の層からも見えない。

**直し方(提案):** `phase` を対象名の文字列から取り出すのをやめ、**属性にする。**

```
いま:   target="開き戸::現況::ページ1"   attributes={}
提案:   target="開き戸::ページ1"        attributes={"phase": "現況"}
```

- 規則は `attributes` の `phase` をそのまま条件にできる(`rules.py` の仕組みは変えない)。
- **規則ファイルの `format_version` を上げる。** 知らない項目を断る仕組みがそのまま効く。
- 差分の層は `attributes["phase"]` で現況と計画を分ける。文字列を切り出さない。
- **`不明` は属性に入れない。** 読めなかった属性を既定値で埋めない約束
  (`estimating/from_intake.py` の2番)と同じ向きである。属性が無いことが「不明」である。

### 3-3. 【2026-09-23 追記】意味の4欄が入ったので、3-2 節の直し方が変わる

この設計を書いた後、main に `axes/reading/meaning.py` が入った。
原則2の意味の4欄(`what` / `where` / `phase` / `purpose_link`)を持つ `Meaning` で、
**4欄すべて必須**(埋められない欄は空にせず `不明` / `目的未確立` と書く)。
`DrawingFinding.meaning`(`intake/drawing_intake.py:421`)に乗る。

**どこまで入っているかを読んで確かめた(main `f01c49f`):**

| 読み | `meaning` | 中身 |
| --- | --- | --- |
| 面積(埋め込み文字・OCR とも) | **付いている** | `_area_findings`。ページによって宣言が違えば `_merge_meanings` が `phase` を `不明` に落とす |
| 開き戸(`_door_arc_findings`) | **付いていない**(`meaning=None`) | `phase` はいまも対象名(`開き戸::現況::ページN`)と `provenance` の中だけ |
| 建具表の数量(`_door_quantity_findings`) | **付いていない** | 現況と計画を1つのレンジに混ぜたまま(3-1 節) |
| `QuantityItem`(`estimating/`) | **届いていない** | `estimating/from_intake.py` が `meaning` を写していない |

**この設計にとっての違いは2つ。**

1. **3-2 節の「属性を新しく作る」は、もう要らない。** `phase` を入れる箱は
   `Meaning.phase` として既にある。**直すことは「新しい欄を作る」ではなく、
   ①開き戸と建具表の読みにも `meaning` を付ける ②`from_intake.py` が
   `QuantityItem` まで運ぶ**、の2つに変わる。**判定を変える変更である**ことは変わらない
   (対象名から `phase` を外す時点で、仲裁層から見た対象の同一性が変わる)。
2. **2-2 節の「`where` が取れない」は、半分だけ解けた。** 欄はできたが、
   **室の輪郭を取る実装が無いことは変わっていない**ので、開き戸の `where` を
   部屋の名前で埋められるわけではない。`Meaning` は4欄必須なので、埋まらなければ
   `不明` が入る。**`where` が `不明` の2件を「同じ `where`」とみなしてはいけない**
   (みなすと、別の部屋の建具が「既存のまま」で相殺される)。
   したがって 2-2 節の代役(`PagePairing` の組)は**そのまま必要**で、
   `Meaning.where` が `不明` でない読みについてだけ、代役ではなく本物を使う。

**変わらないこと:** 0 節に挙げた4つの主張(差分の層の位置／引き算をしない／
現況が不明なときは不明のまま／`planned_only` と `unpaired` を混同しない)は、
今の main でもそのまま成り立つ。8 節の食い違い2件も、今の main で現物を読んで
まだ存在することを確かめた。

## 4. 差分の種類(撤去／新設／既存のまま／改修)

### 4-1. 決め方

同じ照合鍵 `(what, where)` について、現況側と計画側の数量を突き合わせる。

| 現況 | 計画 | 属性(種別・寸法など) | 数量 | 工事区分 |
| --- | --- | --- | --- | --- |
| ある | **無い** | — | — | **撤去** |
| **無い** | ある | — | — | **新設** |
| ある | ある | 同じ | 同じ | **既存のまま** |
| ある | ある | 違う | 同じ | **改修** |
| ある | ある | 同じ | **違う** | **区分未定**(4-3節) |
| ある | ある | **比べられない** | — | **区分未定**(4-2節) |
| 対応が無い | | | | **差分を作らない**(5節) |

区分の値は**日本語で持つ**(`estimating/basis.py` の4値と同じ約束。読み手に英語の語を使わせない)。

```
WORK_REMOVAL   = "撤去"
WORK_NEW       = "新設"
WORK_AS_IS     = "既存のまま"
WORK_ALTERED   = "改修"
WORK_UNDECIDED = "区分未定"
```

### 4-2. 「既存のまま」と「区分未定」を行として出す理由

- **「既存のまま」を出す。** 工事が無いことと、**見落としたこと**を区別できるようにするため。
  出さないと、集計表を見た人には「この建具は工事対象外」と「この建具は読み落とした」が同じに見える。
  数量は 0 ではなく現況のままの値にし、規則の側で「工事の行にしない」と書けるようにする
  (**どう扱うかは会社のルールであって、コードが決めることではない**)。
- **「区分未定」を出す。** 原則5「前提が揃うまで止めるのではなく、何に基づくかを区別して出す」。
  区分が決まらないことを理由に数量を落とさない。**ただし `区分未定` を勝手に「新設」に寄せない。**
  新設と改修は単価も工程も違うので、寄せた瞬間に金額が変わる。

「比べられない」は具体的には、属性が片側にしか無い(現況の建具表に種別が書かれていない)、
`estimating/from_intake.py` の2番でページ間の食い違いのため属性が付かなかった、といった場合である。
**属性が無いことを「同じ」とみなさない。** みなすと「既存のまま」が水増しされ、工事が消える。

### 4-3. 数が違うときに引き算をしない

現況3件・計画2件を、自動で「撤去1件」にしない。**起きたことは2通りある。**

- 1件だけ撤去して、残り2件はそのまま → 撤去1件
- 3件すべて撤去して、2件を新設 → 撤去3件・新設2件

**数の差では、このどちらかは決まらない。** 決めるには個体の対応(2-4節)が要るが、それは無い。
どちらを採るかで見積の行も金額も変わるので、**黙って片方を採ってはいけない。**

**提案する振る舞い:** どちらも捨てず、**排他の組**にして両方出す。
おーちゃんの回答16(面積の基準が未回答のとき、両方の値で「仮説に基づく」行を2本出す)と同じ形である。

```
排他の組 "diff-0007"
  ├ 撤去 1 件   仮説に基づく(仮説: 残った2件は同じ建具である)
  └ 撤去 3 件 + 新設 2 件   仮説に基づく(仮説: 建具はすべて入れ替わる)
```

**この形には危険が1つある。** 同じ組の行を足すと二重に計上される。
そこで `exclusive_group`(排他の組の識別子)を行に持たせ、**同じ組の行は絶対に合計しない**ことを
この層と下流の両方で固定する。`estimating/mapping.py` の `summary()` と
`basis_counts_text()` は行を数えるので、**排他の組を1件として数えるか、内訳として見せるかを
決めておく必要がある**(→ 判断待ち3)。

**排他の組を出す条件:** 数が違い、かつ属性が同じときだけ。
属性が違ううえに数も違うときは、組み合わせが増えすぎるので `区分未定` 1本にして人へ回す。

### 4-4. 解体図が描かれているとき

`PageDeclaration.phase` には `解体` がある。解体図は**撤去そのものが描かれた図面**なので、
差分から作った撤去と**二重に数える危険がある。**

**提案:** 解体図から読んだ数量は、差分の入力ではなく**突き合わせの相手**にする。

- 差分が出した撤去と、解体図の数量が**一致** → 撤去の行に「解体図とも一致」と根拠を足す。
  **ただし階層1に上げない**(1-3節。同じ PDF から読んだ2つのページは独立ではない)。
- **食い違う** → どちらも選ばず、食い違いとして人に示す(回答17と同じ形)。
- 解体図しか無い(現況も計画も無い) → 解体図の数量を**撤去として出す。**
  基づきは「推論に基づく」(読めてはいるが確かめていない)。

### 4-5. 「どこの限界か」を必ず行に残す

2-2節の `where` の代役は粗い。差分の結果には、その粒度で突き合わせたことを注記として残す。

```
notes = ("対応づけはページの組で行った。同じページの中の場所は区別していない",)
```

**注記が無いまま「既存のまま」と書かれた行は、読んだ人が信用してしまう。**

## 5. 現況が不明なときの仮説の置き方

### 5-1. 申告と噛み合わせる

別スレッドが、原則3-3の**現況の把握の申告**(明確に分かる／おおむね分かるが確実ではない／
全く分からない・図面で表現されていない／部分によって混在する)を受け取る場所を作っている。
**この設計を書いた時点(`f569871`)では、`intake/start_kit.py` にまだ入っていなかった。**
**【2026-09-23 追記】入った。** `intake/start_kit.ConditionSurvey`(全体の申告と
`ConditionRange` による範囲ごとの申告)で、`estimating/from_intake.py` が
`CasePremise` に直している。**下の3つの約束は、3つとも満たされている**
(未申告は `condition::unstated` として `source="hypothesis"` + `resolved_by` +
`alternatives` になる)。**噛み合わせのために足してもらうことは無い。**

**噛み合わせの約束(申告の側に求めるのはこの3つだけ):**

1. 申告は**4段階のどれか**と、**どの範囲についてか**を持つ。
2. **未申告は「全く分からない」として扱う。**(コーディネータの前提のとおり。安全側は
   「分からない」であって「明確」ではない。既定を「明確」にすると、申告を忘れただけで
   仮説が消え、根拠の無い値が確定側に寄る。)
3. 申告は `estimating/case_premises.py` の `CasePremise`(`kind="現況の把握の状態"`、
   `source="human"`、`scope` は範囲)として差分の層に届く。
   **差分の層は `intake/` を import しない**(`estimating/from_intake.py` と同じ約束)。

人が申告しなかった案件の振る舞い: **全件「全く分からない」で動く。**
差分は `matched` の組でだけ作られ、残りは5-3節の「現況の確認が必要」に回る。

### 5-2. 申告ごとの差分の作り方

| 申告 | 現況として何を使うか | 出す差分 | 基づき |
| --- | --- | --- | --- |
| 明確に分かる | 現況図の読みをそのまま | 4-1節の表のとおり | **推論に基づく** |
| おおむね分かるが確実ではない | 現況図の読みをそのまま | 同上。ただし **`既存のまま` には現地確認の理由を付ける** | 推論に基づく／現地確認が必要 |
| 全く分からない・図面で表現されていない | **使わない**(仮説を置く) | 5-3節 | **仮説に基づく** |
| 部分によって混在 | 範囲ごとに上の3つを当てる | 範囲ごと | 範囲ごと |
| 未申告 | 「全く分からない」と同じ | 5-3節 | 仮説に基づく |

**「明確に分かる」でも「確定」にはならない。** 人の申告は「自分がどれだけ把握しているか」であって、
図面の読みが正しいことの保証ではない。確定は仲裁層だけが作る(1-3節)。

**「おおむね分かる」で `既存のまま` にだけ現地確認を付ける理由:** この申告で
いちばん危ないのは、現況にあったものが図面に描かれていない場合である。
そのとき差分は `planned_only`(新設)か `既存のまま` になるが、
**実際には撤去が要る**ことがある。撤去は現況を知らないと作れないので、
「そのままでよい」と言い切った行にだけ確認を求める。
回答8のとおり**根拠を付けて提案する**形にし、根拠の無い「現地確認が必要」は作らない
(`QuantityItem.site_survey_reason` が空ならその基づきにならない仕組みが既にある)。

### 5-3. 現況が不明なときに置く既定の仮説

**3案を比べた。**

| 案 | 置く仮説 | 何が起きるか |
| --- | --- | --- |
| 1 | 現況には何も無い(＝計画側は全部新設) | 数量が最大に膨らむ。**撤去が1件も出ない。** 解体費を落とす |
| 2 | 現況は計画と同じ(＝全部既存のまま) | **工事が消える。** 見積がほぼ空になる |
| 3 | **現況は不明のまま。計画側だけを `区分未定` で出し、撤去は作らない** | 数量は出るが、区分が決まらない行が並ぶ |

**推奨は案3。** 理由は3つ。

- 計画側の図面は読めている。**現況が不明なときに確実に言えるのは「工事の後にこれがある」だけ**で、
  それが新しく付いたのか元からあったのかは、現況を知らないと言えない。
  案1と案2は、その言えないことを言い切っている。
- 案1も案2も**間違いが静かに通る。** `新設`(案1)も `既存のまま`(案2)も、それだけ見れば
  もっともらしい行になり、人が気づく手がかりが残らない。`区分未定` は**見れば分かる。**
- **撤去を作らない**のがこの案の要である。撤去は現況からしか作れない。
  現況が無いのに撤去を作れば、それは根拠の無い数字である。
  代わりに**「現況の確認が必要」として挙げる**(下)。

**案3の具体:**

```
計画側の数量 1 件につき、工事内容を 1 件作る
  work_kind = "区分未定"
  alternatives = ("新設", "改修")      ← 現況が分かれば、このどちらかに決まる
  basis = "仮説に基づく"
  hypothesis_premise_ids = ("premise-genkyo-fumei-<範囲>",)
  notes = ("現況が不明なため、新設か改修かを決めていない",)

あわせて、その範囲について 1 件だけ「現況の確認が必要」を出す
  work_kind = "区分未定"
  site_survey_reason = "この範囲の現況が分からないため、撤去があるかどうかを決められない"
  basis = "現地確認が必要"     ← 4値の中でいちばん弱い
```

**撤去の行は作らず、「撤去があるかどうか分からない」ことを1件の確認として出す。**
数量を作らずに、人が答えるべきことだけを残す形で、
抜き取り監査の設計で決まった「出すのは的中率ではなく、人が確かめるべき対象の一覧」と同じ向きである。

### 5-4. 仮説を置いてよい条件(3つすべて)

1. **仮説には「何が分かれば要らなくなるか」を必ず書く。**
   `CasePremise.resolved_by` に既にある欄で、これが無いと原則5の
   「仮説が変わったら連動して見直す」が動かせない。
   例: 「現況平面図が手に入れば要らなくなる」「現地で建具の有無を見れば要らなくなる」。
2. **仮説は現況についてだけ置く。計画について仮説を置かない。**
   計画は人がやりたいことなので、AI が代わりに決めてはいけない。
   原則3-2「人に詳細を設定させると自動積算の意味を失う」の**裏返し**で、
   人が決めるべきことを AI が埋めてはいけない、という同じ話である。
   計画が読めないときは、仮説ではなく**ゲート(人への質問)**にする。
3. **答えが変わる仮説は、必ず `alternatives` に反対側を書き、行を排他の組にする。**
   どちらに転んでも同じ答えになる仮説だけは、組にせず1本で出してよい。

### 5-5. 仮説が変わったとき

`estimating/mapping.py` の `lines_depending_on(premise_id)` が既にある(PR #29)。
差分の層は `hypothesis_premise_ids` を工事内容に付けて下流へ運ぶだけでよく、
**新しい仕組みは要らない。**

ただし1つ足りない。**差分そのものが前提に依存している**場合
(「ページ1とページ3が対応する」という仮説)、その前提を差し替えると
**差分の組み合わせ自体が変わる。** 行を作り直すだけでは足りず、突き合わせからやり直す。
回答10の「依存している行だけを作り直す」に対し、**対応づけの前提だけは全体を作り直す**
必要がある。→ 判断待ち4。

## 6. データの形(提案)

`estimating/scope_diff.py`(新規)。**`intake/` は import しない。**

```
WorkScopeItem                      工事内容 1 件
  work_kind            撤去 / 新設 / 既存のまま / 改修 / 区分未定
  what                 それは何か(照合鍵の1つ。`QuantityItem.kind` から)
  where                どこのものか。`Meaning.where` が `不明` でなければそれを使い、
                       `不明` なら pairing_id で代用する(3-3 節)。**`不明` どうしを
                       同じ `where` とみなさない。** 室が取れたら代用をやめる
  existing_quantity    元になった現況の QuantityItem(無ければ None)
  planned_quantity     元になった計画の QuantityItem(無ければ None)
  value_range / unit   工事の数量。**引き算では作らない**(4-3節)
  alternatives         ほかにありえた区分(("新設", "改修") など)
  exclusive_group      排他の組の識別子。**同じ組の行は合計しない**
  site_survey_reason   現地確認が要る理由。**根拠が無ければ空**
  premise_ids / hypothesis_premise_ids
  notes                限界の注記(4-5節)

ScopePairing                       範囲の対応 1 件
  pairing_id
  existing_pages / planned_pages
  source               human(人の申告) / inferred(AI の推論)
  conflict             人と AI が食い違ったか(食い違ったらどちらも採らない)

ScopeDiffResult
  items                WorkScopeItem の並び
  unpaired             対応が作れなかった数量(素通しで下流へ)
  premises             この層が置いた仮説(CasePremise)
  summary()            人が読む要約。報告にそのまま貼れる形
```

`QuantityItem` への戻し方(下流を変えないため):

```
target      = f"工事内容::{what}::{where}"
attributes  = {"工事区分": work_kind, "phase": …}   ← 規則がそのまま条件にできる
basis       … 元になった現況・計画の数量の基づきのうち、いちばん弱いもの
              (estimating/basis.py の weakest。**弱いほうが勝つ**)
derivation  … 元の数量から運ぶ。ここで作り直さない
```

**基づきは必ず `weakest()` を通す。** 現況が「仮説に基づく」なら、
そこから作った工事内容も「仮説に基づく」より強くならない。

## 8. 原則と既存のテストの食い違い(2件・書き換えていない)

コーディネータの指示どおり、**テストは1行も書き換えず、食い違いとして報告する。**

### 8-1. `tests/test_drawing_intake_schedules.py:279`

```python
# 2 + 5 = 7 にしない。どちらかを選びもしない。
assert finding.value_range == (2.0, 5.0)
```

このテストは、**現況2件と計画5件が1つのレンジに混ざった状態を正しい振る舞いとして固定している。**
足さないこと・片方を選ばないことは原則どおりで、そこは守るべきである。
食い違うのは**レンジにして1件の数量として出す**ところで、
原則2「意味が付けられない値は、数量に使わない」に反する。
3-1節を実装すると、この `assert` は成り立たなくなる。

**どう直すかの提案:** テストの意図(足さない・選ばない)は残し、
突き合わせる対象を `建具数量::WD-01 (phase=現況)` と `(phase=計画)` の2件に分ける。
**ページの宣言が無いテストでは、2件とも `phase` が付かないので、いまと同じ `(2.0, 5.0)` のままになる。**
つまり**このテストは、ページの宣言を足さなければ落ちない。** 落ちるかどうかは実装のしかた次第なので、
実装に入る前に上記の是非をおーちゃんに確認する。

### 8-2. `tests/test_intake_start_kit.py:420`

```python
assert "開き戸::現況::ページ1" in [item.target for item in result.findings]
```

3-2節(`phase` を対象名から属性へ移す)を実装すると、対象名が `開き戸::ページ1` に変わるので
このテストは落ちる。**対象名が変わることは、仲裁層から見た対象の同一性が変わることでもある**
(同じ対象名の読みが1つの判定にまとめられるため)。
**これは明確に「既存の判定のしかたを変える変更」なので、実装したら PR のまま待つ。**

**どう直すかの提案:** 同じテストの意図(人が宣言した現況/計画が下流に残ること)を、
対象名ではなく属性で確かめる形に書き換える。**意図は変えない。**

## 11. 判断待ち(おーちゃんに決めてほしい)

1. **数が違うとき、排他の組で2本出すか、`区分未定` 1本にするか。**(4-3節)
   2本出すのは回答16(面積は両方出す)と同じ向きだが、**面積は値が2つなのに対し、
   こちらは行の構成そのものが変わる**(撤去1件 ⟷ 撤去3件+新設2件)ので、組が大きくなる。
   **推奨: 排他の組で2本出す。** 理由は、`区分未定` 1本にすると「撤去が3件あるかもしれない」
   という情報が消え、人が見積を組むときに手がかりが無くなるため。

2. **`既存のまま` を見積の行として出すか、数量の一覧にだけ残すか。**(4-2節)
   **推奨: 工事内容としては出し、見積の行にするかは規則ファイル側で決める。**
   会社によって「現況のまま＝記載しない」と「現況のまま＝確認済みとして記載する」が分かれるため、
   コードで決めない。

3. **排他の組を、集計でどう数えるか。**(4-3節)
   `estimating/mapping.py` の `summary()` と `basis_counts_text()` は行を数えるので、
   排他の組が入ると数が実際より多く見える。
   **推奨: 組を1件として数え、内訳は組の中に畳む。** 「100件のうち確定0件」という要約の
   分母が、排他の組のせいで膨らむのを避けるため。

4. **対応づけの前提が変わったときに、どこまで作り直すか。**(5-5節)
   回答10は「依存している行だけを作り直す」だが、**対応づけの前提が変わると
   差分の組み合わせ自体が変わる**ので、行だけでは足りない。
   **推奨: 対応づけの前提だけは、差分の突き合わせから全部やり直す。**
   キュー3見直しの判断待ち3(「全部作り直し、変わった行だけを見せる」)と同じ理由で、
   作り直しは安く、取りこぼしは高い。

5. **解体図しか無いときの撤去を、そのまま出してよいか。**(4-4節)
   **推奨: 出す。** 解体図は撤去が直接描かれた図面なので、現況からの差分より根拠が近い。
   基づきは「推論に基づく」にし、確定には上げない。

6. **現況の把握の申告が「部分によって混在」のとき、範囲をどの粒度で受け取るか。**(5-2節)
   ページ単位か、ページの中の区画か。区画にすると人の操作回数が増え、
   原則5末尾「人の負担は操作の回数と時間で測る」と直接ぶつかる。
   **推奨: 既定はページ単位。区画は、差分が食い違ったところだけ後から足せる形にする**
   (基準点の区画についての回答「区画は食い違ったときだけ細かく」と同じ向き)。
