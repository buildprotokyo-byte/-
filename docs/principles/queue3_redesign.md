# キュー3(数量化と見積の行への対応付け)の設計見直し

[開発全体の最上位の原則](./start_kit.md) に合わせた見直し。**この文書は設計だけで、コードは1行も直していない。**
おーちゃんが [原則に反している所の一覧](./principle_conformance_review.md) を確認してから直す。

土台にしたコミット: `a60c831`(main)。いまの実装は `estimating/`(PR #21 `9a9d05f`)、
報告は `docs/estimate_line_mapping_report.md`、設計は `docs/design_v8.md` 16章。

## 1. 3層のうち、いま1層が無い

おーちゃんの言う3層を、いまのコードに当てはめると次のようになる。

| 層 | いまの置き場所 | 状態 |
| --- | --- | --- |
| 読み取った数量 | `estimating/quantities.py` の `QuantityItem` | ある |
| 会社のルール | `estimating/rules.py` の `RuleSet`(差し替えられる外部 JSON) | ある |
| **案件の前提** | **無い** | 人の前提は `intake/start_kit.py` にあり、`intake/` の中で使い切られている |

案件の前提が層として無いことの実害は2つある。

- 面積の選択は `intake/drawing_intake.py:978` で消費され、`施工対象床面積` という**値になった後**でしか
  `estimating/` に届かない。見積の行から「この数量は、人がどの前提を選んだからこの値なのか」を遡れない。
- ページの種類の宣言は `intake/drawing_intake.py:605` で抽出の範囲を決めて消える。
  **その宣言が行に効いたことが、行の側に何も残らない。**

原則5の「どの仮説に依存しているかを記録し、仮説が変わったら連動して見直す」は、
前提が値に溶けてしまう限り書きようがない。**だから前提を第3の層として独立させる。**

## 2. 案件の前提の層(新規の提案 `estimating/case_premises.py`)

前提は**値ではなく前提そのもの**を持ち、数量は識別子で参照する。

```
CasePremise
  premise_id     … 参照用の識別子
  kind           … 面積の基準 / 現況の把握の状態 / 方向性 / ページの種類 /
                   基準点 / 現況と計画の対応 / そのほか
  statement      … 前提の中身(人が読める文)
  source         … human(人が入れた) / inferred(AI が図面から推論した) /
                   hypothesis(AI が置いた仮説)
  scope          … どこに効くか(ページ、範囲、対象の種類)
  alternatives   … 仮説のとき、ほかにありえた選択肢
  entered_by     … 人が入れたものだけ
```

- **仮説も前提の一種**にする(`source="hypothesis"`)。原則3-3の
  「分からない部分は、AI が図面から推論するか、仮説を置いて進む」がここに乗る。
- **`source` は前提の出どころであって、正しさの度合いではない。** 人が入れた前提も
  図面と突き合わせる対象である(原則5)。突き合わせの結果は前提ではなく、別に記録する。

## 3. 各値の「何に基づくか」(4値)

`Basis` を新しく置き、`QuantityItem` と `MappedLine`(見積の行)の両方に持たせる。

| 値 | 意味 | 誰が付けられるか |
| --- | --- | --- |
| 確定 | 仲裁層が自動確定した(階層1) | **仲裁層だけ。** この層は絶対に格上げしない |
| 推論に基づく | 読んだ値から計算した、または一般則で補った | この層 |
| 仮説に基づく | `source="hypothesis"` の前提に依存している | この層 |
| 現地確認が必要 | 図面からは決められない | **規則ファイル側に書く(下の判断待ち1)** |

ラベルは**日本語で入れる**。`axes/reading/protocol.py:75` が既に
「一般則で補った → `assumed`」の形で日本語を受けており、読み手に英語の語を答えさせない約束になっている。

**決め方(既存の判定は変えない)**

1. いまの `QuantityItem.is_confirmed`(仲裁層の `auto_confirm` かつ `confirmed_range` あり)が真 → **確定**。
   ここは今の判定をそのまま使う。**2026-09-22 時点では常に偽**なので、確定は出ない。
2. 偽のとき、依存している前提で決まる。
   - 仮説の前提に1つでも依存していれば → **仮説に基づく**
   - そうでなく、由来(`derivation`)が `derived` か `assumed` なら → **推論に基づく**
   - 図面に書かれていないために値が作れないもの → **現地確認が必要**
3. **弱いほうが勝つ。** `axes/reading/protocol.py:253` の
   「`derived` の根拠に `assumed` が1つでもあれば `assumed` に落ちる」と同じ向きにそろえる。
   1つの行が複数の数量から作られたら、行の基づきは**その中でいちばん弱いもの**になる。

**あわせて直す写し忘れ:** `estimating/from_intake.py:92-106` が `derivation` を
`QuantityItem` に写していない。いまは仮説から来た数量と読んだ数量が行の上で見分けられない。
**これは判定を変えない修正**(運ぶだけ)なので、3の実装より先に入れられる。

## 4. 依存の記録と、前提が変わったときの見直し

- `QuantityItem.premise_ids` / `MappedLine.premise_ids` … その値がどの前提に依存しているか
- `MappingResult.affected_by(premise_id)` … その前提を変えたときに見直す行を返す

前提を差し替えたときは当てはめを作り直すが、**依存を持つ理由は速さではなく、
「どの行が、どの前提のせいで変わったか」を人に見せるため**である。

## 5. 現況と計画の差分(原則1)を、行の側から表現できるようにする

いま `開き戸::現況::ページ1` の `現況` は対象名の文字列の中にあり、
`estimating/quantities.py:110` の `kind` は最初の `::` より前しか見ないので、規則からは見えない。

- 数量に `phase`(現況/計画/解体/不明)を**属性として**持たせ、文字列から取り出すのをやめる。
- 規則が `phase` を条件にできるようにする(`rules.py` の `attributes` にそのまま乗る)。
  **規則ファイルの `format_version` を上げる**(知らない項目を断る仕組みがそのまま効く)。
- 差分(撤去・新設)そのものを作るのは**この層ではない。** 現況の数量と計画の数量を突き合わせる層が
  1つ手前に要る。この層は、**差分の結果を数量として受け取れる形にしておく**だけにする。

## 6. 意味を値に付ける(原則2)

いま対象名の文字列に埋まっている意味を、独立した欄にする。

```
what         … それは何か
where        … どこのものか
phase        … 現況か計画か
purpose_link … 目的にどう関係するか
```

原則2の2行目は「意味が付けられない値は、数量に使わない」なので、
**4つのうち1つでも付けられない値は数量として出さず、「意味未確定」として別に置く**のが原則どおりである。

ただし、これをいま入れると `建具数量::AW-1`(`where` が無い)も `専有延床面積`(`phase` が無い)も
出せなくなり、**この経路から出る数量が0件になる。** `purpose_link` に至っては、
目的(原則3-2)を受け取る場所がまだ無いので誰も埋められない。
**どこまで厳格にするかは、目的が入ってからでないと決められない** → 下の判断待ち2。

## 7. 変えないこと

- **確定の3条件**(規則がちょうど1つ当たった／数量そのものが仲裁層で確定している／その行に他の数量がぶつかっていない)
- 規則をコードに埋め込まず外部ファイルに置くこと、知らない項目と知らない版を断ること
- 次元の違う単位へ換算しないこと
- ページをまたいで足さず、同じ行に複数の数量が当たったら人へ回すこと
- 単価と金額を持たないこと

## 8. 入れる順番の提案(それぞれ独立に入れられる)

1. `derivation` を `from_intake.py` で運ぶ(**写し忘れの修正。判定は変わらない**)
2. `Basis` の4値と、いまの2値からの写像(**判定は変えない**。`is_confirmed` が真なら確定、偽なら依存で決まる)
3. 案件の前提の層(`CasePremise` と `premise_ids`)
4. `phase` を属性にする(規則ファイルの版を上げる)
5. 前提が未決のときに「仮説に基づく」行を出す(**判断待ち1**〈一覧の側〉が決まってから)
6. 意味の4欄(**目的(3-2)が入ってから**)

1と2は既存の判定を変えないので、原則の確認が終わり次第すぐ入れられる。3以降は判断待ちを含む。

## 9. この設計についての判断待ち

1. **「現地確認が必要」を誰が付けるか。**
   図面に書かれていないことを AI が「現地確認が必要」と判断するのは、「図面に無い＝存在しない」と
   同じ誤りを踏みやすい。
   **推奨: 規則ファイル側に「この行は現地確認が要る」と書けるようにし、AI には付けさせない。**

2. **意味の4欄(6節)を必須にする時期。**
   いま必須にすると、この経路から出る数量が0件になる。
   **推奨: 目的(原則3-2)を受け取る場所ができてから必須にする。それまでは欄だけ用意し、
   埋まっていないことを行に残す。**

3. **前提を差し替えたときに作り直す範囲。**
   依存する行だけか、全部作り直して変わった行だけを見せるか。
   **推奨: 全部作り直し、変わった行だけを人に見せる。作り直しは安く、取りこぼしは高い。**
