## 1. 「順番ではなく対」を、どう形にするか

### 1-1. いまの形は、順番になっている

読み取りの部品は、すべて `pdf_path` と `page_index` だけを受け取る
(`extract_scale` / `find_door_arcs` / `find_area_labels` / `find_tables` /
`read_door_schedules` / `read_finish_schedules` / `recognize_page`)。
**目的を受け取る引数が1つも無い。**

ここに「目的」を引数として足すだけだと、**目的は前段になる。**
前段になった時点で「目的が揃うまで読まない」に戻り、原則の言う対ではなくなる。

### 1-2. 目的を、入口と出口の両方に置く

**この設計の柱は1つだけである。**

> **読み取りの部品は、「いまの目的の理解」を受け取り、
> 値と一緒に「目的の理解がどう変わったか」を返す。**

目的が入口と出口の両方にあるので、**前にも後にも置けない。** これが対である。

```
      ┌──────────────── 目的の理解(PurposeState) ────────────────┐
      │                                                          │
      ↓                                                          │
  読み取りの部品(線・面積・部屋・表・寸法) ── 値 + 付けるもの ──→ 更新
      │                                                          │
      └──────────────────────────────────────────────────────────┘
```

### 1-3. 対が「前提条件」に化けないための3つの決まり

**この3つを外すと、設計は順番に戻る。**

1. **目的が無くても動く。** `PurposeState` が空でも部品は動く。
   そのとき、関係する項目と工事区分が「不明」になるだけである。
   → 回帰テストで固定する: **空の `PurposeState` を渡したときの値が、
   いま目的を渡さずに読んだ値と1つも変わらないこと。**
2. **往復は回数で切らず、目的の理解が変わらなくなったら止める。**
   各回、何がどう変わったかを記録する。安全のための上限回数は置くが、
   **上限に当たったことは「止まった」ではなく「収束していない」として残す。**
3. **区分不明を捨てない。** 根拠が無いものは確認事項か仮説として残す。
   **次の回で目的が深まったときに決まるのは、まさにここに溜まったものである。**
   捨てると往復する意味が無くなる。

## 2. 読み取りの部品が返すもの

```
ReadingUnit                     … 読み取った値1つ
  value / unit / provenance     … いまの DrawingFinding と同じ
  meaning                       … いまの Meaning(what / where / phase / purpose_link)
  purpose_links                 … 関係する目的の項目(0件以上。**0件でも捨てない**)
  work_category                 … 既存のまま / 撤去 / 新設 / 改修 / 区分不明
  work_category_basis           … その区分を決めた根拠(下の表)。**区分不明なら空**
  off_menu                      … どの目的の項目にも関係しないとき True
```

### 2-1. 区分を決めてよい根拠

| 根拠 | 部品が自分で持てるか | 備考 |
| --- | --- | --- |
| 要約資料の記述 | **持てる**(目的の項目として渡ってくる) | メニューの項目に結び付いたとき |
| 図面の凡例や線の種類 | **持てる**(そのページの情報) | **いま読む実装が無い**(7節) |
| 現況図と計画図の比較 | **持てない** | ページをまたぐので、差分の層の仕事(PR #33) |
| 人が宣言した現況/計画/解体 | 持てる | **弱い手がかり**。それだけで区分を決めない |

**部品は、自分の手元に根拠があるときだけ区分を付ける。無ければ「区分不明」にする。**
ページをまたぐ比較で決まる区分は、PR #33 の差分の層が後で決める。**同じ区分を2箇所で決めさせない。**

### 2-2. 言葉が3通りある(要判断)

| どこ | 値 |
| --- | --- |
| おーちゃんの今回の指示 | 既存のまま / 撤去 / 新設 / 改修 / **区分不明** |
| PR #33 の設計 | 既存のまま / 撤去 / 新設 / 改修 / **区分未定** |
| いまのコード(`axes/reading/meaning.py` の `phase`) | **現況 / 計画 / 解体 / 不明** |

**上の2つは最後の1語だけ違う。3つ目は別物である。**
`現況`/`計画` は**その図面が何を描いているか**で、`撤去`/`新設` は**工事で何をするか**である。
`解体` と `撤去` も、図面の種類と工事の区分で意味が違う。
→ 判断待ち1。

## 3. 目的の理解(PurposeState)

```
PurposeState
  items         … 目的の項目の並び(メニューの項目、または AI が推定したもの)
  round         … 何回目の往復か
  changed       … 前の回から何が変わったか(項目の追加・分割・確からしさの変化)
```

**空でもよい。** 空のときは、すべての `purpose_links` が0件、`work_category` が「区分不明」になる。

部品が返す更新は**提案であって確定ではない**(第2層「軸から出てくるのは確かめるべき問い」)。
更新を取り込むのは往復を回す側で、**部品が自分で目的を書き換えない。**

## 4. 「要確認」と「キラークエスチョン」を分ける

**2つは別の出口にする。同じ並びに混ぜない。**

| | 要確認 | キラークエスチョン |
| --- | --- | --- |
| 何から出るか | **読めているもの同士**の突き合わせ | **まだ候補が出ていないもの** |
| 何が問題か | 辻褄が合わない | 分かっていない |
| 付けるもの | 答えられる相手(社内/会社の判断/現地確認/質疑) | 下の4つ(6節) |
| 並べ方 | ― | **下流への効き目の大きい順** |

いまのコードでは、この2つが**別々の場所にあるが、どちらも不十分である。**
要確認に当たるのは `PendingDecision`(答えられる相手を持たない)、
キラークエスチョンは `killer_question/engine.py`(下の6節)。

## 5. 要素ごとの推論の3段階と、波及

原則は [start_kit.md](./start_kit.md) の「要素ごとの推論は3段階で行う」
「波及の推論で作り話をしない決まり」。**この節はその実装の設計だけで、コードは書いていない。**

### 5-1. 3段階を、どこに置くか

| 段階 | どこで働くか | この設計との関係 |
| --- | --- | --- |
| 第1段階 区分 | **読み取りの部品の中**(2節の `work_category`) | 部品が自分の手元に根拠を持つときだけ付ける。ページをまたぐ比較で決まる区分は差分の層(PR #33) |
| 第2段階 目的との照合 | **往復を回す側**(1-2節の図の「更新」の所) | 部品が返した区分を目的の項目と突き合わせる。食い違いは**要確認**へ(4節) |
| 第3段階 波及 | **新しい層。読み取りと差分の後段** | 区分が撤去・新設・改修の要素から始める |

**3段階は、別々の3つの仕組みではなく、1つの要素が通る道である。**
ただし**区分の中身は PR #33 の差分の層が持つ**ので、この設計は
**第1段階の「部品が何を付けて返すか」と、第3段階の波及の形**だけを決める。
同じ区分を2箇所で決めさせない(2-1節と同じ理由)。

### 5-2. 第2段階で、目的が候補を絞り込む所と、絞り込まない所

原則の例(「照明器具は全て交換」なら図面上の照明器具は撤去か新設のどちらか)は、
**候補集合を5つから2つに減らすだけで、どちらであるかは決めない。**

- 目的が減らしてよいのは**候補の並び**であって、値ではない
- 減らした結果が1つになったときも、**それだけで確定させない**
  (第1層3行目「単一の根拠では自動確定しない」。目的の記述は1本の根拠である)
- 部品が返した区分が、目的が残した候補のどれにも入らないとき → **要確認**
  (「分かっていない」のではなく「読めているのに噛み合っていない」ため)

### 5-3. 波及ルールの持ち方(差し替えられる設定)

**`estimating/rules.py` と同じ形にする。** コードに埋め込まず、外部ファイルとして読み、
書式の版が違えば読まない。**リポジトリに置くのは架空の見本だけ**にする。

```
PropagationRule                 … 波及ルール1本
  rule_id                       … 記録に残す名前
  when_element                  … どの要素か(壁 / 建具 / 照明器具 / 設備 / 仕上げ …)
  when_change                   … どの変更か(撤去 / 新設 / 改修)
  pulls_in                      … 巻き込まれるものの並び(種類と、場所の決め方)
  confidence                    … このルール自体の確かさ
  source                        … 出どころ(施工要領 / 標準仕様 / 見積漏れの事例)。**今は空**
```

```
PropagationFinding              … 波及で出てきたもの1つ
  from_element / from_change    … どの要素の、どの変更から
  by_rule                       … どの波及ルールで(rule_id)
  depth                         … 何段目か(1〜3)
  target                        … 巻き込まれたもの
  status                        … 観測で裏が取れた / 要確認 / 見積条件付き
  derivation                    … **常に assumed。階層1に上がらない**
```

**いま決めるのは形だけで、中身は入れない。** 施工要領・標準仕様・見積漏れの事例の
調査結果が届いてから入れる。**テストは架空のルールで書く。**
本物らしいルールをテストに書くと、後で本物が入ったときにテストを全部書き直すことになり、
しかも**測っているのが「仕組み」なのか「ルールの中身」なのかが分からなくなる。**

`source` は今は空にする。**空の `source` を「根拠あり」として扱わない**ことを、
読み込みの時点で検査する(`estimating/rules.py` が未知の項目を断るのと同じ)。

### 5-4. 止め方(**ここに現物の問題がある**)

原則は止める所を3つ挙げている。**そのうち1つが、いまのコードでは判定できない。**

| 止める条件 | いま判定できるか |
| --- | --- |
| 深さ3段階まで | **できる**(`depth` を数えるだけ) |
| 工事範囲の外に出た | **できる**(目的の項目と、ページ・部屋の範囲で見る) |
| 金額への影響が無くなった | **できない** |

**金額が判定できない理由**: `estimating/` は単価も金額も持たない
(`estimating/rules.py:83` に「**単価・金額はここにも下流にも無い**」と明記されている)。
単価を受け取る口は `killer_question/engine.py:194` の `unit_prices` だけで、
**そこに値を入れているのは `benchmarks/run_killer_question_eval.py:262` の1箇所、
つまり計測用のベンチマークだけである。本番の経路からは1件も渡っていない。**

→ **当面は、深さと工事範囲の2つだけで止める。** 金額で止める条件は**形だけ用意して、
常に「止めない」を返す**ようにし、単価が入る口ができたときに繋ぐ。
**「金額で止めている」ことにしない**(止まっていないものを止まったことにするのがいちばん危ない)。

### 5-5. 深さと確かさ

- `depth` はそのまま記録に残す。**深さで確かさの数値を掛け算しない。**
  掛け算の係数を決める実測がどこにも無く、**根拠の無い数字が根拠のある数字と
  同じ顔をして流れる**ため。
- 深さに関わらず、**波及だけから出た数量は階層1に上がらない**(`derivation` が `assumed`)。
  いまの `is_hard_eligible` がそのまま効くので、新しい判定は足さない。
- 深さの違いは**並べる順番**にだけ使う(浅いものから人に見せる)。
→ 判断待ち5。

### 5-6. 3つの出口を混ぜない

| 出口 | 何から出るか | 例 |
| --- | --- | --- |
| **波及** | **変える所**から。ルールに基づく | 壁を撤去する → その中の配線 |
| **要確認** | **読めているもの同士**が噛み合わない | 図面は既存のままに見えるが、要約資料は撤去と書いている |
| **キラークエスチョン** | **まだ候補が出ていない** | そもそも配線が図面のどこにも無い |

**同じ並びに入れない。** 混ぜると、人が見たときに
「ルールが言っているだけのもの」と「図面が食い違っているもの」の区別が付かなくなる。

**波及は、質問の入口をもう1つ作る。** 6-4節のとおり、いまのキラークエスチョンは
**変数として登録され、候補値が列挙できた要素だけ**を質問にするので、
まだ読み取られていないものには届かない。届く入口は2つになる。

1. **要約資料のメニュー**(PR #44) … 「あるはずと書かれているのに、まだ候補が無い」
2. **波及**(この節) … 「変更から巻き込まれるはずなのに、まだ候補が無い」

波及から出た問いのうち、**答えが分かると下流が大きく確定するもの**を
キラークエスチョンの候補に加える。**「大きく」の判定は 6-3 節の内訳を使う**
(候補値ごとに下流がどれだけ狭まるかは、いま計算して捨てている)。

### 5-7. 既存を壊さないこと

1. **波及ルールが空なら、波及は1件も出ない。** 設定を渡さなければ、いまと1行も変わらない。
2. **波及は読み取りの値を書き換えない。** 別の並びとして足すだけで、
   観測から出た数量には触らない。
3. **裏が取れた波及も、観測に昇格させない。** 図面に描かれていたものは
   **その観測そのものを拾う**のであって、波及の側を「確からしくする」のではない。
   (波及は「探す場所の当たり」であって、値の根拠ではない)

## 6. キラークエスチョンを強くする設計

### 6-1. いま出しているもの

`Question` が持つのは `variable` / `score` / `candidate_values`(整数の並び) /
`tie_broken_by_axis` / `mode` / `selected_by` だけである。

### 6-2. おーちゃんの4項目に対して、何が足りないか

| 付けること | いまの状態 |
| --- | --- |
| 何が分かっていないか | **無い。** あるのは変数名だけで、人が読める言葉になっていない |
| 分かると確定する下流の行と金額 | **下流の要素名はある**(`CandidateScore.downstream`)。**金額は無い**(`estimating/` が単価を持たないため、`impact` は単価を渡したときだけ効く) |
| 人が答えやすい選択肢 | **整数の並びしか無い。** 人が選べる言葉になっていない |
| 選択肢ごとに下流がどう変わるか | **計算しているのに捨てている**(下) |

### 6-3. いちばん効く一手: 捨てている計算を捨てない

`score_candidate()`(`killer_question/engine.py:296`)は、**候補値1つずつについて
下流がどれだけ狭まるかを実際に解いて求めている**(`reductions` の並び)。
ところが最後に `sum(reductions) / len(reductions)` と**平均して捨てている。**

**「選択肢ごとに下流がどう変わるか」は、解き直さずに出せる。** 捨てるのをやめるだけでよい。
どの下流要素がどれだけ狭まったかも、同じループの中にある。

**これは質問の選び方を変えない。** 平均は今までどおり計算し、
**別の欄として内訳を残すだけ**なので、選ばれる質問の順番は1つも変わらない。
→ 回帰テストで固定する。

### 6-4. 候補が出ていない項目には質問が効かない

おーちゃんのご指摘は、コードでもそのとおりだった。
`_unresolved_names()` が返すのは**変数として登録された要素だけ**で、
`is_askable` は**候補値が列挙できた要素だけ**を質問にする。
**まだ読み取られていないものは、質問の候補にすら入らない。**

→ **要約資料のメニュー(PR #44)が、ここに入る。** メニューの項目は
「あるはずなのにまだ候補が無いもの」なので、**読み取りが候補を出す前に
質問の候補になれる唯一の入口**である。両方の設計を通して初めて、
キラークエスチョンが「まだ分かっていないこと」に届く。

  `phase`(人が宣言した現況/計画/解体)を受け取る。**本番の経路からも渡っている**
  (`intake/drawing_intake.py:1031`)。**ただし渡るのは印だけで、目的の中身は渡らない。**
  → **この形は、この設計の半歩手前である。** 「受け皿が無い」と「結び付けが無い」を
  分けて印を置く所まで来ていて、**足りないのは目的の中身と、返す側の更新だけ**になった。
- **意味を返す部品は `ocr_readings` の2つと寸法の読み取り**で、`purpose_link` は
  どれも置き場の値のまま。**`Meaning.is_complete` はどの経路でも False のままになる**
  (`axes/reading/meaning.py:108` が `purpose_link` の置き場の値を弾くため)。
- **部屋の認識はそもそも実装が無い。** 原則の例に挙がっている5つ(線・面積・部屋・表・寸法)のうち、
  部屋だけが土台から無い。
- `axes/reading/meaning.py` 冒頭の「目的を受け取る場所がこのリポジトリにまだ無い」は
  **古い記述**(`intake/start_kit.py:189` の `Purpose` で受け取れる)。届いていないのは本当。

**直すのは設計の確認後。** この一覧は直す順番を決めるためのものである。

## 8. 既存を壊さないための約束

1. **`PurposeState` を渡さなければ、いまと1行も変わらない。** 引数は任意にする。
2. **付けるものは、値を落とす理由にしない。** `purpose_links` が0件でも、
   `work_category` が区分不明でも、値は出す(原則5「止めずに区別して出す」)。
3. **差分から階層1へ上げない。** PR #33 の 1-3 節と同じ理由で、
   同じ1つの PDF から読んだ2つのページは独立ではない。
4. **キラークエスチョンの内訳を足しても、選ばれる質問の順番を変えない**(6-3節)。
5. **波及ルールが空なら、波及は1件も出ない**(5-7節)。設定を渡さなければ、いまと1行も変わらない。

## 9. 判断待ち(おーちゃんに決めてほしい)

1. **工事区分の言葉をどれに揃えるか。** 「区分不明」(今回の指示)か「区分未定」(PR #33)か。
   **推奨は「区分不明」**(今回の指示が新しく、原則の文書に入った言葉のため)。
   あわせて、いまのコードの `現況/計画/解体/不明` は**別の欄として残す**ことを推奨する
   (図面が何を描いているかと、工事で何をするかは別のものなので、片方に寄せると両方読めなくなる)。
2. **往復の上限回数をいくつにするか。** 収束しない案件で止まらなくなるのを防ぐための数。
   **推奨は、まず上限を置かずに実案件で何回で収束するかを測る**(見立てで決めない)。
3. **図面の凡例と線の種類を読む実装を、いつ入れるか。** 区分を部品が自分で決められる
   根拠のうち、**いま読めないのはこれだけである。** これが無いと、要約資料に書かれていない
   工事の区分は、ページをまたぐ比較でしか決まらない。
4. **部屋の認識をどの順番で入れるか。** 原則の例に挙がった5つのうち、唯一土台が無い。
   面積25項目のうち22項目がここで止まっており、概算モード(PR #44)もここで止まる。
5. **深さで確かさをどう下げるか。** **推奨は、数値を掛けずに `depth` をそのまま残し、
   人に見せる順番にだけ使うこと**(5-5節)。係数を決める実測がどこにも無いため。
   数値で下げたいときは、先に実測を取ってから決める。
6. **金額で止める条件を、いつ繋ぐか。** いま本番の経路には単価も金額も1件も渡っていない
   (5-4節)。**止める条件の3つのうち1つが働いていない状態で走ることになる**ので、
   深さ3段階と工事範囲だけで足りるかを見てから決めたい。
7. **波及ルールの中身を、どこから集めるか。** 原文は施工要領・標準仕様・見積漏れの事例を
   挙げている。**この設計では形だけ用意し、中身は入れない。** 集め方が決まるまで、
   リポジトリに入るのは架空の見本だけになる。

## 10. 測るべきこと(Codex 側)

- 往復が何回で収束するか(1-3節の上限を決めるため)
- 区分不明のまま残る値の割合と、そのうち差分の層で決まる割合
- メニュー外として出る値の件数と、そのうち本当に工事だった割合
- 6-3節の内訳を残したとき、**選ばれる質問の列が1つも変わらないこと**(固定の確認。速度ではない)
- 波及で出した問いのうち、**実際に図面に描かれていた割合**(ルールが当たっているかの確認)
- 波及で出した問いのうち、**本当に見積に必要だった割合**(作り話になっていないかの確認)
- 深さ1・2・3のそれぞれで上の2つがどう変わるか(**深さ3で止めてよいかの裏づけ**)
- 波及ルールを空にしたときの結果が、波及を入れる前と1件も変わらないこと(5-7節の固定の確認)

**どれも実測がまだ無い。** この設計の採否を、見立てだけで決めない。
