## 1. なぜ位置づけを変える必要があるのか(実測した3つの不一致)

現行の実装は、この軸を**個別の対象要素(target)に対する数量レンジを出す弱い軸**として
`AxisQualityFirewall.assess()` に参加させています(`axes/industry_statistics_axis/reading.py`
の `axis_evidence_for_metric(..., target=...)`)。実データを入れた結果、この位置づけは
3点で成り立たないことが分かりました。

### 1-1. 単位が違う(万円/件 対 個数・長さ・面積)

取り込めた実データ15項目の単位は**すべて `万円/件`** です。積算の対象要素は
「建具が何本」「配管が何メートル」であり、同じ軸の出力として比較できるものでは
ありません。

### 1-2. 粒度が違う(1件の工事全体 対 1つの対象要素)

表4-1・表4-2 は「**個別工事の**受注額」の分布です。1件の工事をまるごと1つの
金額として数えた統計であり、その工事の中の1つの部材について何かを言うものでは
ありません。

### 1-3. この不一致が、コード上は黙って通ってしまう(実測)

`AxisEvidence` には単位を表すフィールドがありません(実測: フィールドは
`target` / `count_range` / `source_id` / `axis_id` / `method_id` /
`source_fingerprint` / `strength` / `status` / `calibrated` / `model_confidence` /
`evidence` の11個)。そして階層2への昇格判定
`AxisQualityFirewall._has_two_agreeing_advisory_sources()` は、
**レンジが数値として重なっているかだけを見ます**(`axis_quality_firewall.py`)。

実データで実測したところ、次のようになりました。

```
強い軸(画像軸)        : door_count = (4, 4)          ← 個数
過去実績軸(弱い)       : door_count = (3, 5)          ← 個数
業界一般統計軸(弱い)    : 「住宅 計」= (3, 246)         ← 万円/件 を count_range に入れたもの

→ tier = 2 / provisional_audit / independent_advisory_source_count = 2
```

**「3〜246万円」という金額のレンジが、「建具4本」という個数を支持したと判定され、
階層3(要確認)から階層2(仮採用+抜き取り監査＝自動採用)へ昇格しました。**
`AxisEvidence` に単位が無いので、誰もこれを止めません。これは v8 8節の
「穴2:尤もらしい誤り(複数の解釈がルールに違反せず、フィルターをすり抜ける)」
そのものです。

### 1-4. 報告書4節の「補完関係」の検証は、実データでは再現しない

報告書4節のケースBは「業界一般統計軸を足すだけで階層3→階層2に到達した」と
書いていますが、この検証は `tests/test_industry_statistics_integration.py` の
**架空スナップショット**(`door_count`、単位 `箇所/物件`、検証用の架空値)で
行われたものです。実データのスナップショットには `door_count` という項目が
存在しないため、同じ呼び出しは `status="abstained"`(実測で確認)になり、
階層2には到達しません。

**つまり4節の結論は「実データでは成り立たない」状態です。** 架空の項目を
入れれば成り立ちますが、それは1-3で見たとおり単位不一致を悪用しているだけです。

### 1-5. 危険なのは「昇格させる権限を持っている」こと

v8 5節は補助専用軸について「**他の軸の答えを直接排除する権限を持たせない**」と
定めています。現行実装はこれを守っています(報告書4節で確認済み。確定レンジは
強い軸の値のまま変わらない)。しかし**排除する権限は無い一方で、階層を
上げる権限は持っています。** 階層2は「自動採用するが一定割合を事後監査する」
なので、この軸は単位の合わない数字で**自動採用を後押しできる**状態にあります。
排除よりこちらの方が危険です。

## 2. 修正後の位置づけ(提案)

> **業界一般統計軸は、個別の対象要素の数量には一切関与しない。
> 積算が全部終わった後の「見積もり合計金額」に対してのみ働く、
> 桁違いの誤りを捕まえるための出口検査(安全網)とする。**

具体的には次の4点です。

1. **対象は見積もり合計金額(万円/件)。** 統計の単位・粒度と一致する唯一の
   比較対象です。1件の工事の合計金額を、用途(住宅/一戸建/事務所/店舗など)を
   合わせた分布の中に置いて、どの位置に落ちるかを見ます
2. **働く場所は、軸間照合の中ではなく、その後ろ。** 数量が確定し単価を掛けて
   合計が出た後に回す、独立した検査工程とします。`AxisQualityFirewall.assess()`
   には参加しません
3. **権限は「階層を下げる」方向だけ。** 分布から外れていたら階層3(要確認)に
   落とします。**階層を上げることは絶対にしない**(分布の真ん中に入っていることは
   正しさの証拠ではなく、ただ「桁は合っている」だけなので)。1-5 の危険を
   構造的に塞ぎます
4. **検出できるのは桁違いだけで、それも上振れ側だけ**(根拠は3節)。精度の
   改善には一切寄与しません。v8 1節5項の「精度を上げることと人手コストを
   下げることは別の目的」に照らすと、この検査は**そのどちらでもなく、
   「事故を止める」third の目的**です。この区別も設計書に書き足す提案です

### 2-1. v8 の軸カタログ上の扱い

「軸」という言葉を残すと、また軸間照合に参加させたくなります。**2章の軸カタログ
から外し、別の節(出口検査)に移す**ことを提案します。名前も
「業界一般統計軸」から「**合計金額サニティチェック(業界統計)**」に変えます。

## 3. 閾値をどこに置くか(階級分布から集計した実測値)

「桁違い」を何倍から桁違いとみなすかは、決め打ちせず原本の階級分布から
集計しました(集計スクリプトは `benchmarks/` に追加する提案。4-3節)。

### 3-1. 上振れ側: 「1桁違う」では検出条件にならない

| 用途 | 中央値 | 中央値の10倍を超える工事の実在割合 | p99 | p99/中央値 |
|---|---:|---:|---:|---:|
| 住宅 計 | 31.7万円 | **3.51%** | 796.7万円 | 25.1倍 |
| うち一戸建住宅 | 31.8万円 | **2.73%** | 526.6万円 | 16.6倍 |
| うち共同住宅 専有・専用部分 | 30.5万円 | **4.20%** | 823.0万円 | 27.0倍 |
| うち共同住宅 共用部分 | 32.9万円 | **5.59%** | 2,611.7万円 | 79.4倍 |
| うち共同住宅 全て | 41.2万円 | **11.88%** | (最上位階級に落ちるため算出不可) | — |
| 非住宅建築物 計 | 78.8万円 | **7.42%** | 3,087.2万円 | 39.2倍 |
| 事務所 | 80.3万円 | 7.41% | 3,184.5万円 | 39.7倍 |
| 店舗 | 84.0万円 | 7.66% | 2,912.5万円 | 34.7倍 |
| 生産施設 | 84.8万円 | 7.39% | 3,074.1万円 | 36.3倍 |
| 倉庫・流通施設 | 78.0万円 | 6.12% | 2,840.4万円 | 36.4倍 |
| 学校の校舎 | 73.5万円 | 6.87% | 3,731.9万円 | 50.8倍 |
| 医療施設 | 64.7万円 | 4.89% | 2,163.2万円 | 33.4倍 |
| 宿泊施設 | 82.7万円 | 7.72% | 3,532.9万円 | 42.7倍 |
| 老人福祉施設 | 70.1万円 | 6.38% | 1,993.6万円 | 28.4倍 |
| その他の非住宅建築物 | 79.0万円 | 8.42% | 3,412.5万円 | 43.2倍 |

**中央値の10倍を超える工事は、実際に 2.7〜11.9% 存在します。** つまり
「1桁違うから誤りだ」とは言えません。素朴に「桁違い＝10倍」と実装すると、
正常な案件の 3〜12% を人手確認に回すことになります。

実データの裏付けで言える閾値は **p99(中央値の17〜79倍)** です。これを超えたら
「100件に1件の希少さ」であり、確認を促す根拠になります。

### 3-2. 上振れ側の上限: 統計が何も言えなくなる点

最上位階級は上限がありません(住宅「3,000万円以上」、非住宅「5億円以上」)。
そこに落ちた場合、統計は「これ以上」としか言えません。

| 区分 | 最上位階級 | 中央値との比 | その階級の実在割合 |
|---|---|---:|---:|
| 住宅 計 | 3,000万円以上 | 94.5倍 | 0.151% |
| 住宅 うち一戸建 | 3,000万円以上 | 94.4倍 | 0.022% |
| 住宅 うち共同住宅 全て | 3,000万円以上 | 72.9倍 | 2.435% |
| 非住宅建築物 計 | 5億円以上 | 634.7倍 | 0.044% |
| 非住宅 老人福祉施設 | 5億円以上 | 713.4倍 | 0.005% |

ここに落ちた合計金額は、**最も強い警告(階層3に落とすだけでなく、理由を
「統計の分布の外側で、統計はこれ以上何も言えない」と明記して人に出す)**
として扱う提案です。

### 3-3. 下振れ側: 閾値を置けない(実データの裏付けが無い)

**最下位階級が全体の 59〜82% を占めています。**

| 区分 | 最下位階級 | 占有率 |
|---|---|---:|
| 住宅 計 | 0〜50万円 | 78.8% |
| 住宅 うち共同住宅 専有・専用部分 | 0〜50万円 | 82.0% |
| 住宅 うち共同住宅 全て | 0〜50万円 | 60.7% |
| 非住宅建築物 計 | 0〜100万円 | 63.5% |
| 非住宅 店舗 | 0〜100万円 | 59.5% |
| 非住宅 医療施設 | 0〜100万円 | 77.3% |

報告書が出している `low`(第5パーセンタイル、住宅3.2万円など)は、**この
1つの巨大な階級の内側を一様分布と仮定して内挿した値にすぎません。** 統計は
「0〜50万円の中がどう分布しているか」を一切答えていないので、
**第5パーセンタイル自体が実データではなく仮定の産物です。**

したがって**下振れ側には検査を実装しないことを提案します**(`abstained` として
明示的に棄権する)。「見積もりが安すぎる」方向の桁違いは、この統計では
検出できません。ここを検出したいなら別のデータ源が必要です。

**この結論は、依頼にあった「桁違いの誤りを検出する安全網」という位置づけを
半分に絞ることになります。** 上振れは検出できますが、下振れは検出できません。

### 3-4. 適用範囲の限界(見落とされやすい点)

- **この統計はリフォーム・リニューアル工事の受注額です**(統計名:
  建築物リフォーム・リニューアル調査)。**新築工事の見積もりには適用できません。**
  新築案件では検査自体を棄権させる必要があります
- **1件の工事の受注額**なので、複数工事をまとめた見積もりや、1件の工事を
  分割した見積もりには適用できません
- 令和7年度(2025年4月〜2026年3月)受注分の分布です。物価が動けばずれます。
  年1回(6月頃)の更新で追随します

### 4-2. コードへの反映案(ドキュメントと同時に必要なもの)

位置づけの修正は文書だけでは効きません。1-3の穴が開いたままだと、
将来誰かが金額項目を数量ターゲットに登録できてしまいます。

1. **`axes/industry_statistics_axis/reading.py` の
   `reading_for_metric` / `axis_evidence_for_metric` を廃止する。**
   `SymbolCountReading`(個数の型)に金額を入れる経路そのものを消します。
   これが1-3の穴を塞ぐ最短の手です
2. **新モジュール `arbitration/total_amount_sanity_check.py` を追加する。**
   入力は「見積もり合計金額(万円)・用途・工事区分(リフォーム/新築)」、
   出力は判定です。案:

   ```python
   @dataclass(frozen=True)
   class TotalAmountVerdict:
       status: Literal["within_distribution", "high_outlier",
                       "beyond_statistics", "abstained"]
       # 分布のどこに落ちたか(百分位)。beyond_statistics では None
       percentile: float | None
       # 階層を下げる必要があるか。within_distribution / abstained では False
       forces_review: bool
       reason: str
       evidence: dict[str, object]   # 用途・中央値・p99・出典・取得日
   ```

   - `forces_review=True` を返せるのは `high_outlier`(p99超)と
     `beyond_statistics`(最上位階級)のみ
   - **階層を上げる出力を型として持たない。** `within_distribution` は
     「桁は合っている」だけで、何の支持も与えません
   - 新築・用途不明・複数工事のまとめは `abstained`
   - 下振れは3-3のとおり検出しない(`abstained`)
3. **`arbitration/inference_orchestrator.py` の `ALLOWED_AXES` から
   `"statistical"` を外す。** 軸間照合に登場しない軸なので、登録されている
   こと自体が事故の入口になります
4. **`AxisEvidence` に単位のフィールドを足し、`assess()` で単位が揃って
   いることを検査する**(別提案として切り出し可)。1-3 は業界統計軸に限った
   穴ではなく、**どの軸でも単位を間違えれば同じことが起きます。** 今回の軸を
   外しても、この穴は残ります
5. `tests/test_industry_statistics_integration.py` の4件は、架空の
   `door_count` 項目に依存しているため書き換えが必要です。新しいテストは
   「金額項目を数量ターゲットに登録する経路が存在しないこと」を縛る方向に
   します

> ### 5-2. 出口検査: 合計金額サニティチェック(2026-09-21 新設)
>
> 軸間照合・3段階確信度階層・キラークエスチョンは、すべて**個別の対象要素の
> 数量**を扱う。これらを通過して数量が確定し、単価を掛けて見積もり合計金額が
> 出た後に、**最後に1回だけ走る独立した検査**を置く。
>
> - **目的は精度でも人手コスト削減でもなく、事故の防止。** v8 1節5項は
>   「精度」と「人手コスト」を分けて設計すると定めているが、この検査は
>   そのどちらでもない第3の目的(桁違いの見積もりをそのまま外に出さない)に
>   属する
> - **判定材料は外部の公開統計の分布**(国土交通省 建築物リフォーム・
>   リニューアル調査、用途別の受注額分布)
> - **権限は非対称とする。確信度階層を下げること(階層3へ落とす)だけができ、
>   上げることはできない。** 分布の中に入っていることは正しさの証拠ではなく、
>   「桁が合っている」以上のことを意味しない
> - **検出できる範囲は限定的で、そのことを設計上明示する**
>   - 上振れ(見積もりが高すぎる): 検出する。閾値は分布の p99(用途により
>     中央値の17〜79倍)。「1桁違う=10倍」は閾値にならない(中央値の10倍を
>     超える工事が実際に 2.7〜11.9% 存在する)
>   - 下振れ(見積もりが安すぎる): **検出しない。** 最下位階級が全体の
>     59〜82% を占め、その内側の分布は統計に載っていないため、下限側の
>     分位点は仮定の産物にすぎない
>   - 新築工事: **適用外**(統計がリフォーム・リニューアルの受注額のため)
> - 根拠の数値と集計方法は `docs/proposal_industry_statistics_repositioning.md` 3節
