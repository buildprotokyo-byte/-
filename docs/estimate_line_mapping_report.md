# 数量を見積の行に当てはめる仕組み(報告)

作成: 2026-09-22 / 対象: `estimating/`(新規)、`tests/test_estimate_line_mapping.py`(新規)
土台のコミット: `f005394`(main)

おーちゃんの作業キュー新3「数量化と見積の行への対応付け」に対する実装。
**Codex が作成中の詳しい仕様はまだ届いていない。** そのため、仕様が届いた
ときに作り直しが小さく済む順で進めた。詳細は 7 節。

---

## 1. 着手前にコードで確かめたこと

「実装済み」という記録を信じず、実際に動かして確かめた。合成のベクター PDF を
その場で組み立て、`intake.drawing_intake.read_drawing()` をそのまま走らせた
結果が次である。

```
読めた数量: 3 件
自動確定: 0 件
  - 開き戸::ページ1: 階層3 / requires_review
  - 専有延床面積:   階層3 / requires_review
  - 施工床面積:     階層3 / requires_review
```

分かったこと。

1. **入口が出す数量の種類は 4 つしかない。** `開き戸::ページN`(箇所)、
   `建具数量::<建具番号>`(箇所)、`専有延床面積` / `施工床面積`(㎡)、
   面積の選択に人が答えたときだけ出る `施工対象床面積`(㎡)。
2. **判定は全件が階層3(`requires_review`)で、`confirmed_range` は None。**
   理由コードは `empirical_calibration_missing_or_failed` と
   `tier1_requirements_not_met`。**自動確定は 1 件も無い。**
3. **内装仕上表の行は数量ではない。** 室の輪郭を取る実装が無いので、
   仕上げから面積は出せない(`IntakeResult.finish_schedule_rows` の説明どおり)。
4. 建具表の種別は `DoorScheduleRow.kind` にあり、**読めなければ None**。
5. 見積の行の語彙は、すでに `benchmarks/run_golden_eval.py` にある
   (`code` / `work_item` / `major_category` / `unit` / `expected_source_type`)。
   新しい語彙を作ると将来の突き合わせで対応表が要るので、これに合わせた。

**2 は設計に直接効く。** 当てはめの対象になる数量が 1 件も確定していない以上、
「当てはめが一意に決まったら確定させる」作りにすると、**確定していない数量が
見積の行として確定してしまう。** 確定の条件を 2 つに割ったのはこのためである
(3 節)。

## 2. 作ったもの

`intake/` には**1 行も手を入れていない。** 他スレッドが同じファイルを触って
いるためと、数量の出どころが将来ふえるため。変換は `estimating/` 側に置いた。

| ファイル | 役割 |
| --- | --- |
| `estimating/quantities.py` | 当てはめの入力になる中立の数量 `QuantityItem`。対象名を `::` で(種類, 鍵)に割る |
| `estimating/rules.py` | 当てはめの規則の読み込みと検査。**書式が変わる影響をここだけに閉じ込める** |
| `estimating/mapping.py` | 当てはめの本体。候補・衝突・確定の判定 |
| `estimating/from_intake.py` | `IntakeResult` → `QuantityItem` の変換。建具表から属性を取る |
| `estimating/examples/synthetic_rules.json` | **合成の**見本規則。実在の会社の積算ルールではない |

## 3. 確定の条件を 3 つに割った

見積の行が確定するのは、次の**3 つすべて**が揃ったときだけにした。

1. 当たった規則がちょうど 1 つであること(当てはめが一意に決まった)
2. **数量そのものが仲裁層で確定していること**(`action == "auto_confirm"` かつ
   `confirmed_range` が有ること)
3. その見積の行に、ほかの数量がぶつかっていないこと

1 だけで確定させると、「規則がきれいに書けている」という**単一の指標だけ**を
根拠に自動確定することになる。おーちゃんのルール3(単一の指標だけを根拠に
自動確定させる変更はしない)に正面からぶつかる。

2 だけでも足りない。数量が確定していても、それがどの行の数量なのかが
決まっていなければ見積の行にはならない。

3 が要るのは入口の約束を打ち消さないため。入口は「ページをまたいで足さない」
と決めている(既存平面図と新設平面図の開き戸を足すと同じ建具を二重に数える)。
当てはめで同じ行に集めて足すと、その約束が裏口から破れる。**足さずに衝突として
人へ回す。**

**結果として、2026-09-22 時点でこの経路から出る確定は 0 件である。**
2 が常に偽だからで、実装の不具合ではない。
`tests/test_estimate_line_mapping.py::test_nothing_is_settled_through_the_whole_path`
が固定していて、入口側の `test_nothing_is_auto_confirmed_through_this_path` と
対になっている。どちらかの手法が `calibrated=True` になったとき、両方が気づく。

## 4. 一意に決まらないときの扱い

**「1 つの数量が複数の行になること」と「当てはめが決まらないこと」は別物**なので、
書式で分けた。

- **1 つの規則が複数の行を作る**(取付費と材料費)…… あいまいさではない。
  `line_items` に並べる。2 行はセットで出る。
- **複数の規則が同じ数量に当たる**(木製建具の規則と鋼製建具の規則の両方に
  当たる)…… これが「一意に決まらない」場合。`status = "ambiguous"` にして、
  **規則ごとの束**(`RuleOutcome`)を候補として並べ、**確定しない**。

候補を行の並びではなく束にしたのは、選ぶ対象が行ではなくセットだからである。
「木製の取付費と木製の材料費」か「鋼製の取付費と鋼製の材料費」かであって、
4 行から好きに選ぶわけではない。

---

## 5. 当てはまらなかったものを捨てない

規則が 1 つも当たらなかった数量も `status = "unmapped"` として残し、当たらな
かった理由を付ける。黙って消すと、見積に出てこない項目があることに集計表からは
気づけない(v8 8章の穴2と同じ形)。

理由の出し方にひとつ工夫がある。**種類がそもそも違う規則の「当たらなかった
理由」は残さない**(規則の数だけ出て読めなくなる)。残すのは**種類は合っていた
のに当たらなかった理由**だけで、これが実際に知りたいこと、つまり

- 「規則が条件にしている属性 種別 がこの数量には無い」(建具表の種別が読めなかった)
- 「行の単位 ㎡ は数量の単位 箇所 と揃わない(換算しない)」

である。

---

## 6. 読めなかったものを当てない

規則が `attributes` で条件にしている属性が数量に**無い**ときは、当てない。
読めなかった属性で見積の行を決めてしまわないため。理由は残す。

同じ建具番号の種別がページによって食い違ったときは、**どちらも属性にしない**
(`attributes_for_door_mark`)。片方を選ぶと、選ばなかったほうの規則が黙って
外れる。食い違った事実は `QuantityItem.notes` に残る。

属性の突き合わせは NFKC 正規化と前後の空白除去だけを行う(`ＳＤ` と `SD` が
別物にならないように)。**表記をそろえるだけで、意味は変えない。**

## 7. Codex の仕様が届いたときに作り直す範囲

仕様が届いたときに一番変わりそうなのは**規則の書式**なので、そこだけを
`estimating/rules.py` の読み込みに閉じ込めた。

- 規則ファイルは `format_version` を必ず持つ。**この読み込みが知らない版の
  ファイルは読まない**(`RULES_FORMAT_VERSION` は 1)。新しい書式が来たら、
  版を上げた読み込みを足す。古い読み込みが新しいファイルを半分だけ解釈して
  「一部の規則だけが効いている」状態になるのを防ぐ。
- **知らない項目があったら断る。** 読み飛ばしたほうが親切に見えるが、
  `歩掛` のような新しい項目が黙って無視されると、掛けたつもりの数字が
  掛かっていない見積が出る。
- 行の単位は**読み込みの時点で**検査する(`人工` のような未知の単位は、
  当てはめを走らせる前に落ちる)。

作り直しが小さく済むように分けたのは次の点である。

| 変わりにくい(仕様が来ても残る) | 変わりやすい(仕様で決まる) |
| --- | --- |
| `QuantityItem`(入口が出す形で決まっている) | 規則ファイルの書式 |
| `MappedLine` / `RuleOutcome`(見積の行の語彙はゴールデンで決まっている) | 条件の書き方(属性・数値条件・正規表現) |
| 確定の 3 条件(おーちゃんのルールで決まっている) | あいまいさの解き方(優先順位、既定の規則) |

**いま書式に入れなかったもの**(仕様待ち): 数値の条件(幅 900 以上など)、
歩掛・係数、建具番号への正規表現、規則の優先順位、1 つの行に複数の数量を
まとめる書き方。どれも「あったほうがよい」ではなく「仕様で決まってから
足すほうが安い」という判断。

## 10. Codex 側で測るべき項目

重い計測はこちらで行わない決まりなので、書き出すだけにする。

1. **ゴールデンベンチマーク(renovation-golden-001、99 項目)の各行が、
   この書式の規則で書けるか。** 書けない行が何割あるかで、7 節の「入れなかった
   もの」のどれを先に足すかが決まる。**これは計測ではなく棚卸しなので、
   規則ファイルを 1 つ書いてみるだけで分かる。**
2. 実案件 1 件ぶんの規則を書くのにかかる手間(行数・時間)。差し替えられる
   設定にした意味は、ここが現実的かどうかで決まる。
3. 同じ数量に複数の規則が当たる割合。高ければ、候補のまま人へ回る件数が
   多くなり、あいまいさの解き方(7 節)の優先度が上がる。

## 11. 判断待ち

1. **同じ行に複数の数量が当たったときの扱い。** いまは足さずに衝突として
   人へ回す。既存と新設で行を分ける(`開き戸 取付費(新設)`)という解き方も
   あるが、どのページが既存でどれが新設かは図面の文字からは決まらない
   (入口が判断していない)。スタートキットの「現況/計画の区別」が入って
   いれば決められるので、**そこにつなぐかどうか**の判断が要る。
   推奨: つなぐ。ただし別作業として切り出す(この層だけでは決められない)。
2. **見積の行の単位が数量の単位と違うときに、換算を許すか。** いまは
   次元が違えば行を作らない(箇所 → ㎡ は数量からは導けない)。実務では
   「建具 1 箇所あたりシール延長 3m」のような歩掛があり得るが、それは
   当てはめではなく**新しい数量を作る**ことなので、別の仕組みにするべきだと
   考えている。推奨: この層では換算を許さないまま。歩掛は仕様が届いてから
   別の層として設計する。
3. **規則ファイルをどこに置くか。** いまは呼び出し側がパスを渡す。実際の
   会社の積算ルールはリポジトリの外に置く前提だが、**案件ごとに違うのか、
   会社で 1 つなのか**が決まっていない。
