## 1. 環境確認結果(OR-Tools/Z3のどちらを採用したか、理由)

`ortools`・`z3-solver` はどちらも PyPI から問題なくインストール・実行できました。

| リソース | 結果 | 確認内容 |
|---|---|---|
| ortools | **使える** | 9.15.6755。CP-SAT で `x == y + 1` を解けることを確認 |
| z3-solver | **使える** | 5.1.0.0。`assert_and_track` + `unsat_core()` で矛盾した制約名を取得できることを確認 |

どちらも標準的な整数の範囲・線形関係式の制約充足には十分で、このリポジトリの依存関係(numpy 等)とも
衝突しませんでした。採否を分けたのは、指示書が明示的に要求している次の要件です。

> 解が存在しなければ、「矛盾(空集合)」として、どの制約同士が衝突しているかを特定して返す

Z3 は `Solver.assert_and_track(expr, name)` で制約に名前を付けておくと、`unsat_core()` が
「矛盾の原因になった制約の名前の集合」をそのまま返します。OR-Tools の CP-SAT でも
assumption リテラルを介して同等のことはできますが、制約 1 つずつを reify する配線が別途必要です。
**宣言した制約にそのまま名前が付く Z3 の方が、実装・可読性の両面で単純だったため、今回は Z3 を採用しました。**

なお、実装中に一点注意が必要でした。`assert_and_track` は内部的に `Implies(tracker, expr)` という
形で制約を保持しており、`Solver.assertions()` を素直に別の `Optimize` へ流用すると `tracker` が
真であることが伝わらず、範囲制約が効かなくなります(実際に試して `min x = -2`(本来は範囲外)という
誤った結果を得ました)。そのため、レンジ収束(後述)の計算では毎回、生の制約式から `Optimize` を
組み直す設計にしています(詳細は `consistency_solver.py` の `_tighten` の docstring)。

## 2. consistency_solver.pyの実装内容

### データ構造

- `Variable` … ハードな制約に使う変数 1 つ(名前・下限・上限・所属軸・強度)
- `Constraint` … z3 の式を組み立てる関数を包んだ、名前付きの宣言的制約
- `AdvisoryReading` / `AbstainedReading` … 弱い軸の参考情報 / 棄権した読み取りの記録(いずれも z3 変数にはならない)
- `SolveResult` … 求解結果。`status`(`sat`/`unsat`)、変数ごとの絞り込み後レンジ、
  矛盾した制約名の集合、弱い軸との突き合わせ結果(`AdvisoryNote`)を保持

### 公開 API

- `add_variable(name, lower, upper, *, strength, axis)` … 下限・上限を直接指定して変数登録
- `add_variable_from_reading(name, reading, *, axis, strength)` … `SymbolCountReading`
  (レンジ + 根拠 + 確信度)をそのまま変数として登録する。指示書が要求している
  「画像軸・絶対ルール軸それぞれが出す SymbolCountReading を、ソルバーの変数として宣言する」
  に直接対応する
- `add_advisory_reading(target, reading, *, axis)` … 弱い軸の読み取りを参考情報として登録する。
  **z3 の変数を一切作らない**ため、ハードな解を排除する権限を型のレベルで持たない
- `add_constraint(name, build, *, description)` / `add_relation(name, lhs, op, rhs, *, description)` …
  「開き戸の数 = 部屋数 + 1」のような要素間の関係式を宣言する。`add_relation` は
  `lhs`/`rhs` に変数名・整数・`dict → z3 式` の関数のいずれも渡せるので、単純な等式から
  `door_count == room_count + 1` のような線形式まで表現できる
- `has_variable(name)` … 棄権により変数が未登録の可能性があるため、呼び出し側のガード用に公開
- `solve()` … 求解する。詳細は下記

### solve() の動作

1. **強い軸の変数のみ**を z3 の `Int` として宣言する(弱い軸は最初から z3 に現れない)
2. 各変数の範囲制約と、宣言済みの全関係制約を `assert_and_track` で名前付きで表明する
3. `status == "abstained"` の読み取りは、変数を追加せず `AbstainedReading` として記録するだけにする
   (v8 の「分布外の軸はレンジを主張せず棄権する」への対応)
4. **解が存在する場合**: 各変数について `z3.Optimize` で最小値・最大値を求め、
   「元のレンジ ∩ 全制約」で絞り込まれたレンジ(= v8 の「多軸レンジ収束」の積集合)を返す。
   併せて、弱い軸の読み取りをこの絞り込み後レンジと突き合わせ、重なるかどうかを
   `AdvisoryNote` として添える(重ならなくても解には影響させない)
5. **解が存在しない場合**: `unsat_core()` が返す制約名の集合を、そのまま
   `conflicting_constraints` として返す

## 3. 段階Aのデータでの検証結果(矛盾検出、通常ケースの解)

検証は `benchmarks/run_consistency_eval.py` として実装し、`benchmarks/synthetic_plans.py` の
合成図面をそのまま使いました。

**記号認識について(段階Aと同じ、正直な制約)**: この整合性ベンチマーク自体は、段階Aの
`benchmarks/run_ifc_eval.py` が使ったのと同じ「正解の記号位置にどれだけインクが残っているか」
というプロキシ判定を再利用し、その判定結果を `StaticBackend` に注入して**本物の
`GroundingDinoAdapter` を実際に走らせています**。つまりここで測っているのは
「整合性軸が、段階Aで既に確認済みの読み取り劣化(記号の見落とし)を正しく矛盾として拾えるか」です。
引き継ぎ後にGrounding DINO本体も別途実測しましたが、個別記号のIoU一致が0件だったため、
低精度な実モデル出力を強い変数としてこのベンチマークへ流し込むことはしていません。

### 通常ケース(劣化なし)

戸4・窓4・部屋4がすべて読み取れる条件です。

```
door reading:   status=confident range=(4, 4)
window reading: status=confident range=(4, 4)
status=sat (9.4 ms)
  room_count: (4, 4) -> (4, 4)
  door_count: (4, 4) -> (4, 4)
  window_count: (4, 4) -> (4, 4)
  symbol_total_count: (0, 10000) -> (8, 8) (絞り込み)
```

矛盾なく解け、`symbol_total_count`(戸+窓の会計上の恒等式で定義した派生変数)は
初期範囲 `(0, 10000)` から `(8, 8)` まで絞り込まれました。これが v8 で言う
「多軸レンジ収束」の実例です。

### 矛盾ケース(中度劣化・窓1つ見落とし)

**段階Aの報告書(`docs/stage_a_report.md` 表2「中度 古典(median=1)」)で実測済みの、
窓を1つ読み落とす条件をそのまま再利用しました。新しく数値を作ってはいません。**

```
door reading:   status=confident range=(4, 4)
window reading: status=confident range=(3, 3)
status=unsat (2.0 ms)
  矛盾した制約: range::window_count, range::room_count, window_ge_room
```

`window_count >= room_count`(IfcOpenShell の `space_without_window` に相当する絶対ルール)
に対し、読み取った窓の数(3)が部屋数(4)を下回ったため、正しく `unsat` として検出できました。
`unsat_core` が返した集合には、関係式 `window_ge_room` に加えて両方のレンジ制約
(`range::room_count`, `range::window_count`)も含まれています。これは z3 として正しい挙動です。
`room_count` と `window_count` がどちらも単一値に固定されているため、いずれのレンジ制約が
欠けても変数がその分だけ自由に動けて `sat` になり得る、という意味で**両方とも矛盾の必要条件**
だからです(不要な制約まで拾っているわけではありません)。

### 比較ケース(単純な比率チェックとの差を見るための手動構成ケース)

ステップ4の効果測定を兼ねて、合成図面の読み取りではなく手で組んだケースも1つ検証しました。
戸2・窓6・部屋4という構成です。戸+窓の合計は8で、部屋数4の2倍(8)と**一致**しています。

```
door reading:   status=confident range=(2, 2)
window reading: status=confident range=(6, 6)
status=unsat (1.1 ms)
  矛盾した制約: range::room_count, door_ge_room, range::door_count
```

整合性軸は `door_count(2) < room_count(4)`(戸のない部屋が存在する)を正しく `unsat` として
検出しましたが、詳細はステップ4で述べるとおり、**単純な比率チェックはこれを見逃します**
(合計だけを見ると異常が無いため)。

## 4. 強い軸/弱い軸の区別の反映方法

### 実装上の反映

`add_variable_from_reading` / `add_variable` で登録した変数だけが z3 の変数になり、ハードな
制約(範囲・関係式)の対象になります。`add_advisory_reading` で登録した読み取りは
**そもそも z3 の変数を作らない**設計にしました。これにより、「弱い軸は参考情報・注意喚起
としてのみ提示し、候補を排除する権限を持たせない」という v8 の方針を、実装の都合による
バグではなく、型・API レベルで保証しています(弱い軸の読み取りをうっかりハードな制約に
混ぜてしまう経路自体が存在しません)。

### 段階Aの2つの成果は、それぞれどちらとして扱うべきか

**VTracer(壁の幾何)→ 弱い軸として扱うべき、と判断しました。**

理由は段階Aの実測結果そのものです。

1. 記号(戸・窓)の検出には**明確に悪影響**でした。段階Aの計測では、劣化した図面で
   記号部の線を6〜7割失うことが確認されています(軽度劣化ですら `-61.0%`)。整合性軸が
   扱う「戸・窓の個数」という量に対して、VTracer 由来の情報は不利な材料です
2. `docs/stage_a_report.md` 7節で段階A自身が明記しているとおり、**単一図面・単一乱数シード
   での結果**であり、統計的な再現性は未確認です。v8 の強い軸の定義(「十分なサンプル・
   実測校正済み・分布内」)を満たしていません
3. 壁部の幾何については引き継ぎ後の再実行で `+115.4% → -4.0%` に改善するなど確かに有効ですが、
   これは「壁の総延長」という別の量の話であり、本報告書の整合性軸が扱う記号の個数には
   直接使えません

実際に `benchmarks/run_consistency_eval.py` では、VTracer の連結成分数から作った
「記号総数の粗い見積もり」を弱い軸として登録しました。通常ケースの実行結果は

```
symbol_total_count: (8, 8) (強い軸の解)
[advisory] vtracer の参考情報: 'symbol_total_count' は (10, 14) だが、
強い軸の解 (8, 8) と重ならない(参考情報のため解の排除はしない。要注意)
```

で、**強い軸の解と重ならない**という結果になりました。劣化のない図面ですら
VTracer 由来の見積もりが実際の記号数と食い違うという、弱い軸として扱う判断を裏付ける結果です。
それでもこの不一致は解を `unsat` にはせず、注意喚起(`AdvisoryNote`)としてのみ提示されています。

**IfcOpenShellの空間階層検証 → 「ルールそのもの」は強い軸、代入する値の強度は元の軸次第、と判断しました。**

これは単純な二分法では答えられない、と考えています。IfcOpenShell の
`space_without_door` / `space_without_window` のようなチェックは、統計的な推定ではなく
「部屋には出入口が要る」「居室には採光開口が要る」という建築基準法・実務慣行に基づく
**普遍的な規則**です。この規則自体(=本報告書で `door_count >= room_count` のような
関係式として実装した部分)は、v8 の絶対ルール軸の定義どおり、疑う余地のない強い制約
として扱ってよいと判断しました。

一方で、その関係式に代入する `door_count` や `window_count` という**値そのもの**は、
どの軸が測ったかによって強度が変わります。今回の検証では Grounding DINO アダプタが
`confident` と判定した読み取りだけを強い変数として登録し、`abstained`(1件も検出できない)
場合は変数ごと除外しました。これは v8 が絶対ルール軸について指摘している
「式は普遍的だが、代入する材料が画像由来であることが多い」という条件付き独立性の構造を、
そのまま整合性軸の設計に持ち込んだ形です。

## 5. 効果測定

### 5-1. 矛盾の検出精度・誤検出の少なさ

単純な比率チェック(`戸+窓の合計 < 部屋数×2 なら異常`)との比較を行いました。

| ケース | 整合性軸 | 単純な比率チェック |
|---|---|---|
| 通常(劣化なし) | 矛盾なし | 異常なし(一致) |
| 中度劣化・窓1つ見落とし(戸4・窓3・部屋4) | **矛盾あり**(`window_ge_room`) | 異常あり(合計7<8。一致) |
| 比較ケース(戸2・窓6・部屋4、合計は部屋数の2倍と一致) | **矛盾あり**(`door_ge_room`) | **異常なし(見逃し)** |

3件中2件は両者とも同じ判定でしたが、3件目で明確な差が出ました。**合計だけを見る比率チェックは、
内訳の偏り(ある部屋にだけ戸が足りない、というような取り違え)を原理的に検出できません。**
これは v8 が「合計=内訳の和という制約だけでは、内訳同士の入れ替わりを検出できない」
(トライアル10の留保点)として既に指摘していた盲点と同じ構造です。整合性軸は要素ごとの
関係式を宣言できるため、この種の偽陰性を減らせることを確認しました。

誤検出(偽陽性)については、今回検証した3ケースの範囲では発生していません。ただし
これは母数が小さいため、「誤検出が少ない」ことの十分な証拠ではなく、**今回確認できた
のは検出できる矛盾の種類が広がったことだけ**、と正直に留保します。

### 5-2. 処理にかかる時間(合成図面規模での実測)

`solve()` 全体を200回繰り返して計測しました(4部屋規模、変数4個、追跡対象の制約7個
= 範囲4個 + 関係式3個)。引き継ぎ後のWindows環境で短時間計測が0 msに丸められないよう、
高分解能の `time.perf_counter()` を使う再現可能な計測をベンチマークへ追加しました。

| 指標 | 値 |
|---|---|
| 中央値 | 4.491 ms |
| 平均 | 4.840 ms |
| 95パーセンタイル | 7.019 ms |
| 最大 | 10.841 ms |

「読み取り(インク残存率の計算・VTracer 呼び出し)〜求解」までの今回の再実行では
約87〜316 msでしたが、これは大部分が画像処理(VTracer のベクター化呼び出し等)に
かかっている時間で、**ソルバー自体の処理時間は無視できる水準**でした。

今回の規模(変数一桁・制約一桁)では OR-Tools と Z3 の速度差を云々するレベルではありません。
変数・制約が数百〜数千に増える場面(例えば部材ごとに変数を持つような規模)が出てきた場合は、
改めて両者を比較する必要があります。

### 5-3. 実装・設計にかかった手間、つまずいた点

- 設計自体は指示書の方針(SymbolCountReading をそのまま変数にする、強い軸のみハードにする)
  に沿って素直に実装できました。手間がかかったのは Z3 特有の落とし穴で、
  `assert_and_track` の内部実装(`Implies(tracker, expr)`)を理解せずに `assertions()` を
  別の `Optimize` へ流用すると、範囲制約が効かないまま最適化してしまうという事象に
  一度遭遇しました(1節参照)。実装前に小さなスクリプトで先に検証したため、
  本体のコードに紛れ込む前に発見できました
- 「弱い軸をどう解に混ぜないか」という設計判断は、変数を作らないという方針にした
  ことで、実装上の考慮ポイントが最小限で済みました

## 6. 段階Aとの統合における注意点

1. **`SymbolCountReading` はそのまま使えました。** 段階Aのデータクラスに一切手を加えず、
   `add_variable_from_reading` の入力として直接渡せます
2. **強い軸が完全に棄権すると、その要素についての矛盾検出そのものが成立しなくなります。**
   `door_count` や `window_count` の読み取りが `abstained`(検出0件)の場合、
   `consistency_solver` は変数を作らないため、それを参照する関係式を追加しようとすると
   `KeyError` になります。`benchmarks/run_consistency_eval.py` では `has_variable()` で
   ガードしましたが、実運用では「棄権した要素をどう扱うか」(例: 別の軸で埋め合わせる、
   人に確認する)を呼び出し側で決める必要があります
3. **IfcOpenShell の `audit()` とは、今回あえて統合しませんでした。** `ifc_containment.py`
   の `audit()` は「既に登録された要素」から空間階層上の異常(orphan・空室等)を検出する
   ものですが、本報告書の整合性軸は「登録する前の、レンジを持った読み取り値」を扱います。
   両者は役割が違うため、今回は `audit()` が検出するルール(`space_without_door` 等)を
   **z3 の関係式として宣言し直す**形にしました。同じルールが2箇所に記述されている状態
   なので、今後どちらか一方に一本化するか、`audit()` 側からルールを取り出して
   `consistency_solver` に流し込む変換層を作るか、設計判断が必要です
4. **room_count の扱いは今回の検証固有の単純化です。** 検証では合成図面の部屋一覧
   (`plan.rooms`)から直接、既知の値として構築しましたが、実運用では部屋数自体も
   何らかの軸(画像軸・絶対ルール軸)からレンジ+確信度として読み取る必要があります

## 7. 制約・うまくいかなかった点

1. **整合性ベンチマークへの入力は実モデル結果ではありません。**引き継ぎ後にGrounding DINO本体は
   実行できましたが、合成図面4条件で個別記号のIoU一致が0件でした。これを強い変数として
   入れるのは設計違反になるため、整合性軸の機能検証には従来どおり既知のプロキシ入力を使っています
2. **単一の合成図面・単一の乱数シード(seed=7)での結果です。** 段階Aの報告書が
   自ら指摘している限界がそのまま引き継がれています。異なる乱数シード・異なる
   部屋数構成での再現性は未検証です
3. **VTracer の連結成分数からの「記号総数の見積もり」(±2個の余裕)は、根拠のある
   誤差モデルではなく、ラフな仮定です。** これ自体は弱い軸として扱っているため
   ハードな解には影響しませんが、参考情報としての精度も検証していません
4. **「レンジの絞り込み」は変数ごとの射影であり、変数間の相関を保持しません。**
   例えば `x + y == 10` で `0 <= x <= 10`、`0 <= y <= 10` という制約だけがある場合、
   `_tighten` は `x`・`y` それぞれについて独立に `(0, 10)` を返しますが、実際の解集合は
   直線上の点に限られます。個々の変数のレンジとしては正しい値ですが、
   「変数の組み合わせとしてどの解が同時に成り立つか」までは表現していません。
   複数の解の組み合わせ自体が必要な場面では、`solve()` が返す絞り込みレンジではなく、
   個別の充足可能な割り当て(モデル)を都度 `check()` で取り出す必要があります
5. **誤検出の少なさは十分に検証していません。** 5-1節のとおり、3ケースの範囲では
   偽陽性は出ませんでしたが、母数が小さく、誤検出率を主張できる段階ではありません
6. **効率(自動化率・監査コスト)への効果は測っていません。** 段階Aと同じ理由で、
   確信度階層とキラークエスチョンエンジンの実装が先に必要です
7. **IfcOpenShell の `audit()` との重複は未解消です。** 6節の3で述べたとおり、
   同じ絶対ルールが2箇所(`ifc_containment.py` の `audit()` ロジックと、
   `consistency_solver` に渡す関係式)に別々の形で存在しています

---

## 8. 結論

**段階Bの目標(OR-Tools または Z3 による整合性軸の実装・検証)は達成できました。**
Z3 を採用し、`SymbolCountReading` をそのまま変数として宣言できる `consistency_solver.py`
を実装し、段階Aの合成図面データで通常ケース・矛盾ケースの両方が期待どおりに解けることを
確認しました。加えて、単純な比率チェックでは検出できない「内訳の取り違え」型の矛盾を
検出できることも、手動構成したケースで確認できました。

実務に効く知見は次の3つです。

1. **v8 の「弱い軸は参考情報のみ、候補を排除する権限を持たせない」という方針は、
   変数を作らないという設計にすることで、実装上の考慮漏れではなく型のレベルで
   保証できる**
2. **VTracer は記号の個数に関しては弱い軸として扱うべきで、実測でもその判断を裏付ける
   結果(通常ケースでも強い軸の解と重ならない見積もりを出す)が得られた**
3. **絶対ルール軸のルールそのものは強い制約として扱えるが、そこに代入する値の強度は
   別問題であり、この2つを区別して実装する必要がある**(v8 の「条件付き独立性」の
   構造がそのまま整合性軸の設計に反映される)

次に進むべきは、6節で挙げた `audit()` との重複解消、および複数の乱数シード・
より複雑な図面構成での再検証です。Grounding DINOは取得・実行の問題から、
**図面記号への適応不足**という精度上の問題へ切り分けられました。
