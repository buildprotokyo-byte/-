# 抜き取り検査を本番の処理に組み込む設計

2026-09-22。おーちゃんの指示「抜き取り検査を本番の処理に組み込む。ただし、まず設計を書くこと」に対する設計。
設計を先に送り、おーちゃんの承認(階層1の初期値 10%・最小3件)を受けて**実装済み**。
実装との差は本文に反映してある(6節に実際に入れたものを書いた)。

**抜き取り検査は「確定」とした行が本当に正しいかを検査する仕組みである**
(おーちゃんの定義、2026-09-22)。だから母集団は階層1(自動確定)と階層2(仮採用)だけで、
階層3(人が必ず見る)は入れない。

読んだコード: `intake/drawing_intake.py`(main `de395e9`)、`arbitration/inference_orchestrator.py`、
`arbitration/axis_quality_firewall.py`、`arbitration/provisional_audit.py`、`intake/case_answers.py`、
`estimating/from_intake.py`。上位の原則は `docs/principles/start_kit.md`、
現状との差は `docs/principles/principle_conformance_review.md`。

---

## 0. 先に、この設計で数字が良くならないことを書いておく

**組み込んでも、当面は抜き取られる対象が0件のままである。** 理由は監査の側ではなく判定の側にある。

`intake/drawing_intake.py` の docstring が既に書いているとおり、図面 PDF は1ファイルで1つのデータ源なので、
そこから何種類の手法で読んでも独立したデータ源の数は 1 にしかならない。階層1(自動確定)は独立した強いデータ源が
2つ以上要る。加えてこの経路の手法はどれも実測校正を通っていないので(`arbitration/method_policies.py`)、
そもそもハード制約に入らない。**結果として、いまの入口を通した対象は全部が階層3(人の確認)になる。**

抜き取り検査の母集団は階層1と階層2だけなので、**母集団は 0 件**である。
`IntakeResult.confirmed_targets` が「2026-09-22 時点では常に空になる」と書いてあるのと同じ事実である。

したがってこの組み込みが今すぐ生むものは、**検出率の改善ではなく、次の2つ**である。

1. 母集団が0件であることが**記録に残る**。「監査して全部当たった」と区別できる形で残る
   (`AuditReport.status == "no_population"`)。いま同じ0件は、記録がないので「監査していない」と
   区別がつかない。
2. 階層1・階層2が出るようになった瞬間に、**追加の実装なしで検査が走り始める。**

数字が動くのは、独立した第2のデータ源(建具表の文字と図形、あるいは別ファイル)が揃って階層が上がってからである。
**そのときまでこの検査は0件を報告し続ける。それが正しい出力である。**

## 1. どこで走らせるか

### 1-1. 結論

**`intake/drawing_intake.py` の `read_drawing()` の末尾、`decisions` が出そろってから `IntakeResult` を作るまでの間。**

```
read_drawing()
  ├ _extract()                  ページを分け、図面から読む
  ├ _apply_area_basis()         人の回答が要る数量を保留する
  ├ _decide() × 対象の数        ← 1対象ずつ。ここでは母集団が作れない
  ├ ★ 抜き取り(この設計で足す)   ← decisions が全部そろう唯一の場所
  └ IntakeResult(...)
```

### 1-2. なぜここか(他の候補を落とした理由)

| 候補 | 落とした理由 |
|---|---|
| `InferenceOrchestrator.process()` の中 | 1回の呼び出し = 1対象なので、母集団が常に1件になる。抽出率30%も最小5件も意味を失い、全件監査と同じになる |
| `AxisQualityFirewall.assess()` の中 | 同上。さらに判定そのものに監査を混ぜると、監査が判定を変えていないことを示せなくなる |
| `_decide()` の中 | 同上(対象1件ずつ) |
| `estimating/` 側 | 当てはめの層は階層の情報を `IntakeResult.decisions` から引いているだけで、判定の根拠(`AxisEvidence`)を持たない。カテゴリ(手法ID)が取れないので、不一致が出たときの拡大監査ができない |

**「1案件ぶんの判定が全部そろう場所」は `read_drawing()` の末尾しかない。**

### 1-3. 案件をまたぐ監査は、この設計では実装しない(記録の形だけ決める)

v8 10章18項の結論は「抽出率を上げるより母集団を大きくするほうが検出力に効く」である。
1案件の階層1・階層2は10〜20件の規模なので、**1案件だけで監査しても誤り1件を半分以上見逃す。**

ただし案件をまたぐ監査は「いつ走らせるか」「誰が結果を受け取るか」が運用の話になり、いまは決められない。
**この設計では、案件ごとの監査だけを実装し、案件横断で積み上げられる形の記録を残すところまでにする**(4節)。

## 2. 何を母集団にするか

### 2-1. 対象

`read_drawing()` が作った `decisions`(`TargetDecision`)のうち、

- `action == "auto_confirm"`(階層1)
- `action == "provisional_audit"`(階層2)

の対象。**階層3は入れない。** 人が必ず見るので抜き取る意味が無く、入れると的中率が薄まるだけである
(`AUDITABLE_TIERS == (1, 2)`)。

### 2-2. 階層は混ぜず、階層ごとに数える

PR #10 で入れた `run_tiered_audit()` をそのまま使う。**階層1と階層2の母集団・抽出件数・的中率・検出力は
別々に数える。** 1つの的中率にまとめると、件数の多い階層が少ない階層の誤りを薄めて隠す。

### 2-3. 抽出率

| 階層 | 抽出率 | 最小件数 | 根拠 |
|---|---|---|---|
| 階層1(自動確定) | **10%** | **3件** | **実測の裏づけは無い。** 下記 |
| 階層2(仮採用) | 30% | 5件 | 既存の値。変えない |

**階層1の 10%・最小3件には実測の裏づけが無い。** 根拠にしたのは次の1点だけである。

> 階層1は人が一度も見ないまま通る階層なので、完全に無検査にはしない。

階層1は独立した強い軸2つの一致と中心値の検査を通っているので、誤りの事前確率は階層2より低い**はず**である。
一方で、見逃したときの重さは階層2より大きい(階層2は抜き取られれば人が見る)。
**どちらの効きが大きいかは測っていない。** 10% は「階層2の30%より軽く、0ではない」という以上の意味を持たない。

**後で測って調整する前提で入れる。** 測り方は7節に書く。

### 2-4. 対象の名前

いまの入口が作る対象名は `建具数量::<建具番号>`、`開き戸::ページN`、`施工対象床面積` などである
(`intake/drawing_intake.py` の `TARGET_*`)。監査の対象名はこれをそのまま使う。
**人が見るときは対象名だけでは何のことか分からない**ので、記録には根拠(`provenance`: ページ番号・座標・
元の文字列)を必ず添える(4節)。

### 2-5. カテゴリ(拡大監査の単位)

既定は手法 ID(`method_id`)。系統誤差は手法から出るため。
この経路の手法は `METHOD_DOOR_ARC` / `METHOD_TEXT_SCALE` / `METHOD_TEXT_AREA` / 建具表の読みなので、
**「開き戸の円弧の拾い方が系統的に間違っていた」ような誤りが、1件見つかれば同じ手法の全件に広がる。**
これは v8 4-3節ルール3。**広げるのは監査の対象としてであって、自動で階層を下げたりはしない。**

## 3. 正解をどこから引くか(記入者が決まるまで保留)

### 3-1. 抽出と照合を、経路として分ける

いまの `run_provisional_audit()` は「抽出」と「正解との照合」を1つの関数でやっている。
**本番の入口に組み込むときは、これを2つに割る。**

```
plan_tiered_audit(candidates, policies, seed) -> TieredAuditPlan   # 抽出だけ。正解に触らない
score_audit_plan(plan, ground_truth)          -> TieredAuditReport # 照合だけ
run_tiered_audit(...)                                             # 上2つの合成(既存の呼び出し口)
```

理由は2つある。

1. **`read_drawing()` は正解データを一切読まない、という既存の約束を壊さないため。**
   `read_drawing()` の docstring に「正解データ(見積明細・ゴールデン)はここでは一切読まない」と書いてある。
   入口が呼ぶのは `plan_tiered_audit()` までにする。
2. **`renovation-golden-001.json` の usage_policy と同じ形にするため。**
   「抽出と採点の経路を分ける」は既に約束済みで、`benchmarks/run_golden_eval.py` は
   `extract_from_drawing()` が PDF しか引数に取らない形でそれを担保している。同じ作りにする。

### 3-2. 正解の引き口

```python
class GroundTruthSource(Protocol):
    def lookup(self, case_id: str, target: str) -> int | None: ...
```

**既定の実装は「常に `None` を返す」もの**(`NoGroundTruth`)。記入者が決まったら差し替える。
`None` を返してよいことは既存の `run_provisional_audit()` の約束そのままである。

### 3-3. 正解が引けない間、どう振る舞うか

ここが今いちばん大事なところである。

- `hit_rate` は **`None`**。1.0 を返さない。正解が無い対象を「一致」と数えると的中率が常に100%になる。
- `status` は **`awaiting_human`**。「抽出はしたが1件も照合できていない」。
  母集団0件(`no_population`)とも、「監査して全部当たった」とも区別される。
- 報告の文面は「照合できていない。人の確認待ちであり、**的中率は出せない(全件一致ではない)**」。

そして、**正解が無い間の監査の出力は「的中率」ではない。「人が確かめるべき対象の一覧」である。**

抜き取られた対象は、対象名・採用された範囲・ページ番号・座標・読んだ元の文字列を添えて出す。
人はその一覧を見て、図面と突き合わせる(あるいは現地で確かめる)。
**これは `docs/principles/start_kit.md` 原則5の「現地確認が必要」そのものであり、おーちゃんの回答8の
「システムが根拠を付けて提案し、人が確認する形」に当たる。**

つまり、正解の記入者が決まるまでの間も、この検査は遊んでいない。**人が確かめた結果がそのまま正解になる**ので、
正解データは「別途どこかで作るもの」ではなく、**この一覧に人が答えることで溜まっていく。**
記入者が決まったときに、この一覧が記入の入口になる。

### 3-4. 人の入力を無条件の正解にしない

原則5に「人が与えた情報も、図面の中身と突き合わせて矛盾を探す。人の入力を無条件の正解にせず、
単一の根拠では自動確定させない」とある。監査の照合結果も例外ではない。

- 人が「一致」と答えたことをもって、その対象を階層1に上げたりはしない。**監査は階層を変えない。**
- 人が「不一致」と答えたときも、その1件だけで手法を止めたりはしない。同じカテゴリの全件を
  **監査の対象として挙げる**(2-5節)。止めるかどうかは人が決める。

## 4. 結果をどこに残すか

### 4-1. 保管場所は `AnswerStore` と同じ形

**案件の情報なので、リポジトリには置かない。** `intake/case_answers.py` の `AnswerStore` と同じ約束にする。

- `IntakeConfig` に `audit_log_path: Path | None = None` を足す。**既定値は持たせない。**
- `None` なら保存しない(その実行の中だけ有効)。
- 形式は JSON の追記。

### 4-2. 1回の監査で残すもの

```
{
  "case_id":               案件
  "recorded_at":           いつ
  "source_fingerprint":    図面の中身の sha256   ← 同じ図面かどうかの判定に要る
  "start_kit_fingerprint": 人が入れた前提の指紋   ← 前提が変われば別の監査になる
  "seed":                  乱数シード
  "tiers": {
    "1": {population, sample, rate, minimum, status, sampled: [...]},
    "2": {...}
  }
}
```

`sampled` の1件は、対象名・採用された範囲・単位・手法ID・**根拠**(ページ番号・座標・元の文字列)。
根拠を落とすと、人が一覧を見ても何を確かめればいいのか分からない。

**指紋を入れる理由。** 案件をまたいで母集団を積み上げるとき(1-3節)、
「同じ図面の同じ読みに対する監査を二重に数えていないか」を後から判定する必要がある。
ファイル名は匿名化で変わるうえ案件名が入ることがあるので、**中身の sha256 を使う**
(既存の `file_fingerprint()` がそうなっている)。

### 4-3. 乱数シードは案件と図面から決める

`seed = 案件IDと図面の指紋から決まる整数`(例: sha256 の先頭バイト列)。時刻や実行回数を混ぜない。

**理由: 同じ図面をもう一度読んだときに、人に見せる一覧が入れ替わってはいけない。**
人が既に3件を確かめている最中に再実行して別の3件が出てきたら、確かめた分が捨てられる。

ただし**母集団そのものが変われば抽出も変わる**(新しい建具が読めるようになった、など)。
これは避けられないので、記録に母集団の件数を残して、変わったことが分かるようにする。

### 4-4. `IntakeResult` にも載せる

`IntakeResult` に `audit_plan: TieredAuditPlan | None = None` を足し、`summary()` に1行足す。

```
抜き取り検査: 階層1 母集団0件 / 階層2 母集団0件(監査対象なし)
```

母集団が0件のときに**「監査対象なし」と書く**のが要点である。「0件監査、全部一致」と書かない。

## 5. 誰がいつ見るか

### 5-1. 「質問」と「確かめてほしい一覧」を混ぜない

いまの入口には既に `pending_questions`(人に聞く質問)がある。**監査の一覧はこれとは別に持つ。**

| | 性質 | 答えないとどうなるか |
|---|---|---|
| `pending_questions` | 答えないと数量が出ない(面積の基準など) | **数量が出ない** |
| 監査の一覧 | 数量は出ているが、人に確かめてほしい | 数量は出たまま。確かめられていないことが記録に残る |

混ぜると、「答えないと止まる質問」と「答えなくても進む確認」が人の画面で同じに見える。
原則5末尾の「人の負担は、質問の数ではなく、操作の回数と時間で測る」を考えると、
**止まる質問は少なく、確認は後回しにできる形にしておく**必要がある。

### 5-2. 原則5の4区分のどこに入るか

原則5は数量を「確定／推論に基づく／仮説に基づく／現地確認が必要」に区別して出せと言っている。
`docs/principles/principle_conformance_review.md` 12番のとおり、**この4区分はまだ実装されていない**
(いまは `is_confirmed` の真偽値だけ)。

この設計では、**監査の出力が4区分のどこに入るかだけ決めておく。4区分そのものの実装はこの作業の範囲外**とする。

- 抜き取られて、まだ人が確かめていない対象 → **「現地確認が必要」**
- 抜き取られて、人が一致と答えた対象 → 区分は変わらない(**監査は階層を変えない**)
- 抜き取られて、人が不一致と答えた対象 → その対象と同じカテゴリの全件を「現地確認が必要」に寄せる**提案**を出す。
  実際に寄せるかどうかは人が決める

### 5-3. いつ見るか

案件ごとの監査は `read_drawing()` のたびに走るが、**一覧が変わらない限り人に再通知しない**
(4-3節のシードの固定がこれを可能にする)。

## 6. 実装(2026-09-22 完了)

段取りどおりに入れた。**各段階とも、再現する失敗テストを先に書いた。**

1. `arbitration/provisional_audit.py` に `plan_tiered_audit()` / `score_audit_plan()` を
   分けて足した。既存の `run_tiered_audit()` は2つの合成として残っていて、
   呼び出し口も結果も変わっていない(`tests/test_audit_plan_split.py`)。
   1階層ぶんは `plan_provisional_audit()` / `score_tier_plan()`
2. `GroundTruthSource` プロトコルと `NoGroundTruth`(常に `None` を返す既定)
3. `IntakeConfig.audit_log_path` と `append_audit_record()`(`AnswerStore` と同じ形)
4. `read_drawing()` の末尾に `_audit_candidates()` → `plan_tiered_audit()` を差し込み、
   `IntakeResult.audit_plan` に載せた。シードは `audit_seed(case_id, 図面の指紋)`
5. `IntakeResult.audit_line()` を `summary()` に足した

**設計に無かったが、実装して分かって足したもの: `provenance["page_numbers"]`。**
根拠の形は読みの種類ごとに違う(面積は `occurrences` の中に、開き戸は直下に
`page_number` を持つ)。**形の違いを人に探させない**ために、`_audit_candidates()` が
どのページを見ればいいのかを1つの欄にまとめて入れる。

**壊し試験で10通りを確かめた**(いずれもテストが落ちる):
入口に正解の引き口を渡せるようにする / 母集団0件を「全件一致」と書く /
階層3も母集団に入れる / シードに実行ごとの値を混ぜる / 母集団0件の回を記録に残さない /
階層1の抽出率を階層2と同じにする / 根拠を落として対象名だけ渡す /
抽出の関数に正解を渡せるようにする / 正解が無いのに的中率を出す /
階層1の既定値を部品側に入れる。

テストは `tests/test_audit_plan_split.py`(14件)と `tests/test_intake_audit.py`(14件)。
**階層1・階層2が出たときの振る舞いは、仲裁層の代役を差し込んで固定した。**
いまの本番経路では全対象が階層3になるので(0節)、実物では試せないためである。

## 7. 階層1の10%を、後でどう測って調整するか

**Claude Code では測らない**(重い試行の繰り返しになるため)。Codex 側で測る項目として書き出す。

| 測るもの | 測り方 | 判定 |
|---|---|---|
| 階層1の誤り率 | 階層1として確定した対象のうち、人が不一致と答えた割合 | 階層2の誤り率と比べる |
| 検出力 | `detection_probability()` に実際の母集団と抽出件数を入れる | 誤り1件を50%以上で捕まえられるか |
| 人の負担 | 抜き取られた件数 × 1件あたりの確認時間 | 操作回数と時間で測る(原則5末尾) |

**採否の判定基準は、測る前に宣言してコミットする**(おーちゃんのルール)。
たとえば「階層1の誤り率が階層2の半分未満なら10%を維持、同等以上なら30%に上げる」のような形。
**具体的な基準値は、母集団が0でなくなってから決める**(いま決めても当てはめる数字が無い)。

## 8. この設計で解決しないこと

正直に並べておく。

1. **当面は母集団0件なので、検出力は0である**(0節)。これは監査の問題ではなく、
   独立した第2のデータ源が無いことの問題である。
2. **1案件だけでは検出力が足りない。** 母集団10〜20件で誤り1件を捕まえる確率は30〜50%。
   案件横断の積み上げが要るが、この設計では記録の形を決めるところまで(1-3節)。
3. **正解の記入者が決まっていない。** 決まるまで的中率は出ない。出ないことを `None` と
   `awaiting_human` で表す(3-3節)。
4. **階層1の10%に実測の裏づけが無い**(2-3節)。
5. **原則5の4区分そのものは、この作業では実装していない**(5-2節)。
   4区分は別スレッドが `estimating/basis.py`(PR #29)で入れており、
   `QuantityItem.site_survey_reason` が空でなければ「現地確認が必要」になる形になっている。
   **抜き取った一覧をその `site_survey_reason` に流し込む配線は、まだ無い。**
   流すには `estimating/from_intake.py` が `IntakeResult.audit_plan` を読む必要があり、

6. **監査は階層を変えない。** 不一致が見つかっても、自動で階層を下げたりはしない(3-4節)。

   (人1人の確認も単一の根拠である)。
