## ルール

1. 記録を信じず、コードを読んでから着手する(「実装済み」と書かれていても、本番の経路から呼ばれているか確認する)
2. 修正は、再現する失敗テストを先に書いてから行う
3. 単一の指標だけを根拠に自動確定させる変更はしない
4. 実図面・見積明細・そこから作ったデータは、匿名化済みでもリポジトリにコミットしない。テストには合成データを使う
5. 設計に関わる作業は Opus 5、作業だけのスレッド(テスト実行、定型の修正)は Sonnet 5 を明示して起動する
6. 計測の待ち時間には、次の作業を進める。クラウドでの並列化は速くならないことがあるので、それを前提にしない
7. 各作業の報告は「スレッド名、使用したコミット、完了したこと、残っていること」の形で status.md に残す

## マージしてよいもの、してはいけないもの

マージしてよい(全件テストと CI が通り、その作業の完了条件を満たした場合)：

- 機能を追加するだけで、既存の判定のしかた(ファイアウォールの階層条件、許容差、群合計制約の判定、質問の選び方)を変えない変更

マージせず、PR のまま私の確認を待つもの：

- 既存の判定のしかたを変える変更(群合計制約の修正など)
- 判定の基準値(許容差、抜き取り率の既定値など)を変える変更
- 段階0.5の既定を A2 に戻すこと

絶対にしないこと：

- main への force push、ブランチの削除、テストを飛ばす・弱める変更、CI の無効化
- 実図面・見積明細のコミット

## 作業キュー(上から順に。止まったら次へ)

1. 本番の入口(最小構成)：すでに依頼済みの内容のとおり。PDF の入口、ページ種別判定、縮尺・面積・開き戸の接続、根拠付きの証拠として InferenceOrchestrator へ渡す、面積の選択は案件ごとに1回だけ質問して使い回す、合成ベクター PDF での通しテスト。完了条件：通しテストと全件テストと CI が通る → マージしてよい
2. 図面の文字を位置付きで読み、表として構造化する：建具表(建具番号、種別、幅、高さ、数量)と内装仕上表(部屋名、部位、仕上)。1の入口に証拠として接続する。テスト用の表入り PDF は合成で作る。完了条件：合成 PDF で表が正しく復元されるテスト、全件テスト、CI → マージしてよい
3. 抜き取り監査を階層1にも広げる：階層1と階層2の抜き取り率を別々に設定できるようにし、監査の記録に階層を残す。既定の抜き取り率の値は今の階層2の値を変えず、階層1の既定値は PR 本文で提案するだけにする。完了条件：既存と新規のテスト、CI → 既定値に触れない範囲ならマージしてよい
4. 群合計制約の修正(別スレッドで実装中)：実装が終わったら PR のまま待つ。効果の測定は私が戻ってから Codex 側で行う
5. 質問選定の高速化：設計案とテストまで(実装しない)。条件は、選ばれる質問の順番が今のエンジンと完全に同じであること、決定性を壊さないこと、暫定目標は1,000要素で1問あたり P95 5秒以内・全体10分以内。4と同じファイルを触る場合は、重なる箇所を明記する

## ルール追加(2026-09-24 14:26 おーちゃんが追加、K-30)

**これまでの指示の出し方が間違っていた、と おーちゃんから訂正があった。**
困ったところを一つずつ塞ぐ指示を出してきたが、**この形では教えた決まりしか使われず、

**構えの全文は `docs/reading_stance.md`。**要点だけ:

1. **図面は文書である。決まりを知らなければ読めない。**
   **汎用の画像処理・文字処理を図面にそのまま当ててはいけない。**
2. **読む前に、必ず「何の知識が要るか」を自分で判断する。これが一番大事な決まり。**
   どの分野の知識が要るか / どういう決まりに従って書かれているはずか /
   その決まりはどこに書かれているか。**何を使うかはこちらが判断する。**
3. **前提として置いてよい知識**(既に持っているはずの知識。使っていなかっただけ):
   JIS A 0150・Z 8311・Z 8312・Z 8317・C 0303、法令、
   一級建築士・一級建築施工管理技士・第一種電気工事士・一級電気工事施工管理技士・
   一級管工事施工管理技士が前提とする実務知識、設計者の意図。
4. **決まりを固定しない。**JIS は既定値。案件の凡例が違えばそちらを優先。
   **どちらの根拠で読んだかを必ず記録する。**
5. **読めなかったときは 3 つに分けて書く。混ぜない。**
