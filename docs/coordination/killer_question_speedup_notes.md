## 時間の使い道（コードを読んで特定した構造）

1. `ConsistencySolver.solve()` は、変数1個ごとに `_tighten()` を呼び、その中で
   **下限用と上限用に `z3.Optimize` を2つ新規に組み立て直す**（`consistency_solver.py`
   の `_tighten` / `_optimize`）。組み立てのたびに全制約を `opt.add` する。
   → solve() 1回あたり `Optimize` を 2N 個、`opt.add` を 2N×M 回（M は制約数）。
2. `KillerQuestionEngine.score_candidate()` は、**候補値1つにつき
   `solver.clone().solve()` を1回**呼ぶ（最大 256 候補）。
3. `next_question()` は、**未確定の変数すべてについて** `score_candidate()` を呼ぶ。

掛け合わせると、質問1問あたり `Optimize` の組み立てが
**（未確定数）×（候補数）×2×（変数数）** 回。1,000要素では現実的な時間に収まらない。

なお `score_candidate()` は `graph.connected_component(variable)` で下流を取っているのに、
**仮確定して解くときは毎回グラフ全体を解き直している**。まとまり（連結成分）の外の変数は
仮確定の影響を受けないので、ここが最初に削れるところ。

## 決定性の衝突は、思っていたより狭い範囲に閉じ込められる（コードで確認）

「まとまりごとに solver を使い回すと `03b8eac` の決定性修正とぶつかる」という
最初の警告は、**範囲を切り分ければ回避できる**見込みが立った。根拠は2つ。

1. **候補評価の経路は `unsat_core()` を一度も読んでいない。**
   `score_candidate()` は仮確定した結果について `is_consistent` しか見ず、
   矛盾したら削減量0を足すだけ。`conflicting_constraints` を実際に読むのは
   `inference_orchestrator` / `axis_quality_firewall` / `escalation_router` /
   `constraint_exhaustive_search` と、`_finish()` が返す最終結果だけで、
   **最終結果は本物の solver の `solve()` から来る**（仮説の solver ではない）。
   → **速くするのは候補評価の経路だけにし、本物の `solve()` は今のまま
   「毎回新しいコンテキスト」を維持すれば、核の非決定性には触れない。**
2. **仮確定の結果として読んでいる値は、数学的に一意である。**
   読んでいるのは ①sat か unsat か ②各変数の最小値・最大値（`_tighten`）だけ。
   すべての強い変数には `range::` 制約で上下限が付くので領域は有界で、
   有界な整数線形領域上の最小値・最大値は**答えが1つしかない**。
   一方 `unsat_core()` は「矛盾の説明」として正しいものが複数あり、
   どれを返すかは内部状態で変わる。**壊れたのは後者だけだった。**

→ 設計上の規則として書くべき文: **「コンテキストや solver を使い回してよいのは、
答えが一意である問い（sat/unsat、有界な整数変数の最小値・最大値）に限る。
`unsat_core()` を読む経路では、これまでどおり毎回新しいコンテキストで解く。」**
この規則を破らない限り、質問の列は入力だけで決まる。

## 飛ばしてよいと分かったもの（完全に等価）

- **下流のうち、いま幅が0の変数は計算しなくてよい。** 削減量は
  `max(0, 元の幅 - 新しい幅)` で、元の幅が0なら新しい幅が何であっても0。
  質問が進むほど幅0の変数が増えるので、後半ほど効く。
- **`_tighten` は変数ごとに `Optimize` を2つ新規に作り、そのたびに全制約を入れ直す。**
  1つの `Optimize` に制約を1回入れ、目的ごとに `push`/`pop` すれば、
  `opt.add` は 2×変数数×制約数 から 制約数 に落ちる。答えは一意なので結果は変わらない。

## 落とし穴（設計案に必ず書く）

- **変数を1つも参照しない制約**（`add_relation("c", 1, "==", 2)` のような定数だけの式）は
  どのまとまりにも属さない。まとまり限定でこれを落とすと、**本来 unsat の問題が
  sat に見える。** 全まとまりに入れるか、別枠で必ず評価すること。
- **浮動小数の同点判定。** `score == max_score` で同点を見ているので、
  足し算の順番が変わるとビットが変わり、同点崩しの結果が変わりうる。
  高速化は**計算の順番を変えないこと**を条件にする。

## 別スレッド（`claude/group-total-masking`）との重なり — 具体的に

同じファイルを触る箇所が3つある。

1. **`ConsistencySolver.solve()` に `use_detection_ranges` 引数が増える。**
   確定用と検出用で変数の定義域が変わるので、**候補評価の結果を使い回す案（段階2）の
   キーに、このフラグを必ず含めること。** 含め忘れると別物の結果を再利用する。
2. **`ConsistencySolver.remove_constraint()` が増える。** `group_total.py` が
   「その制約が無かったらどうなるか」を見るために制約を外した複製を解く。
   **制約が外れるとまとまりの形も変わる**ので、依存関係グラフを質問間で使い回す案は、
   制約の集合が変わっていないことを確かめてからにすること。
3. `killer_question/firewall_bridge.py` が両方で変更対象になりうる。今回の設計案は
   このファイルを変えない方針。

**あわせて、この作業と無関係だが見つけたこと:** `claude/group-total-masking` は
`.github/workflows/pytest.yml` が入る前の main から切られているため、**そのまま
main へ入れると CI の設定ファイルが消える。** 取り込み直してから出すよう、
あちらのスレッドに伝えたほうがよい。
