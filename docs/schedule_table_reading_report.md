# 建具表・内装仕上表を、位置つきで読んで表として構造化する(2026-09-22)

対象: `axes/image_axis/pdf_tables.py`、`axes/image_axis/schedule_tables.py`、
`intake/drawing_intake.py` への接続。
分岐元: main `c2ad7dc`(キュー1「本番の入口」のマージコミット)。

---

## 1. 着手前にコードで確かめたこと

記録の「実装済み」は信じず、部品が実際に何を返すかを読んでから始めた。

| 確かめたこと | 実際 |
|---|---|
| 図面の文字を**位置つき**で読む経路があるか | **無い。** `pdf_pages.rasterize()` は `page.get_text("text")`(平文)を `PdfPage.text` に載せるだけで、座標は落ちている。 |
| 表を読む部品があるか | **無い。** `find_area_labels()` が `page.get_text("text")` を正規表現で舐め、数値の位置だけ `page.search_for()` で後追いしている。行と列の対応は最初から存在しない。 |
| `find_area_labels()` を流用できるか | できない。拾えるのは `専有延床面積` と `施工床面積` の 2 ラベルに固定されている(`_AREA_RE`)。 |
| 罫線を自前で探す実装があるか | 無い。`pdf_vector_symbols` が `page.get_drawings()` を使うが、見ているのはベジェ曲線だけで直線(`"l"`)は明示的に無視している。 |

**平文にした時点で建具表は読めなくなる。** 建具表の `1650` という数値の意味は、
同じ行の別の列(建具番号)と同じ列の見出し(幅)の**両方**で決まるからである。
面積の記載のように「ラベルと数値が隣り合う」だけの記載とは、必要な情報が違う。

## 2. 作ったもの

### 2-1. `axes/image_axis/pdf_tables.py` … 升目を位置つきで取り出す層

罫線の検出そのものは PyMuPDF の `Page.find_tables()` に任せた。自前の罫線探索を
書かなかった理由は 2 つある。(a) 罫線の途切れ・二重線・セル内の塗りといった
実図面の癖に対する調整が既に入っている。(b) このリポジトリで新しく書いた検出器が
実図面で**的中 0 件**だった前例がある(ラスターのテンプレート照合、
`docs/real_drawing_eval_report.md` 4 節)。

この層が足しているのは次の 2 点である。

- **縦に結合されたセルと、罫線はあるが空のセルを区別する。**
  PyMuPDF は前者を `None`、後者を `""` で返す。内装仕上表は室名を縦に結合して
  書くのが普通なので、ここを潰すと室名が消える。逆に、単に記入が無いセルを
  「上の続き」と扱うと、書かれていない仕上げを図面が指定したことになる。
  結合されたセルの座標は、**文字が書いてある親セルの座標**にしてある
  (その行の座標を返すと、人が図面を見に行ったときに空白を指すことになる)。
- **表のすぐ上にある行を見出し(キャプション)として拾う。** 建具表と内装仕上表は
  列見出しだけでは見分けがつかない図面がある。表の上端から 24pt 以内、かつ表の
  横幅と重なる行だけを見出しとする。**この 24pt は実測で校正した値ではない。**
  離れた文字を見出しにしてしまうより、見出しが取れないほうが安全な向きに倒した。

### 2-2. `axes/image_axis/schedule_tables.py` … 升目に意味を与える層

- **列の役割は見出しの文字から決める。列の順番は決め打ちしない。**
  建具表の列の並びは事務所ごとに違う。`建具番号 / 種別 / 幅 / 高さ / 数量` の
  それぞれに書き方の候補(`記号`・`員数`・`巾` など)を登録してある。
  **網羅はしていない。** 知らない書き方は「その列が無い」として扱われるので、
  誤って別の列に割り当たるより安全な向きに倒れる。
- 建具番号の列があるだけでは建具表と認めない(`DOOR_MIN_SUPPORTING_COLUMNS = 2`)。
  図面には凡例表・面積表・記事欄など、罫線で組まれた別の表がいくらでもある。
- 内装仕上表は 2 通りの書き方に対応した。`室名 / 部位 / 仕上` が列になっている形
  (`layout="long"`)と、**部位そのものが列になっている形**(`室名 / 床 / 壁 / 天井`、
  `layout="wide"`)である。後者のほうが図面では多い。どちらも
  「室名・部位・仕上」の 3 つ組に開いて返す。
- すべての値に**ページ番号・座標・図面に印字された元の文字列**が付く
  (`ScheduleCell`)。正規化した文字列は照合にしか使わず、根拠として残すのは
  印字されたままの文字である。

### 2-3. 本番の入口への接続

- 建具番号ごとの数量を `建具数量::<建具番号>`(単位 `箇所`)として仲裁層へ渡す。
  手法は `pdf_table_door_schedule` で、`arbitration/method_policies.py` に
  **未校正**として登録した。
- **開き戸の円弧から数えた `開き戸::ページN` とは別の対象にしてある。**
  同じページに建具表と平面図があっても、数が合うかどうかを入口で判定しない。
  突き合わせは仲裁層の仕事で、渡す前に片方を捨てたり合わせたりしない。
- **ページをまたいで足さない。** 同じ建具番号が別のページで違う数量になっていたら、
  どちらかを選ばずレンジにする(既存と新設の建具表が両方あると、足せば二重に数える)。
- 内装仕上表は **1 件も数量にしない。** 室の輪郭を取る実装がリポジトリに無いので、
  仕上げから面積は出せない。読んだ対応は `IntakeResult.finish_schedule_rows` に
  構造として残すだけである。

## 3. この作業の意味(拾えるようになったこと)

**引戸・折戸は円弧を描かないので `find_door_arcs()` では原理的に拾えない。**
P011 の新設建具は全部引戸か折戸で、だから図形からの検出は 0 件だった。
建具表の**種別の文字**が読めれば、この建具は文字から拾える。

`IntakeResult.arc_blind_doors()` が、建具表に「引戸・折戸など」と書かれていた
建具番号を返す。**種別が読めなかった建具はここに入れない**(「拾えている」とも
「拾えていない」とも言えないため。知らない種別を「図形で拾える」に倒すと、
見落としがその前提の下に隠れる)。

内装仕上表のほうは、**いま数量を増やさない。** 面積 25 項目のうち 22 項目が
「室の輪郭を取る実装が無い」ところで止まっており、そこは動いていない。
室名と仕上げの対応は、輪郭が取れるようになったときに「その面積が何の仕上げの
数量なのか」を決めるための材料である。

## 4. 確定する数量は、これでも 0 件のままである

**この作業は、それ単独で自動確定する数量を 1 件も増やさない。**

階層1(自動確定)は独立した強いデータ源が 2 つ以上要り、独立性は
`source_fingerprint`(ファイル内容の sha256)で判定される。**1 つの図面 PDF から
何種類の手法で読んでも独立数は 1 にしかならない。** 加えて新しい 2 手法は
どちらも未校正なので `is_hard_eligible` が False のままである。

`test_nothing_is_auto_confirmed_even_with_the_schedules` がこれを固定している。
どちらかの手法を `calibrated=True` にしたら、このテストは必ず落ちる。

## 5. 拾えないもの(そのまま記録する)

- **罫線で組まれていない表は拾えない。** 文字の並びだけで組まれた表は 0 個になる。
  座標の近さだけで列を作ると、図面の中の寸法文字の並びを表と取り違える。
- **スキャンしたページからは何も読めない。** P011 は 34 ページ全部がスキャンで
  埋め込み文字 0 文字なので、**この案件の実図面では建具表も内装仕上表も
  1 件も読めない。** この作業が効くのは CAD 由来の PDF が手に入る案件である。
- **ページをまたいで続く 1 つの表は、別々の表として読まれる。** 2 ページ目に
  列見出しが無ければ、その続きは表として認識されない(見出しが無いため)。
- **単位が表に書かれていない寸法は mm に直さない。** 住宅の建具表の `1650` は
  まず mm だが、「たいてい当たる推測で単位を埋める」ことが 2026-09-21 に直した
  単位の取り違え(`docs/top_priority_unit_safety_defect.md`)と同じ形である。
  印字された文字列(`width_text`)だけを残し、`width_mm` は None にして理由を書く。
  読めるのは列見出しの括弧(`幅(mm)`)か、キャプションの `単位:mm` の表記のときだけ。
- **建具表に載っていない建具は拾えない。** 表は工事対象の建具だけを載せることがある。
- **合成の表でしか確かめていない。** 実図面での誤り率は未知である(6 節)。

## 6. Codex 側で測るべき項目

担当は実装と全件テストまでなので、ここでは測っていない。

1. **`pdf_table_door_schedule` の校正。** CAD 由来の実図面の建具表を複数案件集め、
   ①升目の取り違え(罫線の途切れ・セル内改行・続き表)の率 ②建具表に載っていない
   建具の割合 を測る。この 2 つが出るまで `calibrated=True` にしない。
2. **見出しの候補の網羅度。** 登録した書き方(`記号`・`員数`・`巾` など)で実図面の
   建具表の何割が読めるか。読めなかった見出しを集めて候補に足す。
3. **キャプションの 24pt という閾値。** 実図面で、見出しを取り逃がす率と
   無関係な文字を見出しにしてしまう率の両方を測る。
4. **`layout="wide"` の内装仕上表の割合。** long と wide のどちらが実際に多いか。
5. **34 ページの実行時間。** `find_tables()` はページごとに罫線を探すので、
   入口全体の時間が変わる。キュー1 の計測項目と一緒に測るとよい。

## 7. 壊し試験(テストが本当に検出するかの実測)

わざと壊して、テストが落ちることを確かめた。`__pycache__` を消し
`PYTHONDONTWRITEBYTECODE=1` を付けて実行している(バイト数が変わらない壊し方だと
古いバイトコードが計測を汚す)。

| 壊し方 | 結果 |
|---|---|
| 結合セルを「ただの空セル」として扱う | 3 件が落ちた |
| キャプションの距離の制限を外す | 1 件が落ちた |
| 単位が書かれていない寸法を mm と決め打ちする | 1 件が落ちた |
| 建具番号の列だけで建具表と認める | 1 件が落ちた |
| 読めない数量を 0 で埋める | 2 件が落ちた |
| 知らない種別を「円弧で拾える」に倒す | 1 件が落ちた |
| ページをまたいだ数量を足す | 2 件が落ちた |
| 建具表の手法を校正済みとして登録する | 1 件が落ちた |

**最初の実行では 2 つを見逃していた**(「建具番号の列だけで建具表と認める」と
「知らない種別を False に倒す」)。前者はテストの表が 2 列しか無くて閾値の 1 と 2 を
区別できておらず、後者は知らない種別そのものを試していなかった。
どちらもテストを足して検出するようにした。

## 8. 判断待ち

1. **単位が書かれていない寸法の扱い。** いまは `width_mm` を None にしている。
   実図面の建具表は「単位:mm」をシートのどこか(表の外の記事欄)に 1 回だけ書く
   ことが多く、そこまで探せば埋まる。選択肢は
   ①現状のまま(印字された文字列だけを残す)
   ②シート全体から `単位:mm` の表記を探して使う
   ③案件ごとに人へ 1 回だけ聞く(面積の選択と同じ仕組みが既にある)。
   **推奨は③。** ②はどの表に掛かる注記かが図面から決まらず、取り違えると
   1000 倍ずれる。③なら既存の `intake/case_answers.py` に載せられる。
2. **建具表の数量と、平面図の開き戸の検出数が食い違ったときの扱い。**
   いまは別々の対象として出すだけで、突き合わせていない。突き合わせを
   入れるなら、それは仲裁層の判定のしかたを変える変更になる。
