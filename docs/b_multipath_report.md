# トライアルB 多方向からのアプローチ — 結果

実施: 2026-09-23。採否の基準は測る前に `docs/b_multipath_criteria.md` に置いた。
**基準は結果を見てから変えていない。**

実装: `arbitration/multi_path_reconciler.py`
測定: `benchmarks/run_multipath_eval.py` / 数字: `docs/b_multipath_result.json`

## 判定: **採用**

| 基準 | 結果 |
|---|---|
| 合わせた再現 > いちばん良い単独の経路 | **18/18 対 7/18** |
| 誤った一致 | **0 件** |
| 取りこぼした食い違い | **0 件** |
| 負の対照 4 つ | **すべて合格** |
| 3 回の繰り返しで同じ件数か | **同じ(ばらつきなし)** |

## 何を測ったか

合成した 1 つの案件(1 つの PDF・4 ページ + 合成のスタートキット + 合成の見積書式)を、
**互いの出力を見ない 5 つの経路**で解いて、突き合わせた。

| 経路 | 何から読んだか | 単独の再現 | 得意分野 |
|---|---|---|---|
| 下から | 電気設備図の線(繰り返す図形) | 4/18 | 記号を数える行 |
| 横から | 器具表に印字された個数 | 4/18 | 記号を数える行 |
| 別の角度 | 平面図の壁を閉じた室の輪郭 | 7/18 | 形から出す行 |
| 上から | 人の入力(スタートキット) | 2/18 | 人が入れた行 |
| 後ろから | 見積の書式にある行 | 7/18 | 会社のルールの行 |
| **合わせて** | | **18/18** | |

## 読み取れたこと

**1. 経路は重なっていない。** どの単独の経路も 7/18 を超えない。
上がったのは「同じ行を別の言い方で数え直した」からではなく、
**経路ごとに埋まる行の種類が違う**からである。
記号の行は線と表からしか出ず、面積の行は壁からしか出ず、
会社のルールの行はどの図面経路からも出ない。
0 章で「読み方の作戦を変えても埋まらない」とされた 3 種類が、
**別々の経路でしか埋まらない**ことが数字で出た。

**2. 一致はほとんど根拠を強めない。** 一致 5 件のうち、独立したデータ源が
2 つそろったのは **2 件だけ**(埋込コンセントと洋室1の床面積)。
残りの 3 件は、同じ PDF を線からと表から読んだ一致なので、
**独立した証言として数えていない。**
2 件で独立が 2 になったのは、どちらも**人の入力が絡んでいる**からである。
人の入力は図面とは別のデータ源だという見立てが、仕組みとして効いている。

**3. 図面と表の食い違いが表に出る。** 電気設備図に 13 個描いてあるのに
器具表が 12 個と印字している案件では、埋込コンセントが**食い違い**になり、
強める一致が 2 件から 1 件に落ちた。**どちらの値も選んでいない。**
単独の経路ならどちらかの値を黙って出していた場面である。

**4. それでも自動で確定するものは 1 件も無い。** 独立が 2 つそろっても、
どの手法も未校正(`calibrated=False`)なので、この層は階層を決めない。
18 件のうち確定は 0 件のままである。

## 測定のとちゅうで直したこと(記録)

1 回目は、会社のルールの行の正解を手で書いたときに
合成の見積書式の行の名前と違う名前(「仮設水道・電気」「小運搬」「荷上げ」)を
書いてしまい、分母が 16、後ろからの経路の再現が 2/16 になっていた。
**行の名前は書式の側が正であって、正解の側で言い換えてよいものではない。**
名前を書式に合わせて分母を 18 にし、測り直した。
**採否の基準(合わせた再現 > 単独、誤った一致 0、取りこぼした食い違い 0、
負の対照すべて合格)は 1 文字も変えていない。**
1 回目の数字でも、合わせた再現 13/16 対 単独 7/16 で判定は同じだった。

## この測定で分からないこと

- **実案件での成績は測れない。** 実図面 PDF はこの作業環境に無い。
- **合わせた再現 18/18 は作りのうえで当たり前である。** 正解の行を
  「5 つの経路が出しうるものの和」として作ったのだから、和集合が全部埋まるのは
  設計どおりである。**ここで意味があるのは 18/18 ではなく、
  どの単独の経路も 7/18 を超えないこと**のほうである。
- 「上から」と「後ろから」は**合成した入力**である。実際に人が入れた値でも、
  実在の会社の見積書式でもない。
- 経路どうしを見せない決まりは、経路が別々の関数で互いの出力を引数に取らないこと
  で満たしている。**読む側が言語モデルになる場合、この保証は別に要る。**
- 見積の金額は出していない。埋まるのは行と数量までである。
- 表記ゆれは突き合わせの外にある。`item_key` を揃えるのは呼ぶ側の仕事で、
  実案件では「埋込コンセント」と「コンセント(埋込)」が別の鍵になる。
  **ここはまだ何も手当てしていない。**

## 次に効きそうなこと

- **表記ゆれを揃える層**が無いと、実案件では一致がほとんど起きない。
  これは次の周の候補になる。
- 「後ろから」は 7 件すべてが片方にしか無いものとして残った。
  会社のルールの行は**図面からは永遠に出ない**ので、
  ここは A-3 の決着(中身をおーちゃんに確かめる)待ちのままである。
