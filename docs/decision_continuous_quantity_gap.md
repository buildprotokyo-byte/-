# 【判断材料】v8 9.5節「連続量への対応」と実装の食い違い

作成日: 2026年9月21日
状態: **判断待ち。** おーちゃんがどちらを選ぶかを決める。この文書は選択肢と
実測値を並べるだけで、まだ何も変更していない。
関連: `docs/design_v8.md` 9.5節、`docs/top_priority_unit_safety_defect.md` 4-2節

---

## 1. 何が食い違っているのか

v8 9.5節は、トライアル10の結果として次のように書いている。

> - v8の設計は、**離散カウント以外の数量(連続的な長さ・面積、タイプ分類を伴う
>   個数)にも有効**であることが確認された。配管延長のMAPEは1.700%→0%、
>   床面積は1.482%→0.088%、タイプ別個数の正答率は22.2%→100%に改善した
>
> ### 設計への反映
> 1. **連続量における階層1(自動確定)の定義を修正する。** 離散カウントの
>    「完全一致」ではなく、**「許容誤差内での自動採用」**として再定義する。

一方、実装の実測はこうである。

### 1-1. 実運用の入口が、長さ・面積・金額を受け付けない

```
点検8: 連続量(長さ・面積)を入口で表現できるか
  unit=m           → unknown_unit
  unit=メートル      → unknown_unit
  unit=m2          → unknown_unit
  unit=㎡           → unknown_unit
  unit=平方メートル    → unknown_unit
  unit=円           → unknown_unit
```

`UNIT_ALIASES = {"count": "count", "件": "count", "個": "count", "数量": "count"}`
で、**正規形は `count` 1種類しかない。**

### 1-2. 小数を受け付けない

```
点検9: 小数の数量(配管延長 12.5m 等)を表現できるか
  count_range=[12.5, 13.0] → count_must_be_integer
```

### 1-3. 「許容誤差内での自動採用」は、どこにも実装されていない

`tolerance` / `許容誤差` という実装は、`arbitration/`・`killer_question/`・`axes/`
のいずれにも存在しない(検索結果0件)。階層1の条件は現在も
「独立した強い軸が2つ以上、レンジの積集合が空でない」という離散の判定のままである。

### 1-4. そもそも、トライアル10の実装はこのリポジトリに無い

**配管延長・床面積を扱うコードは、このリポジトリに1行も無い。**
`benchmarks/synthetic_plans.py` が正解値として `total_floor_area_mm2()` を
持っているだけで、積算のパイプライン側がそれを消費する経路は存在しない。

同ファイルの冒頭にこう書かれている。

> トライアル4・6・10で使った合成図面は Codex 側で生成したもので、このリポジトリには
> 残っていません。

つまり **9.5節の数値(MAPE 1.700%→0% 等)は Codex 側の検証結果であり、
本リポジトリの実装で再現されたものではない。** 食い違いの本質は
「入口が単位を拒否する」ことではなく、**「連続量の対応がまだ実装されていない」**
ことである。

## 2. 選択肢

### 選択肢A: 9.5節の記述を実態に合わせる(ドキュメントのみ)

9.5節に「Codex 側の検証結果であり、本リポジトリには未実装」と明記し、
10章の次アクションに「連続量対応の実装」を独立項目として置く。

| | |
|---|---|
| 作業量 | 小(設計書の2箇所) |
| コード変更 | なし |
| リスク | なし |
| 得られるもの | 設計書を読んだ人が「連続量は動く」と誤解しなくなる |
| 失うもの | なし。連続量は依然として扱えない |

**この選択肢は、BやCを選んだ場合にも必要である**(実装が終わるまでの間、
設計書は実態を示すべきなので)。

### 選択肢B: 固定小数点として整数で表現する(推奨)

**連続量を、十分小さい単位の整数として扱う。** 長さは mm、面積は cm² または
0.01㎡、金額は円。こうすると小数が不要になり、**z3 の整数ソルバーを
そのまま使える。**

必要な変更は次の2点だけである。

1. `UNIT_ALIASES` に `m`(→mm)・`m2`(→cm²)・`yen` と日本語別名を追加し、
   単位ごとに「最小刻み」を宣言する
2. 入力を最小刻みの整数へ正規化する(`12.5m` → `12500mm`)

`MAX_COUNT = 1_000_000` との相性も確認した。

| 数量 | 単位 | 値 | 上限との関係 |
|---|---|---:|---|
| 配管延長 10m | mm | 10,000 | 余裕あり |
| 床面積 100㎡ | cm² | 1,000,000 | **上限ちょうど**(0.01㎡ 単位なら 10,000 で余裕) |

| | |
|---|---|
| 作業量 | 中(`inference_orchestrator.py` の単位正規化まわり) |
| コード変更 | ソルバー・キラークエスチョンは**変更不要** |
| リスク | 低。整数のまま扱うので既存の経路が壊れない |
| 注意点 | 最小刻みの選び方を単位ごとに決める必要がある。刻みが粗いと精度が落ち、細かいと上限に当たる |

### 選択肢C: z3 を実数(`z3.Real`)に切り替える

| | |
|---|---|
| 作業量 | 大 |
| 影響範囲 | `consistency_solver.py`(`z3.Int`→`Real`、`_tighten`、`as_long()`)、`constraint_exhaustive_search.py`、`killer_question/engine.py` |
| **重大な問題** | **キラークエスチョンが原理的に動かなくなる。** 候補列挙が `range(lower, upper + 1)` で、連続値には候補という概念が無い。区間分割などの新しい設計が必要 |
| リスク | 高 |

v8 9.5節の「設計への反映2」自身が「独立した合算(配管の区間ごとの長さ、
部屋ごとの面積)にはキラークエスチョンを無理に適用しない」と書いているので、
**連続量にキラークエスチョンを効かせる必要は元々薄い。** その意味でCの
コストは見返りに見合わない。

## 3. どの選択肢でも別途必要になること: 許容誤差

**「許容誤差内での自動採用」(9.5節 設計への反映1)は、単位の話とは独立した
未実装項目である。** B や C で単位を扱えるようにしても、階層1の判定は
「積集合が空でない」のままなので、9.5節の要求は満たされない。

許容誤差を入れる場合に決めなければならないこと。

1. 数量の種類ごとの許容誤差(長さ何%、面積何%、個数は完全一致か)
2. 許容誤差を「レンジを膨らませる」形で実装するか、「2つの軸の値の差が
   許容内かを判定する」形にするか。**前者は積集合が空になりにくくなるので、
   v8 3-2節の「空集合検出で絶対ルールの誤りを発見できる」(穴3への部分的対応)
   という利点を弱める**
3. 許容誤差を通った値を階層1(自動確定)にしてよいのか、階層2(抜き取り監査)
   に留めるのか

3つ目は設計方針そのものなので、おーちゃんの判断が必要になる。

## 4. 私の見解

**選択肢A(記述の訂正)は、他のどれを選んでも必要なので先に実施すべき。**
そのうえで連続量を実際に扱いたいなら、**選択肢B(固定小数点)を勧める。**
理由は3つ。

1. ソルバーとキラークエスチョンを一切変えずに済む。今回のような
   「既存の検証済み挙動が壊れる」事故のリスクが最も低い
2. 建築の数量は元々ミリ単位・円単位で扱うのが自然で、固定小数点は
   ごまかしではなく業務の実態に合っている
3. Cの最大の見返り(連続値に対するキラークエスチョン)は、9.5節自身が
   不要と結論している

ただし、**Bを入れても 9.5節の「連続量に有効」を本リポジトリで実証したことには
ならない。** 実証にはトライアル10相当のベンチマーク(配管延長・床面積の
合成シナリオと、軸間照合を通した改善率の測定)を新しく書く必要があり、
これは単位対応より大きい作業になる。9.5節の数値を本リポジトリで再現するのか、
Codex 側の結果として引用に留めるのかも、あわせて判断をお願いしたい。
