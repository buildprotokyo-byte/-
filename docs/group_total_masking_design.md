# 群合計制約の矛盾検出が、停止した要素のせいで効かなくなる問題 — 現象の確認と設計案

作成: 2026-09-22 / 対象コミット: `816e95b`（`claude/eloquent-feynman-c0o8rf` の HEAD）
再現テスト: `tests/test_group_total_masking.py`
**この文書は設計案までで、実装は含まない。**

---

## 1. 何を確かめたか

Codex がトライアル16の保存データを commit `c0c9d13` の本番ファイアウォールで
再判定して、次の現象を報告した。

- 本番ファイアウォールは階層2に「強い軸1つ + 異なる弱い軸2つ以上」を要求するため、
  旧判定より多くの要素を停止する
- 停止した要素は範囲が広がるため、群合計制約が UNSAT から SAT に変わる
- その結果、旧処理では群ごと停止していた「強い2軸が同じ誤値で一致」型の誤りが
  自動確定されるようになった
- 誤自動確定の合計は 456件から541件に増加（中心値検査は一度も発火しておらず、無関係）

このリポジトリの本番経路（`AxisQualityFirewall.assess()` →
`killer_question/firewall_bridge.py` → `ConsistencySolver`）で同じ形を組み直し、
**現象が再現することを確認した。** トライアル16の保存データは Codex 側にあり
本リポジトリには無いので、同じ性質の群（同一単位の10要素、群合計30）を新規に構成した。

## 2. 現象は本番経路でも起きる（実測）

同一単位の10要素からなる群（建具表に「合計30本」と書かれている想定）。
`door_1` は独立した強い軸2つが**同じ誤った値**（1、正解3）で一致している。
この形は

- 積集合が空にならないので、軸間矛盾としては検出できない
- 中心値も完全に一致するので、`CENTER_TOLERANCES` の中心値検査も発火しない

したがって**群合計制約だけが唯一の検出経路**である。

| 条件 | `door_0` の状態 | solver 上の範囲 | 群合計の判定 |
|---|---|---|---|
| 停止なし | 階層1 | (3, 3) | **unsat（検出できる）** |
| 停止・範囲そのまま | 階層3 | (2, 4) | **unsat（検出できる）** |
| 停止・精密モードで開き直し | 階層2 | (0, 6) | **sat（検出が消える）** |
| 停止・使える強い軸が0（既定） | 階層3 | **未登録** | **制約を書けない** |

最後の行が既定の挙動である。`firewall_bridge` はバグ①の修正として、使える強い軸が
1つも無い階層3の要素を `registered=False` で返し、solver に変数を作らない。
すると**その要素を参照する群合計制約は `solve()` の中で `KeyError` になる**ので、
呼び出し側は制約ごと落とすしかない。停止した1要素を守るために、**同じ群の他の9要素の
検査がまとめて消える。**

3行目（精密モード）が、Codex の言う「範囲が広がるため UNSAT が SAT に変わる」に
そのまま対応する。標準モードでは範囲が `(2, 4)` のままなので同じ群が unsat のままで、
**同じデータに対して、精密モードのほうが誤りを見逃す。**

### 2-1. 検出力は連続的に落ちる

停止した要素の幅が十分に大きければ、どんな誤りも吸収できてしまう。これは実装の
不具合ではなく論理の帰結で、群合計制約で否定できるのは

    群の誤差の合計 > 停止した要素の幅の合計

の場合だけである。したがって「停止した要素があっても群合計で必ず検出できること」を
要件にはできない。要件にできるのは次の2つ。

1. **群合計制約を立てられること。** 停止した要素が変数として登録されず、制約を
   書くことすらできない、という状態にはしない。
2. **「停止した要素が吸収したから sat になった」を sat と区別すること。**
   吸収が起きた群では、群の中の階層1の要素を自動確定のままにしない。

### 2-2. 併せて見つかったこと（この問題とは別件）

群合計が unsat になったとき、`unsat_core` は群の**全要素**の `range::` 制約と
`group_total` を並べて返す（実測）。矛盾の核が絞り込まれないので、
「どの要素を人に確認すればよいか」はこの核からは決まらない。
`benchmarks/run_trial789_reproduction.py` の `_variables_in_conflict()` は核に
出た変数を全部人に確認する作りなので、群合計を使うと**群の全要素を人に投げる**
ことになる。等式クラスタ（2変数）では問題にならなかったが、群合計では効いてくる。

## 3. 原因の切り分け

3つの別々の原因が同じ症状を出している。直す場所も別なので分けて書く。

**原因A: 停止した要素が変数として登録されない（既定の挙動）。**
`firewall_bridge.add_target_to_joint_solver()` は、使える強い軸が0の階層3要素を
登録しない。安全側の判断として正しい（棄権した証拠の番兵値 `(0, 0)` がハード制約の
範囲を書き換えるのを防ぐ、バグ①の修正）。しかし**「変数が無い」は「変数が自由」より
悪い。** 自由変数なら制約は書けて、誤差が幅を超えれば検出できる。変数が無いと
制約自体が書けない。

**原因B: 「人に質問できるようにする」と「共有solver の定義域」が同じ1つの範囲に
同居している。** 精密モードの開き直し（`mode is PrecisionMode.PRECISE` の分岐）は、
階層2の要素を直接確認の対象にするために読みの和集合まで範囲を戻す。目的は
**質問の候補を広げること**であって、群全体の検査を緩めることではない。ところが
同じ範囲が群合計制約の定義域になるので、副作用として検査が緩む。

**原因C: 群合計制約が「検査」として扱われていない。** いまの経路では、群合計は
solver に入る制約の1つでしかなく、sat だったときに「この検査は何かを否定できたのか」
を誰も問わない。停止した要素の幅で吸収されただけでも、sat は sat として通る。

## 4. 設計案

4つを層にして提案する。A案とB案が原因A・原因Bへの直接の手当て、C案が原因Cへの
手当て、D案が運用への織り込み。**C案がこの問題の中心**で、A案はその前提になる。

### 4-1. C案（中心）: 群合計の残差中心検査

群合計が sat になったとき、**停止した要素に押し付けられた値（残差）が、その要素
自身の読みの中心からどれだけ離れているか**を見る。離れていれば、その sat は
「誤りが無い」ではなく「停止した要素が吸収した」である。

    停止していない要素の合計の区間     [Σlow_fixed, Σhigh_fixed]
    残差（停止した要素が担うべき値）   R = [T − Σhigh_fixed, T − Σlow_fixed]
    停止した要素自身の中心の合計       C = Σ center(停止した要素)
    許容幅                             W = 単位ごとの許容差 × 停止要素数

    R と [C − W, C + W] が交わらなければ「吸収された」と判定する

`center()` は、その要素に使える強い軸があればその積集合の中心、無ければ棄権して
いない読みの和集合の中心を採る。単位ごとの許容差は**既にある
`CENTER_TOLERANCES` をそのまま使う**（個数 ±1、連続量 ±5%）。中心値検査と同じ
道具を、要素単体ではなく群の残差に当てるだけなので、許容差の議論
（v8 10章12項）を二重に持たずに済む。

**試作して確かめた**（`/tmp` の試作。本番コードには入れていない）。上の10要素の群で:

| 条件 | solve | 残差 | 停止要素の中心 | 許容 | 吸収判定 |
|---|---|---|---|---|---|
| 誤りなし・停止あり（精密） | sat | 3 | 3 | ±1 | **なし**（誤報なし） |
| `door_1` が −2 誤り（精密） | sat | 5 | 3 | ±1 | **あり（検出）** |
| `door_1`/`door_2` が −2 誤り（精密） | unsat | 7 | 3 | ±1 | あり |
| 誤りなし・強い軸0を和集合で登録 | sat | 3 | 3 | ±1 | **なし**（誤報なし） |
| `door_1` が −2 誤り・強い軸0を和集合で登録 | sat | 5 | 3 | ±1 | **あり（検出）** |
| `door_1` が +1 だけずれ（精密） | sat | 2 | 3 | ±1 | なし（**死角**、下記 5節） |

いまは自動確定で素通りしている2行目・5行目が、この検査で止まる。誤りが無い条件
（1行目・4行目）では発火しないので、自動化率をむやみに下げない。

**吸収が判定されたときの扱い（要判断）。** 群合計は「どの要素が誤っているか」までは
言わない。言えるのは「この群は、停止した要素を自分の読みの近くに留めると合計が
合わない」ことだけである。候補は3つ。

- (a) 群の中の階層1の要素を階層2（仮採用＋抜き取り監査）へ落とす
- (b) 群全体を階層3（人が確認）へ落とす ← 旧処理の挙動に近い。安全だが人手が増える
- (c) 群の中でキラークエスチョンを1問立てる（合計の残差を最も動かす要素を選ぶ）

**(c) を推す。** 群合計は「1問で群全体が決まる」形の制約なので、キラークエスチョン
エンジンが最も効く場所である。ただし (c) は実装が最も重い。**(a) を先に入れて
(c) を後から足す**のが段取りとしては安全だと考える。ここはおーちゃんの判断が要る。

### 4-2. A案（前提）: 停止した要素も必ず変数として登録する

`firewall_bridge` の `registered=False` をやめ、階層3の要素も必ず変数にする。

- 定義域は、**棄権していない証拠のうち使える強い軸の積集合**。それが無ければ
  棄権していない読みの和集合。それも無ければ `arbitration/units.py` が持つ
  その単位の許容域（`max_value`）
- `requires_confirmation=True` は従来どおり立てる（確定済みとして扱われない）
- **番兵値の混入はしない。** バグ①の実害は「棄権した証拠の `(0, 0)` が下限を
  0 まで引き下げた」ことで、棄権を除外すれば起きない（既に bridge は除外している）
- 新しいフラグ（仮に `domain_is_unvalidated`）を変数に持たせ、「この定義域は
  校正を通った読みに裏づけられていない」ことを下流が読めるようにする

これで群合計制約が常に書けるようになり、C案の残差検査も常に動く。
**A案だけでは足りない**（幅が広がれば吸収されるので、C案とセットで意味がある）。

### 4-3. B案: 質問の候補を広げることと、共有solver の定義域を分ける

精密モードの開き直し（`firewall_bridge` の `PrecisionMode.PRECISE` の分岐）は、
共有solver の定義域を広げるのをやめ、**狭い `confirmed_range` のまま
`requires_confirmation=True` を立てる**。読みの和集合は、キラークエスチョン
エンジンが自分の仮説空間として持つ（`engine.py` の候補列挙側）。

これで「精密モードのほうが誤りを見逃す」という逆転が消える。
`allow_provisional_domain=True` も同じ扱いにできるが、こちらは
`docs/killer_question_report.md` 3節の絞り込みの挙動に関わるので、
既定が False のまま（v8 10章14項で「意図的に着手しない」と決めた項目）なら
当面そのままでよい。

### 4-4. D案: 群合計制約の検出力を数字で出す

群合計を検査として使うとき、その群の**吸収余地**

    S = Σ (停止した要素の幅)

を計算して報告に載せる。S が、その群で捕まえたい最小の誤差より大きければ、
**その群合計は何も否定できない**ので「検査あり」と数えない。
`arbitration/provisional_audit.py` が `hit_rate=None` で「照合できない対象」を
区別しているのと同じ考え方で、「検出力の無い検査」を「通った検査」と混ぜない。

## 5. この設計案の死角（正直に書く）

1. **許容差の中に隠れる誤りは捕まえられない。** 上の表の最終行がそれで、
   `door_1` が +1 だけずれた場合、残差は 2 で中心 3 から ±1 の中に入るので
   発火しない。要素単体の中心値検査と同じ死角であり、同じ原因（許容差を
   置く以上、その幅の中は見えない）である。
2. **停止した要素が多い群では効かなくなる。** 許容幅 W は停止要素数に比例して
   広がるので、10要素中8要素が停止した群では W = ±8 になり、ほとんど何も
   否定できない。D案の S を見て「検出力なし」と判定するしかない。
3. **停止した要素の中心そのものが誤っている場合、誤報になる。** 停止した要素の
   読みが大きく外れていると、残差が中心から離れて「吸収された」と判定される。
   このとき止まるのは正しい（その要素は確かに怪しい）が、**止まる理由が
   「他の要素が誤っている」ではない**ので、(c) のキラークエスチョンで
   どの要素かを絞る価値がここにもある。
4. **群合計そのものの読み取りが誤っている場合は扱えない。** 建具表の「合計30本」
   を読み違えていれば、この検査は群全体を疑い続ける。群合計の値自体を
   何本の軸で読んだかは、いまどこにも記録していない。

## 6. 残っている確認事項

- **トライアル16の保存データでの再現。** 本文書の再現は同じ性質の群を新規に
  構成したもので、Codex の「456件 → 541件」という数値そのものは再現していない。
  Codex が用意している評価データ（同じ単位の10要素の群）が届いたら、C案の
  試作をそれに当てて効果を測る
- **4-1節の (a)/(b)/(c) の選択**（おーちゃんの判断）
- **群合計制約の API。** いまリポジトリには群合計の専用の入口が無く、
  `add_relation` にラムダを渡して書くことになっている。C案を入れるなら
  「この制約は群合計である」と宣言できる入口が要る（残差検査は、どの変数が
  1つの群を成すかを知らないと書けないため）
