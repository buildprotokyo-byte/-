# トライアル7・8・9の数値を、このリポジトリで再現できるか

作成日: 2026年9月21日
実行: `python -m benchmarks.run_trial789_reproduction --trials 30`
回帰テスト: `tests/test_trial789_reproduction.py`
関連: `docs/audit_unimplemented_trial_claims.md` 4節、`docs/design_v8.md` 4章

## 0. 結論

**3件のうち1件はほぼ再現でき、1件は部分的に再現、1件は測れなかった。**

| トライアル | 主張 | この実装での結果 | 判定 |
|---|---|---|---|
| 7 | 19要素を理論下限と一致する6問で解決 | **19要素・理論下限6問・実際6問・精度100%** | **再現した** |
| 8 | 階層なし100%→78.9%、階層ありで100%に回復(6問→8問、+33%) | 階層なし68.4%、階層あり97.4%(100%到達は25/30)。コストは理想条件の**1.44倍** | **条件付きで再現。ただし重要な反例あり(3節)** |
| 9 | データ源考慮で監査コストを44%削減 | 監査件数 4.93 → 4.93、総コスト 14.30 → 14.30。いずれも **0.0%** | **測れなかった。**「効果が無い」の実測ではない(4-5節) |

**最も重要なのは、トライアル8の再現の過程で見つかった反例である。**
誤った読みが正解のレンジと**重なる**場合、**3段階確信度階層は精度を回復させる
どころか、階層なしより悪化させることがある**(実測: 57.9% → 42.1%)。
これは v8 8章の穴2(尤もらしい誤り)が、設計の中心部分で実際に起きることを
示している。詳細は3-2節。

### 前提として、元データは無い

**トライアル7〜9で使った合成データは Codex 側にあり、このリポジトリには
残っていない**(`docs/killer_question_report.md` 2節と同じ事情)。したがって
ここでやったのは「同じ数値を出すこと」ではなく、**同じ性質のシナリオを組んで、
この実装で何が起きるかを測ること**である。数値が一致しない場合は、
一致しないことをそのまま書く。

## 1. シナリオ

19要素・6独立クラスタ。1クラスタが部屋1つに相当し、内部は等式で結ばれる
(戸・窓・コンセント・スイッチが同数)。

| クラスタ | 要素数 |
|---|---:|
| living | 4 |
| kitchen | 4 |
| bath | 3 |
| bed_a | 3 |
| bed_b | 3 |
| hall | 2 |
| **合計** | **19** |

クラスタ間は無関係なので、**理論下限は「幅の残っている連結成分の数」= 6問**に
なる。この下限は**ハードコードせず、`DependencyGraph.components()` から毎回
計算している**(`theoretical_lower_bound()`)。クラスタごとに違う正解値を
与えているので、クラスタをまたいだ誤った伝播が起きれば数値に出る。

### 運用コストの定義

v8 4-3節は「監査込みの実質質問数を運用コストとする」と書いているが、
**その内訳の定義は資料に残っていない。** 本報告では次のように定義した。

```
運用コスト = キラークエスチョンの質問数
           + 矛盾(積集合が空)の解消のために人が確認した回数
           + 階層3(要確認)の要素を人が確認する回数
           + 階層2の抜き取り監査の件数
```

**この定義は本報告の解釈であり、トライアル8の原典と同じとは限らない。**
特に「矛盾の解消」は、原典に対応する項目があるかどうか分からない。

### 誤りの入れ方を2通り測った

| 名前 | 内容 |
|---|---|
| `disjoint` | 誤った軸のレンジが、正解のレンジと**重ならない**。軸間照合が矛盾として検出できる |
| `overlapping` | 誤ったレンジが正解のレンジと**部分的に重なる**。積集合が空にならないので矛盾として検出できず、v8 8章の穴2になる |

この区別は当初のベンチマーク設計には無く、**実装して測っている途中で
「重なる誤り」の挙動が明確に違うことに気づいて追加した。**

## 2. トライアル7: 再現した

```
要素数              : 19
独立クラスタ数      : 6
理論下限(計算値)    : 6問
実際の質問数        : 6問
精度                : 100.0%
```

**理論下限と一致し、19要素すべてが正解になった。** 主張どおりである。

ただし留保が1つある。`docs/killer_question_report.md` 2節が既に指摘している
とおり、**この実装は Z3 による大域求解なので、等式で結ばれた鎖はどこを聞いても
1問で全体が確定する。** 「逐次的に1段ずつ伝播する」設計だった場合より下限に
到達しやすい可能性があり、**主張の再現というより、この実装が下限に到達できる
構造であることの確認**に近い。

## 3. トライアル8: 条件付きで再現。ただし重要な反例がある

理想条件(誤り0%)のコストは **11**(質問6 + 階層3 0件 + 監査5件)だった。
以下の「理想条件の何倍」は、この11を基準にしている。

### 3-1. 明確に矛盾する誤り(`disjoint`): ほぼ主張どおり

| 指標 | 主張(トライアル8) | 実測(30試行) |
|---|---|---|
| 階層なしの精度 | 78.9% | **68.4%** |
| 階層ありの精度 | 100%に回復 | **97.4%**(100%到達は25/30) |
| コストの増分 | +33%(6問→8問) | **+44%**(11→15.8) |

**方向は完全に一致した。** 階層なしでは精度が3割落ち、階層を入れると
ほぼ回復し、その代わりコストが4割強増える。「理論上の効率と正確性は
両立せず、確信度階層とセットで初めて安全に機能する」(v8 6章の教訓9)は、
この実装でも成り立っている。

数値が一致しない理由は特定できる範囲で2つある。

1. **階層なしの68.4%は、誤り率の設定で決まる値である。** 画像軸30%・文章軸5%
   (v8 2章が「文章軸はトライアル9で5%と設定」と書いているのに合わせた)を
   置いた結果がこれで、原典が同じ誤り率だったかは分からない
2. **コストの内訳が違う。** 実測のコスト増15.8 − 11 = 4.8 のうち、
   **大半は「矛盾の解消」(平均9〜10件)である。** 原典の「6問→8問」は
   +2件しかないので、原典のコスト定義に矛盾解消が含まれていたとは考えにくい

### 3-2. 【重要】重なる誤り(`overlapping`): 階層が精度を悪化させることがある

**これが本報告で最も重要な発見である。**

誤った読みが正解のレンジと部分的に重なると、**積集合が空にならないため矛盾と
して検出できない。** その結果、独立した強い軸2つが「一致した」と判定され、
**階層1(自動確定)で誤った値が確定する。** さらにクラスタ内の等式によって、
その誤りが**クラスタ全体に伝播する。**

実測(先頭10試行):

| seed | 階層なし | 階層あり | 差 |
|---:|---:|---:|---|
| 0 | 63.2% | 100.0% | +36.8 |
| **1** | **57.9%** | **42.1%** | **−15.8** |
| **2** | **73.7%** | **63.2%** | **−10.5** |
| 3 | 68.4% | 78.9% | +10.5 |
| 4 | 57.9% | 57.9% | ±0 |
| 5 | 63.2% | 78.9% | +15.7 |
| 6 | 52.6% | 84.2% | +31.6 |
| **7** | **63.2%** | **47.4%** | **−15.8** |
| 8 | 47.4% | 47.4% | ±0 |
| 9 | 31.6% | 42.1% | +10.5 |

**10試行のうち3試行で、階層を入れたほうが精度が低い。** 2試行は同じ。

これは実装の不具合ではなく、**設計上の性質**である。

* 階層なしは要素ごとに独立に判定するので、誤りは1要素で止まる
* 階層ありは等式で結ばれたクラスタ全体を同時に解くので、**1つの誤った
  自動確定がクラスタ全体(最大4要素)を汚染する**

**v8 3-2節は「空集合検出で絶対ルールの誤りを発見できる」ことを穴3への部分的
対応として挙げているが、その裏返しとして、空集合にならない誤りは検出できない
まま増幅される。** 8章の穴2そのものが、設計の中心部分で起きている。

## 4. トライアル9: 測ろうとして、実装の欠陥が見つかった

### 4-1. 最初は「効果0%」に見えた

データ源別誤り率を渡す場合と渡さない場合で、監査件数と総コストを比べたところ、
**全試行で完全に同じ値**になった。しかしこれを「効果が無い」と報告するのは
誤りだった。**ルールが一度も発火していなかった**からである。

### 4-2. 原因: 軸の名前が firewall_bridge で失われていた

v8 4-3節ルール2(トライアル9)の実装は `killer_question/engine.py` の
`_tie_break()` にあり、`solver.variable_axis()` で引いた軸名を
`axis_error_rates` の辞書に当てて誤り率を得る。

ところが `killer_question/firewall_bridge.py` は、変数を登録するときに
`axis` へ**確信度階層のラベル**を入れる(`firewall_confirmed` /
`firewall_provisional` / `firewall_unconfirmed`)。**元の軸("image" /
"text" 等)はそこで消える。**

実測(修復前):

```
solver 上の変数の軸名:
  'firewall_unconfirmed': 7件
  'firewall_provisional': 12件
AXIS_ERROR_RATES のキー: ['history', 'image', 'rules', 'text']
→ 誤り率表に載っている軸名を持つ変数の数: 0
```

**19要素すべてが誤り率表に一致しない。** その場合 `_tie_break()` は
`_UNKNOWN_AXIS_ERROR_RATE = 1.0` を全要素に割り当てるので、全員同点になり、
変数名の昇順に落ちる。**つまりこのルールは、実運用の経路(ファイアウォール →
bridge → キラークエスチョン)では一度も効いていなかった。**

既存のテストが通っていたのは、`tests/test_killer_question_engine.py` が
**bridge を通さずに `add_variable(axis="text_axis")` を直接呼んでいる**ため。
エンジン単体では正しく動いており、**つなぎ目だけが切れていた。**

なお bridge には、精密モードで階層2を開き直す分岐に
`axis = speaking[0].axis_id`(元の軸を残す)というコメント付きの処理が既にあり、
**この問題を一度は意識した痕跡がある。** ただし標準モードの経路には入って
いなかった。

### 4-3. 修復

`Variable` に `source_axis`(値の出どころの軸)を足し、`axis` の階層ラベルとは
別に持たせた。bridge がこれを埋め、エンジンは
`variable_error_rate_axis()` で引く。

**階層ラベルはそのまま残している。** バグ②(階層3を確定済み扱いする)の回帰
テストがラベルに依存しているので、そこを壊さないため。

修復後は19要素すべてが `image` / `text` に解決するようになった。

### 4-4. もう1つの落とし穴: 軸が1種類だと測れない

修復しても、**最初は依然として順序が変わらなかった。** シナリオの全要素の
主軸が画像軸だったため、誤り率が全員同じ値になり、また同点に落ちていた。

**トライアル9のルールは、要素の出どころが複数種類あって初めて意味を持つ。**
そこでクラスタごとに主軸を画像軸/文章軸へ振り分けた(`mixed_primary_axes`)。
これで **8試行のうち3試行で質問順が実際に変わる**ようになった。

この2つの落とし穴は、どちらも「測定が空回りしていても緑に見える」種類のもので、
`tests/test_trial789_reproduction.py` に回帰テストを置いた
(`test_the_bridge_preserves_the_originating_axis`、
`test_the_axis_error_rate_rule_changes_the_question_order`、
`test_a_single_source_axis_cannot_exercise_the_rule`)。

### 4-5. 最終実測: 削減率 0.0%。ただし「効果が無い」ことの実測ではない

修復と主軸の振り分けを済ませた上で、30試行を回した実測値。

```
  30試行の平均監査件数: 考慮なし 4.93 → 考慮あり 4.93
  監査コストの削減率: +0.0%
  30試行の平均総コスト: 考慮なし 14.30 → 考慮あり 14.30
  総コストの削減率: +0.0%
```

10試行ぶんの内訳を出したが、**全シードで監査件数も総コストも1件の差も出なかった**
(`benchmarks/run_trial789_reproduction.py` の出力)。

そこで「ルールは発火しているのに、なぜ監査件数が動かないのか」を追った。

**理由は、監査の抽出件数がこのシナリオの規模では定数だからである。**
`arbitration/provisional_audit.py` の `plan_sample_size()` は
`max(1, min(N, max(round(N × 0.30), 5)))`。実測値:

| 階層2母集団 N | 4 | 5 | 9 | 10 | 16 | 18 | 19 | 22 |
|---|---|---|---|---|---|---|---|---|
| 抽出件数 | 4 | 5 | 5 | 5 | 5 | 5 | 6 | 7 |

**N が 5 から 18 までの間、抽出件数は最小抽出件数の 5 に張り付いて動かない。**
`round(N × 0.30) > 5` になるのは N ≥ 19 から。本シナリオの階層2母集団は
実測で 4〜11 件なので、**母集団が何件動いても抽出件数は 5 のまま**になる。

12試行で母集団まで並べて確認した実測:

```
seed 1: 順序変化=True  階層2母集団= 7/ 7  監査=5/5
seed 3: 順序変化=True  階層2母集団= 9/10  監査=5/5
seed 6: 順序変化=True  階層2母集団= 5/ 5  監査=5/5
seed 9: 順序変化=True  階層2母集団= 5/ 5  監査=5/5
12試行: 順序が変わった=4  総コストが変わった=0  母集団が変わった=1
```

seed 3 では**母集団が 9 → 10 に1件増えている**(このルールを入れたほうが
1件悪くなっている)。それでも抽出件数は 5/5 で同じである。つまり
**監査件数という指標は、この規模では母集団の変化を映さない。**

したがって正確な結論は次のとおりである。

* **「44%削減」は、本リポジトリでは再現していない。** 実測は 0.0% である
* **ただしこれは「効果が無い」ことの実測ではない。** 本シナリオは、この効果を
  測る手段そのものを持っていない。最小抽出件数5の床が、母集団の差を
  すべて飲み込んでいる
* 測るには、階層2母集団が 19件以上になる規模(要素数で60件程度)の案件か、
  最小抽出件数を下げた設定が必要である。**本報告ではどちらも行っていない**
* seed 3 のように**母集団が増える方向に動いた試行がある**ことは、
  ルールの効果の向きすら本シナリオでは確認できていないことを意味する

**「再現しなかった」と「測れなかった」は違う。トライアル9については後者である。**

## 5. 何が言えて、何が言えないか

### 5-1. 再現できたこと

* **トライアル7の主張は成り立つ。** 19要素・6独立クラスタで、理論下限の6問、
  精度100%。ただしこの実装は Z3 の大域求解なので、等式で結ばれた構造では
  下限に到達しやすい(2節の留保)
* **トライアル8の「方向」は成り立つ。** 階層なしでは精度が3割落ち、階層を
  入れるとほぼ回復し、その代わりコストが4割強増える。v8 6章の教訓9
  (「理論上の効率と正確性は両立せず、確信度階層とセットで初めて安全に機能する」)
  は、この実装でも確認できた

### 5-2. 再現できなかったこと

* **トライアル8の数値は一致しない**(78.9%→68.4%、+33%→+44%)。誤り率の設定と
  コスト定義が原典と同じか分からないため、一致しないことに意味を読むべきでない
* **トライアル9の44%は再現しない(実測 0.0%)。ただし「効果が無い」という
  実測でもない。** ルールが質問順を変えることは確認できたが、監査の抽出件数は
  最小抽出件数5の床に張り付いており、母集団が何件動いても 5 のまま変わらない。
  **本シナリオは、この効果を測る手段そのものを持っていない**(4-5節)。
  原典がどの機構で44%を出したのかも、資料から復元できない

### 5-3. この作業で新しく見つかったこと

**再現ベンチマークを書く目的は数値の確認だったが、実際に価値があったのは
こちらだった。**

| # | 見つかったこと | 性質 |
|---|---|---|
| 1 | 重なる誤りに対して、階層が精度を**悪化させる**ことがある(3-2節) | **設計上の問題。未解決** |
| 2 | トライアル9のルールが実運用の経路で一度も発火していなかった(4-2節) | 実装の欠陥。**修復済み** |
| 3 | 軸が1種類のシナリオではこのルールを測れない(4-4節) | 測定上の落とし穴。テストで固定 |
| 4 | 監査件数は母集団 5〜18 件の範囲で定数になり、母集団の変化を映さない(4-5節) | 測定上の限界。**44%を測れない原因** |

1 は v8 10章19項、2・4 の残課題(44%の扱いと測定手段)は20項に切り出した。

## 6. 正直な留保点

* **19要素6クラスタというシナリオは、私が構成したものである。** 原典の構造
  (要素の種類、依存関係の形、誤り率)とどこまで一致しているかは分からない。
  したがって数値の一致・不一致から原典の正しさを判断することはできない
* **運用コストの定義は本報告の解釈である**(1節)。特に「矛盾の解消」は原典に
  対応する項目があるか分からない。実測のコスト増の大半がこの項目なので、
  定義が違えば「+44%」という数字も変わる
* **誤りの入れ方(`disjoint` / `overlapping`)の比率が現実と合っているかは
  未検証である。** 実際の図面でどちらがどれだけ起きるかは測っていない。
  3-2節の問題がどれだけ深刻かは、この比率で決まる
* **階層なしのモデルも私の構成である。** 「積集合を採り、空なら主軸を採り、
  中央値を単一値とする」という素朴な実装を仮定した。原典の「階層なし」が
  同じだったかは分からない
* トライアル11(44%削減の複数シード検証)は Codex 側で結果待ちのままである。
  **本報告はそれとは別に、本リポジトリの実装で測った結果である**
* **4-3節の修復で、証拠が複数の軸から来ている場合は「先頭の軸」を出どころと
  している。** 誤り率がいちばん低い軸を選ぶほうが 4-3節ルール2の意図には
  近いが、bridge は誤り率表を持っていないためそこでは決められない。
  精密モードの既存の分岐が同じ規約(`speaking[0].axis_id`)を使っているので
  それに合わせた。**この選び方がルールの効果を弱めているかは測っていない**
