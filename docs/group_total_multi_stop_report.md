|---|---|---|---|

**ただし、素通り54群のうち候補が拾えるのは18群だけで、36群は残る。** 残る36群は
全部「群の許容幅の中」で、停止した要素がそれぞれ許容差 ±1 の中で少しずつ動けば
合計の差を説明できてしまう。設計書 4-1節の式(許容幅 = 許容差 × 停止要素数)では
**原理的に見えない**。停止1つのときの ±1 の死角(`docs/group_total_masking_design.md`
5節)が、停止の数だけ広がったものである。事前の予想(R3)どおりだった。

## 3. 何が起きているか(コードを読んで確かめたこと)

`check_group_total()`(`arbitration/group_total.py`)は、群合計を含めて解いたあと、
停止した要素を**1つずつ**見て、その要素の解の範囲が自分の窓(読みの中心 ± 1)から
**全部外れたとき**だけ「吸収」とする。停止した要素が2つあると、他方が動けるぶん
それぞれの解の範囲が広がり、どちらも自分の窓と重なったままになる。

例: 停止2つ(`door_0` 中心3、`door_5` 中心4、どちらも半幅3)、階層1の `door_3` が −3。
停止した2要素が担うべき合計は 10、窓の合計は [5, 9]。**群としては合わない**が、
`door_0` の解の範囲は [3, 6](窓 [2, 4])、`door_5` は [4, 7](窓 [3, 5])で、
どちらも自分の窓と重なるので吸収なしになる(実際に解いて確かめた)。
2つが同時に窓の上端(4 と 5、合計9)に寄っても10には届かないが、要素ごとに見ると
それが見えない。候補の式は 10 と [5, 9] を比べるので吸収とする。

#101 の測定スクリプト(`benchmarks/measure_group_total_question.py`)も、
(c) の入口 `KillerQuestionEngine.group_total_question()` も、この同じ
`check_group_total()` を呼んでいる。

## 4. 候補の中身(スクリプトの中だけ)

`benchmarks/measure_group_total_multi_stop.py` の `candidate_absorbed()`。

- いまの判定が吸収なら、そのまま吸収
- そうでなくても、群が sat で、
  **残差 R = 群合計 − 停止していない要素の検出用の範囲の合計** が
  **停止した要素の窓(`_center_window()`、いまと同じもの)の合計**と交わらなければ吸収
- unsat には触らない。監査に落とす要素は いま と同じ規則(停止していない階層1)

## 5. 限界

- **合成の格子だけ。** 10要素・個数・誤りは1要素だけ。連続量(許容差 ±5%)、
  誤りが2要素以上にまたがる場合は測っていない
- **いまの本番経路では、この判定は呼ばれていない。** `check_group_total()` を呼ぶのは
  `KillerQuestionEngine.group_total_question()` とテストと `benchmarks/` だけで、
  `group_total_question()` を呼ぶのもテストと `benchmarks/` だけ(コードを検索して
  確かめた)。**実案件で何件素通りしているかは、この測定では分からない**
- 候補を入れたときの (c) の問いそのものは測っていない(エンジンが内部でいまの判定を
  呼ぶため)。件数は「吸収された群に1問」(#101 の A2・A3)から、新しい問いは
  階層1の18群・停止した要素の2群、陰性対照は 0 と見込むだけ
- 停止した要素の誤りが −3 のとき、読みの下限を0で切るので中心がずれ、+3 と同じ
  動きにならない(新しく監査に落ちた2群が +3 だけなのはこのため)

## 6. 判断が要ること

- **候補((a) の判定に群の式を足す)を入れるか。** 入れると、停止2つ以上の群で
  群の許容幅を超える誤り(測った18群)が吸収と判定され、階層1が監査に落ち、(c) の1問が
  立つ。停止0・1の群と陰性対照は変わらない。停止した要素の読みが外れた群で、
  正しい階層1が監査に落ちることがある(測った2群)
- **群の許容幅の中の死角(測った36群)をどう扱うか。** 許容幅を「許容差 × 停止要素数」
  で足し上げる限り、停止が増えるほど見えない誤りが増える。狭めるなら許容誤差の本決め
  (v8 10章12項)の話になり、この測定の外である
