## 1. データ取得可否の確認結果(e-Statへの到達可否、データ形式)

**到達できました。**(2026年9月21日実測)

| 対象ホスト | 結果 |
|---|---|
| `https://www.e-stat.go.jp/` | **200** |
| `https://www.mlit.go.jp/` | **200** |
| `https://api.e-stat.go.jp/`(ルートパス) | 403(CDN=ZENEDGE がルートを拒否) |
| `https://api.e-stat.go.jp/rest/3.0/app/json/getStatsList?...` | **200**(中身は「認証に失敗しました。アプリケーションIDを確認して下さい。」) |

api.e-stat.go.jp のルートパスの403は**通信の遮断ではなく、CDNがルートURLを
返さない**というだけです。REST APIのエンドポイント自体は200を返しており、
中身はアプリケーションID未指定の認証エラーでした。つまり**ネットワークは
通っており、APIを使うにはe-Statのユーザー登録(appId取得)が必要**という状態
です。

### appIdを取らずに済ませた方法

e-Statの**ファイルダウンロード**(`https://www.e-stat.go.jp/stat-search/file-download?statInfId=...&fileKind=0`)
は**アプリケーションID不要**で、統計表の .xlsx をそのまま取得できます。
今回はこちらを使いました。appIdの取得をおーちゃんに依頼する必要はありません。

### 実際のデータ形式・更新頻度・含まれる項目

| 項目 | 実測値 |
|---|---|
| 統計名 | 建築物リフォーム・リニューアル調査 |
| 提供分類 | 年度次(ほかに四半期・半期あり) |
| 取得した回 | **令和7年度計**(2025年4月〜2026年3月受注分) |
| e-Statの公開(更新)日 | **2026年6月12日** |
| statInfId | `000040463576` |
| ファイル名 | `2025fykeirr_e-stat_excel.xlsx`(272KB) |
| sha256 | `b5dbc6887f721c8a06cf66835f084d62ff2565709e488c5afc723556475c6d5c` |
| 形式 | Excel (.xlsx)。CSVやJSONでの提供は無い |
| シート数 | 34(表一覧 + 本表22枚 + 参考表11枚) |
| 更新頻度 | 年度次は年1回(6月頃)。四半期報は四半期ごと |

含まれる表は、受注高の推移、工事種類別・用途別・構造別の受注件数と受注高、
工事目的別・工事部位別の受注件数、建築の時期別、工期、施工地域別など
22表と参考表11表です。

### ここで判明した、設計に効く制約

**大半の表は「合計」か「平均」しか載っていません。** 代表値からは
「あり得る値の範囲」を正直に作れません(平均値を low=high として置けば、
実態より極端に狭いレンジを主張することになり、v8が避けたい過信そのものに
なります)。

**分布そのもの(階級ごとの件数)を持っているのは、次の2表だけでした。**

* 表4-1 個別工事の受注額、用途別 受注件数＜住宅＞(金額階級13区分)
* 表4-2 個別工事の受注額、用途別 受注件数＜非住宅建築物＞(同24区分)

そのため、この2表だけを使っています。

## 2. 実装内容(インターフェース、スナップショット方式)

### ディレクトリ構成

```
axes/industry_statistics_axis/
├── __init__.py
├── snapshot.py       # スナップショットの保存・読み込み
├── metric_names.py   # 用途 → 項目名の引き当てだけを行う(reading.py の後継)
├── fetch.py          # e-Statからの取得・パース・スナップショット生成(ステップ0)
├── _xlsx.py          # 標準ライブラリだけの最小xlsxリーダー(ステップ0)
├── sources/
│   └── 2025fykeirr_e-stat_excel.xlsx   # e-Statから取得した原本(272KB)
└── snapshots/
    └── 2026-09-21.json                  # 実データ15項目(is_placeholder=False)
```

原本(.xlsx)もリポジトリに入れてあります。スナップショットのJSONが原本から
機械的に再生成できることをテストで確かめるためで、**手で書いた数値が紛れ
込んでいたらテストが落ちます**(`test_shipped_snapshot_is_reproducible_from_the_shipped_source`)。

### スナップショット方式(`snapshot.py`)

`StatisticsSnapshot`は、`source_name`・`source_url`・**`fetched_at`(取得日)**・
`period_covered`(統計データ自体が対象とする期間)・`metrics`(項目名→
`IndustryMetric`)・`is_placeholder`を持つ。`save_snapshot()`/`load_snapshot()`/
`load_latest_snapshot()`でJSONとしてローカルに保存・読み込みする。

指示書どおり、**「取得のたびに最新を見に行く」処理は実装していない。**
取得(ネットワークアクセスを伴うスクリプト)は別工程として想定しており、
今回は「保存済みのスナップショットを読み込む」側だけを実装した
(取得スクリプト自体は5節「制約」で述べるとおり、ネットワークが使える
環境でないと書いても検証できないため、今回は実装を見送っている)。

同梱している既定スナップショットは `2026-09-21.json`(`is_placeholder=False`、
15項目)。**中身は1節のe-Stat原本から生成した実データで、架空の数値は
含まれていない。**

同じ取得日に実データとプレースホルダーが並んだ場合、`load_latest_snapshot()`
は**実データの方を返す**(`(fetched_at, not is_placeholder)` で比較)。
中身の無いスナップショットを黙って掴まないようにするため。

### 取得スクリプト(`fetch.py`)— ステップ0で追加

`python -m axes.industry_statistics_axis.fetch` で、e-Statから原本を
ダウンロードし、パースし、スナップショットを保存する。`--offline` を付けると
ダウンロードせず同梱の原本から作り直す(テストとCI用)。

**openpyxl は使っていない。** 実装時点でこの実行環境から pypi.org に到達できず
(2026-09-21午前の実測で403)、インストールできなかったため。
**同日にpypi.orgの許可が入って到達できるようになりましたが、標準ライブラリ
だけで完結している利点(依存を増やさない)を保つため、そのまま残しています。**
`_xlsx.py` に zipfile + xml.etree だけの最小リーダーを書いた。ふりがな
(`<rPh>`)を本文と一緒に拾うと「住宅ジュウタク」のように連結してしまうので、
明示的に取り除いている。

### 実データから「あり得る値の範囲」を作る方法

表4-1・表4-2 は「金額階級 × 用途」の受注件数の表なので、用途ごとに
**階級分布からパーセンタイル**を計算した。

| 出力 | 値 |
|---|---|
| `low` | 第5パーセンタイル |
| `typical` | 中央値 |
| `high` | 第95パーセンタイル |
| `unit` | `万円/件` |

階級の内側は一様分布を仮定した線形内挿で求めている。**最上位階級は上限が
無い**(「3,000万円以上」「5億円以上」)ので、第95パーセンタイルがそこに
落ちる用途は、**上限を捏造せずにその項目ごと落とす**(`percentile()` が
`None` を返し、`build_metrics()` が理由を `notes` に記録する)。今回の
データでは該当した用途は無かった。

読み取りが崩れていないことの担保として、**階級ごとの件数の合計を、表に
載っている「計」の行と突き合わせている**(許容ずれ0.5%)。一致しない用途は
採用せず、理由を `notes` に残す。今回は全用途が一致した。

## 4. 検証結果(過去実績軸との比較・補完関係)

> ## ⚠ この節の結論は撤回されました(2026年9月21日)
>
> **撤回する主張:** 「業界一般統計軸を追加するだけで、階層3から階層2
> (仮採用+抜き取り監査)に到達した」(下記ケースB)。
>
> **撤回の理由:** この検証は `tests/test_industry_statistics_integration.py` の
> **架空スナップショット**(項目名 `door_count`、単位 `箇所/物件`、検証用の
> 架空値)に依存していました。実データのスナップショットには `door_count`
> という項目が存在しないため、同じ呼び出しは `status="abstained"` になり、
> **階層2には到達しません**(実測で確認)。
>
> さらに悪いことに、実データの**金額**項目を同じ経路に流すと、階層2への
> 昇格が**成立してしまいます**。
>
> ```
> 強い軸(画像軸)     : door_count = (4, 4)      ← 個数
> 過去実績軸(弱い)    : door_count = (3, 5)      ← 個数
> 業界一般統計軸(弱い) : 住宅 計   = (3, 246)    ← 万円/件
> → tier = 2 / provisional_audit
> ```
>
> 「3〜246万円」という金額のレンジが「建具4本」を支持したと判定されています。
> `AxisEvidence` に単位のフィールドが無く、階層2の昇格判定
> (`_has_two_agreeing_advisory_sources`)がレンジの数値の重なりだけを見るためです。
> **つまりケースBの「補完関係」は、単位の取り違えによって成立していた
> 見かけ上の成果でした。**
>
> **現在の状態:** この昇格を実行する公開経路は削除されました
> (`axes/industry_statistics_axis/reading.py` を削除、`ALLOWED_AXES` から
> `"statistical"` を除外)。この軸は階層を上げることに寄与しません。
> 代わりに出口検査として、**階層を下げることだけ**ができます
> (`docs/design_v8.md` 5-2節)。
>
> **残っている問題:** 単位を検査しないという欠陥自体は、この軸を外しても
> 全軸に残ります。最優先課題として
> `docs/top_priority_unit_safety_defect.md` に切り出しました。
>
> 以下は撤回前の記録です。**結論としては使えません**が、何を確認して何を
> 見落としたかの記録として残します。

**過去実績軸には専用モジュールが存在しない**ため(既存コードでも
`AxisEvidence(axis_id="history", ...)`を直接組み立てる運用)、比較検証でも
同じ流儀で表現した。

### ケースA: 強い軸1つ + 過去実績軸(弱い、1つ)のみ

```
tier=3, action=requires_review
理由: 「自動確定に必要な独立した強いデータ源が2つ未満」
```

過去実績軸が「サンプル不足で弱い」という課題どおり、単独では階層3のまま
にとどまる。

### ケースB: 強い軸1つ + 過去実績軸 + 業界一般統計軸(両方とも弱い、独立)

```
tier=2, action=provisional_audit
理由: 「強い独立データ源1つを、異なる弱いデータ源2つ以上が支持」
independent_advisory_source_count = 2
```

**業界一般統計軸を追加するだけで、階層3から階層2(仮採用+抜き取り監査)に
到達した。** これが「両者がどう補完し合うか」の具体的な答えである。
過去実績軸(自社データ)と業界一般統計軸(業界全体の統計)は、大元の
データ源が別であるため、v8の独立性判定(3-3節)上「独立した弱い軸」
として別々に数えられ、**2つ揃って初めて階層2の条件(複数の弱い軸の支持)
を満たす。** 業界一般統計軸1つだけでは(過去実績軸が無ければ)同じ理由で
階層2には届かない。

### 確定するレンジの値そのものには影響しない

ケースA・ケースBのどちらでも、確定するレンジ(`confirmed_range`)は
強い軸の値`(4, 4)`のまま変わらなかった。**弱い軸がいくら支持しても、
候補を排除したり値を変えたりする権限は持たない**という設計どおりの
動作を確認した。

### 補完は無条件の足し算ではない

強い軸の値と弱い軸2つの範囲が大きく乖離しているケース(強い軸=10、
過去実績軸・業界統計軸ともに3〜6のレンジ)では、業界統計軸を追加しても
階層2には到達しなかった(方向が一致していないため)。**「弱い軸を2つ
揃えれば自動的に階層2になる」わけではなく、範囲が重なって初めて効く**
ことを確認した。

## 7. 出口検査「合計金額サニティチェック」の仕様

実装: `arbitration/total_amount_sanity_check.py`
設計上の位置づけ: `docs/design_v8.md` 5-2節
閾値の根拠と集計方法: `docs/proposal_industry_statistics_repositioning.md` 3節
(`python -m benchmarks.analyze_amount_distribution` で再現できます)

### 7-1. 走るタイミングと権限

数量が確定し、単価を掛けて見積もり合計金額が出た**後**に、1回だけ走ります。
軸間照合(`AxisQualityFirewall.assess()`)には参加しません。

**権限は非対称です。** `TotalAmountVerdict.applied_tier(tier)` は、
`forces_review=True` のとき 3 を返し、それ以外は与えられた `tier` を
そのまま返します。**階層を上げる経路は型として存在しません。** 分布の
真ん中に入っていることは「桁が合っている」以上の意味を持たないためです。

### 7-2. 判定

| ステータス | 条件 | `forces_review` |
|---|---|---:|
| `beyond_statistics` | 上限の無い最上位階級(住宅3,000万円以上 / 非住宅5億円以上)に落ちた | **True** |
| `high_outlier` | 第99パーセンタイルを超えた | **True** |
| `within_distribution` | それ以外(下振れもここに入る) | False |
| `abstained` | 単位違い・新築・用途不明・プレースホルダー・閾値なし・負の金額 | False |

住宅 計(中央値31.7万円)での実測:

| 合計金額 | 判定 | 階層1→ |
|---:|---|---:|
| 0.5万円 | `within_distribution` | 1 |
| 31.7万円 | `within_distribution` | 1 |
| 796.7万円(=p99) | `within_distribution` | 1 |
| 800.0万円 | `high_outlier` | **3** |
| 3,000.0万円 | `beyond_statistics` | **3** |

### 7-3. 検出できないこと(設計上の明示)

* **下振れ(安すぎる方向)は検出しません。** 最下位階級が全体の 59〜82% を
  占め、その内側の分布が統計に載っていないため、`low`(第5パーセンタイル)は
  階級内一様分布の仮定だけから出た値です。`0.5万円` でも
  `within_distribution` を返すのは、この制約をそのまま反映したものです
* **「桁違い=中央値の10倍」は閾値になりません。** 中央値の10倍を超える工事が
  実在で 2.7〜11.9% あります。そのため閾値は第99パーセンタイル
  (用途により中央値の17〜79倍)にしています
* **新築工事には適用できません**(統計がリフォーム・リニューアルの受注額)。
  `work_kind="new_construction"` は `abstained` を返します
* **1件の工事の受注額**なので、複数工事をまとめた見積もり・1件を分割した
  見積もりには適用できません
* **単位は読み替えません。** `unit` が `万円` 以外なら `abstained` を返します。
  黙って読み替えることが、この修正の発端そのものだったためです

### 7-4. 閾値はスナップショットに入っている(手書きの数値ではない)

`IndustryMetric` に3つのフィールドを追加し、`fetch.py` が原本の階級分布から
計算します。

| フィールド | 内容 |
|---|---|
| `high_outlier_threshold` | 第99パーセンタイル |
| `beyond_statistics_threshold` | 上限の無い最上位階級の下限 |
| `bottom_band_share` | 最下位階級が全体に占める割合(下振れを判定しない根拠) |

`test_shipped_snapshot_is_reproducible_from_the_shipped_source` が、
スナップショットが原本から機械的に再生成できることを縛っているため、
**手で書いた閾値が紛れ込めばテストが落ちます。**
