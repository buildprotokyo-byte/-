## 1. データ取得可否の確認結果(e-Statへの到達可否、データ形式)

**到達できました。**(2026年9月21日実測)

| 対象ホスト | 結果 |
|---|---|
| `https://www.e-stat.go.jp/` | **200** |
| `https://www.mlit.go.jp/` | **200** |
| `https://api.e-stat.go.jp/`(ルートパス) | 403(CDN=ZENEDGE がルートを拒否) |
| `https://api.e-stat.go.jp/rest/3.0/app/json/getStatsList?...` | **200**(中身は「認証に失敗しました。アプリケーションIDを確認して下さい。」) |

api.e-stat.go.jp のルートパスの403は**通信の遮断ではなく、CDNがルートURLを
返さない**というだけです。REST APIのエンドポイント自体は200を返しており、
中身はアプリケーションID未指定の認証エラーでした。つまり**ネットワークは
通っており、APIを使うにはe-Statのユーザー登録(appId取得)が必要**という状態
です。

### appIdを取らずに済ませた方法

e-Statの**ファイルダウンロード**(`https://www.e-stat.go.jp/stat-search/file-download?statInfId=...&fileKind=0`)
は**アプリケーションID不要**で、統計表の .xlsx をそのまま取得できます。
今回はこちらを使いました。appIdの取得をおーちゃんに依頼する必要はありません。

**分布そのもの(階級ごとの件数)を持っているのは、次の2表だけでした。**

## 2. 実装内容(インターフェース、スナップショット方式)

### ディレクトリ構成

```
axes/industry_statistics_axis/
├── __init__.py
├── snapshot.py       # スナップショットの保存・読み込み
├── reading.py        # SymbolCountReading互換の読み取り結果への変換
├── fetch.py          # e-Statからの取得・パース・スナップショット生成(ステップ0)
├── _xlsx.py          # 標準ライブラリだけの最小xlsxリーダー(ステップ0)
├── sources/
│   └── 2025fykeirr_e-stat_excel.xlsx   # e-Statから取得した原本(272KB)
└── snapshots/
    └── 2026-09-21.json                  # 実データ15項目(is_placeholder=False)
```

原本(.xlsx)もリポジトリに入れてあります。スナップショットのJSONが原本から
機械的に再生成できることをテストで確かめるためで、**手で書いた数値が紛れ
込んでいたらテストが落ちます**(`test_shipped_snapshot_is_reproducible_from_the_shipped_source`)。

### スナップショット方式(`snapshot.py`)

`StatisticsSnapshot`は、`source_name`・`source_url`・**`fetched_at`(取得日)**・
`period_covered`(統計データ自体が対象とする期間)・`metrics`(項目名→
`IndustryMetric`)・`is_placeholder`を持つ。`save_snapshot()`/`load_snapshot()`/
`load_latest_snapshot()`でJSONとしてローカルに保存・読み込みする。

指示書どおり、**「取得のたびに最新を見に行く」処理は実装していない。**
取得(ネットワークアクセスを伴うスクリプト)は別工程として想定しており、
今回は「保存済みのスナップショットを読み込む」側だけを実装した
(取得スクリプト自体は5節「制約」で述べるとおり、ネットワークが使える
環境でないと書いても検証できないため、今回は実装を見送っている)。

同梱している既定スナップショットは `2026-09-21.json`(`is_placeholder=False`、
15項目)。**中身は1節のe-Stat原本から生成した実データで、架空の数値は
含まれていない。**

同じ取得日に実データとプレースホルダーが並んだ場合、`load_latest_snapshot()`
は**実データの方を返す**(`(fetched_at, not is_placeholder)` で比較)。
中身の無いスナップショットを黙って掴まないようにするため。

### 取得スクリプト(`fetch.py`)— ステップ0で追加

`python -m axes.industry_statistics_axis.fetch` で、e-Statから原本を
ダウンロードし、パースし、スナップショットを保存する。`--offline` を付けると
ダウンロードせず同梱の原本から作り直す(テストとCI用)。

**openpyxl は使っていない。** この実行環境からは pypi.org に到達できず
(2026-09-21実測、直接・プロキシ経由とも403)、インストールできないため。
`_xlsx.py` に zipfile + xml.etree だけの最小リーダーを書いた。ふりがな
(`<rPh>`)を本文と一緒に拾うと「住宅ジュウタク」のように連結してしまうので、
明示的に取り除いている。

### 実データから「あり得る値の範囲」を作る方法

表4-1・表4-2 は「金額階級 × 用途」の受注件数の表なので、用途ごとに
**階級分布からパーセンタイル**を計算した。

| 出力 | 値 |
|---|---|
| `low` | 第5パーセンタイル |
| `typical` | 中央値 |
| `high` | 第95パーセンタイル |
| `unit` | `万円/件` |

階級の内側は一様分布を仮定した線形内挿で求めている。**最上位階級は上限が
無い**(「3,000万円以上」「5億円以上」)ので、第95パーセンタイルがそこに
落ちる用途は、**上限を捏造せずにその項目ごと落とす**(`percentile()` が
`None` を返し、`build_metrics()` が理由を `notes` に記録する)。今回の
データでは該当した用途は無かった。

読み取りが崩れていないことの担保として、**階級ごとの件数の合計を、表に
載っている「計」の行と突き合わせている**(許容ずれ0.5%)。一致しない用途は
採用せず、理由を `notes` に残す。今回は全用途が一致した。

### SymbolCountReading互換の出力(`reading.py`)

`reading_for_metric(snapshot, metric_name)`が、指定した項目の統計値を
`axes/image_axis/grounding_dino_adapter.py`の`SymbolCountReading`
そのもの(サブクラスや独自互換型ではなく、同一のデータクラス)として返す。

- 項目がスナップショットに存在する場合: `count_range`はその項目の
  `[low, high]`を整数に丸めたもの、`status="low_confidence"`
- **項目が存在しない場合(既定スナップショットは常にこれに該当): 架空の
  数値を作らず`status="abstained"`を返す。**v8の「分布外の軸はレンジを
  主張せず棄権する」の実践

### 恒久的に補助専用であることの保証(3重のガード)

`axis_evidence_for_metric(snapshot, metric_name, target=...)`が、
`arbitration/axis_quality_firewall.py`にそのまま渡せる`AxisEvidence`を作る。
この軸を「過去実績軸と同様、恒久的に補助専用」にするため、次の3つを
**呼び出し側の引数として公開せず、常に固定値**にした。

1. `strength = "weak"`(ハードな制約の計算対象から外れる)
2. `status`は`"confident"`にならない(データがあれば`"low_confidence"`、
   無ければ`"abstained"`)
3. `calibrated = False`(全国平均であって個別案件への実測校正ではない)

`is_hard_eligible`(強い軸として認められる条件)は「`strength=="strong"`
かつ`status=="confident"`かつ`calibrated`」の3条件全てを要求するため、
上記3つのうちどれか1つが将来誤って崩れても、残り2つが防波堤になる設計
にしている。

## 3. 軸品質ファイアウォールへの統合結果(補助専用としての参加制限の確認)

**過去実績軸専用の「参加禁止」の仕組みというコードは、リポジトリには
存在しなかった。** `axis_quality_firewall.py`を確認したところ、過去実績軸
(`axis_id="history"`)は特別扱いされておらず、`AxisEvidence.strength`
(汎用の「強い/弱い」フラグ)だけで補助専用が実現されている。指示書が
「過去実績軸と同様の参加禁止の仕組みがそのまま使えるはず」と述べていた
とおり、**この汎用の`strength="weak"`の仕組みをそのまま使えた。**

確認したテスト(`tests/test_industry_statistics_axis.py`):

- `axis_evidence_for_metric()`が返す`AxisEvidence`は常に
  `strength="weak"`・`status != "confident"`・`calibrated=False`
- `axis_evidence_for_metric`のシグネチャに`strength`/`calibrated`を渡す
  経路がそもそも存在しないこと(`inspect.signature`で確認)
- ランダムな範囲・単位の統計値200件で、`is_hard_eligible`が常に`False`
  になること
- `AxisQualityFirewall.assess()`にこの軸の証拠**単体**を通しても、
  階層1・2には到達せず、常に階層3(要確認)になること

## 4. 検証結果(過去実績軸との比較・補完関係)

**過去実績軸には専用モジュールが存在しない**ため(既存コードでも
`AxisEvidence(axis_id="history", ...)`を直接組み立てる運用)、比較検証でも
同じ流儀で表現した。

### ケースA: 強い軸1つ + 過去実績軸(弱い、1つ)のみ

```
tier=3, action=requires_review
理由: 「自動確定に必要な独立した強いデータ源が2つ未満」
```

過去実績軸が「サンプル不足で弱い」という課題どおり、単独では階層3のまま
にとどまる。

### ケースB: 強い軸1つ + 過去実績軸 + 業界一般統計軸(両方とも弱い、独立)

```
tier=2, action=provisional_audit
理由: 「強い独立データ源1つを、異なる弱いデータ源2つ以上が支持」
independent_advisory_source_count = 2
```

**業界一般統計軸を追加するだけで、階層3から階層2(仮採用+抜き取り監査)に
到達した。** これが「両者がどう補完し合うか」の具体的な答えである。
過去実績軸(自社データ)と業界一般統計軸(業界全体の統計)は、大元の
データ源が別であるため、v8の独立性判定(3-3節)上「独立した弱い軸」
として別々に数えられ、**2つ揃って初めて階層2の条件(複数の弱い軸の支持)
を満たす。** 業界一般統計軸1つだけでは(過去実績軸が無ければ)同じ理由で
階層2には届かない。

### 確定するレンジの値そのものには影響しない

ケースA・ケースBのどちらでも、確定するレンジ(`confirmed_range`)は
強い軸の値`(4, 4)`のまま変わらなかった。**弱い軸がいくら支持しても、
候補を排除したり値を変えたりする権限は持たない**という設計どおりの
動作を確認した。

### 補完は無条件の足し算ではない

強い軸の値と弱い軸2つの範囲が大きく乖離しているケース(強い軸=10、
過去実績軸・業界統計軸ともに3〜6のレンジ)では、業界統計軸を追加しても
階層2には到達しなかった(方向が一致していないため)。**「弱い軸を2つ
揃えれば自動的に階層2になる」わけではなく、範囲が重なって初めて効く**
ことを確認した。

## 5. 制約・うまくいかなかった点

1. **この環境では既存の回帰テストを実行できませんでした。** pypi.org・
   files.pythonhosted.org への到達が遮断されており(2026-09-21実測、直接
   ・プロキシ経由とも403)、`pytest`・`z3-solver`・`numpy`・`opencv-python-headless`
   のどれもインストールできません。`reading.py` は `arbitration.axis_quality_firewall`
   経由で `z3` を読み込むため、**この軸の既存テスト(17件)も含めて
   import の時点で失敗します。**
   ステップ0で追加した `tests/test_industry_statistics_fetch.py`(26件)は
   標準ライブラリだけで完結するので実行でき、**26件すべてパスしました**
   (pytestが無いため、`approx`/`raises`/`parametrize`/`fixture`/`tmp_path`
   だけを実装した最小のランナーで実行しています。pytest本体での確認は
   できていません)。**既存241件の再実行は未実施です。**
   → **おーちゃんへの依頼: 許可ドメインに `pypi.org` と
   `files.pythonhosted.org` を追加していただけると、この環境で回帰テストを
   回せるようになります。**
2. **金額階級の分布を持つ表は2つだけでした。** 1節のとおり、他の20表は
   合計か平均しか持たず、そこから正直なレンジは作れません。したがって
   この軸が現時点で答えられるのは**「個別工事の受注額(万円/件)」だけ**で、
   建具の個数・部材の数量といった積算そのものの数量には、まだ一切答えられ
   ません(該当項目は `abstained` のまま)。
3. **`quantity_scale`(連続量→整数個数への変換係数)の妥当な決め方は、
   実データを見た後でもまだ決まっていません。** 「受注額(万円)」を
   「窓が何本」に変換する係数には、この統計だけでは根拠がありません。
   面積あたりの単価など、別のデータ源との突き合わせが要ります。
4. **参考表1-7〜1-9 には「主たる工事部位別の平均受注額(千円/件)」があり、
   工事部位(屋根・外壁・内装・外部建具・設備)ごとの相場が分かります。**
   積算の対象要素に一番近いのはここですが、**平均値しか無く分布が無い**
   ため、今回は取り込んでいません。取り込むならレンジの広がりを別途
   仮定することになり、それは実データではなく推測になります。
5. **代表数量の丸め方(floor/ceil)が統計的に最も適切かは、依然として
   未検証です。** レンジが実際より広がる方向にしか丸めないので保守的
   (安全側)ではあります。
6. **階級内を一様分布と仮定しています。** 実際には階級の下側に偏って
   いるはずなので、`low`・`typical` はやや高めに出ている可能性があります。
   最下位階級(0〜50万円)は特にその影響を受けます。
7. **四半期報・半期報は取り込んでいません。** 年度次だけを対象にしました。
   更新は年1回(6月頃)で、四半期ごとに見に行く必要はありません。
8. **スナップショットの更新運用は、まだ運用ルールとして未確定です。**
   仕組み(`fetch.py` と `save_snapshot`)は揃いました。年度次の公表が
   年1回なので、年1回の実行で足ります。
