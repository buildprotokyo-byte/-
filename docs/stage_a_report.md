## 2. Grounding DINOの実装・検証結果

### 実装したもの

`axes/image_axis/grounding_dino_adapter.py`。構造は2層に分けました。

1. **バックエンド**(モデルの生スコアを取り出す層)
   - `HuggingFaceGroundingDinoBackend` … 本番用。重みが取れない環境では**黙って0件を返さず、
     `RuntimeError` を送出します**(「検出できなかった」と「動かせなかった」を混同させないため)
   - `StaticBackend` … しきい値規則のテスト用
2. **アダプタ**(生スコアを v8 の確信度ステータスとレンジに変換する層)

この分離により、**モデルが手元で動かせない環境でも、変換規則の側は完全に検証できます**。

### 確信度ステータスへの対応づけ(提案)

記号カテゴリごとに、受理しきい値 `box_threshold` / `text_threshold`(実装詳細設計書の実例値は
0.30 / 0.25)に加えて、**余裕幅 `confident_margin`(既定 0.15)**を持たせます。

| 検出1件ごとの条件 | 個別の扱い | 軸の出力への寄与 |
|---|---|---|
| 両スコアが「しきい値 + 余裕幅」以上 | confident | レンジの下限・上限の両方に数える |
| 両スコアがしきい値以上、ただし余裕幅未満 | low_confidence | レンジの**上限だけ**に数える |
| どちらかがしきい値未満 | rejected | 数えない |

軸全体のステータスは次のように決めます。

- 受理された検出が1件もない → **`abstained`(棄権)**。v8 の「分布外の軸はレンジを主張せず棄権する」に対応し、**「0個」と断定しません**
- 受理はされたが confident が0件 → `low_confidence`
- confident が1件以上あり、low_confidence の件数がそれを超えない → `confident`
- confident はあるが low_confidence の方が多い → `low_confidence`(候補が割れている状態を confident と呼ばない)

### 出力の形

単一値ではなく **`count_range = (confident件数, confident+low_confidence件数)`** というレンジと、
根拠(適用した閾値、生の検出数、棄却数、使ったバックエンド)を返します。v8 の
「各軸は単一値ではなく『あり得る範囲+根拠』を出す」(3-2 多軸レンジ収束)にそのまま乗ります。

### ⚠️ 検証したこと・できなかったこと

> ここで「未実施」としている比較は、**9-3 で実施済み**です。

- **できたこと**: 上記の変換規則を22件のテストで固定しました。しきい値の上書きによる
  チューニング、レンジの単調性(下限 ≤ 上限)、棄権の発火条件、重みが取れないときに
  例外を出すこと、まで含みます
- **できなかったこと**: **実際の記号検出は1件も行っていません。**したがって
  「これまでの古典的画像処理・汎用AI単体との検出精度の比較」は**未実施**です。
  この比較は、重みが手に入るまで保留になります

## 3. VTracerの実装・検証結果

### 実装したもの

`axes/image_axis/vtracer_vectorizer.py`。

- `vectorize()` … VTracer に掛けて SVG を得て、`<path>` ごとの輪郭を取り出す
  (Python バインディングには CLI の `--preset bw` がないため、相当する `colormode="binary"` を
  `BW_PRESET` としてまとめました)
- `VectorDrawing.to_mask()` … ベクターをラスターに描き戻す
- `measure_linework()` … Zhang-Suen 細線化で芯線を取り、総延長・連結成分数・平均線幅を測る
- `binarize_classical()` … 比較対象の古典的前処理(メディアンフィルタ + 大津の二値化)

### 実験の組み方

**下流の読み取りアルゴリズムを固定し、前処理だけを差し替えました。**こうすると
「VTracer を挟んだことによる差」だけが切り出せます。比較した3パイプラインは次のとおりです。

1. `classical` … 古典的画像処理のみ。メディアンのカーネルを 1 / 3 / 5 で振り、**最も良かったものを
   ベースラインの成績とする**(ベースラインを不当に弱くしないため)
2. `vtracer` … グレースケール画像をそのまま VTracer に入れる
3. `otsu+vtracer` … 大津の二値化をかけてから VTracer に入れる

線長は「壁部」(太い線)と「記号部」(細い線)に分けて測りました。劣化した図面では
この2つで壊れ方がまったく違うためです。

### 結果(各劣化レベルでの最良同士)

| 劣化 | パイプライン | 設定 | 壁部の誤差 | 記号部の誤差 | 連結成分数 |
|---|---|---|---|---|---|
| なし | 古典 | median=1 | -7.6% | +29.1% | 1 |
| なし | VTracer | fs=4 | -7.7% | **+2.9%** | 1 |
| なし | 大津→VTracer | fs=4 | -7.7% | **+2.9%** | 1 |
| 軽度 | 古典 | median=1 | -7.9% | +2.3% | **43** |
| 軽度 | VTracer | fs=0 | -7.7% | -61.0% | 20 |
| 軽度 | 大津→VTracer | fs=0 | -7.7% | **-6.0%** | **8** |
| 中度 | 古典 | median=1 | +7.9% | -37.2% | **902** |
| 中度 | VTracer | fs=0 | -7.3% | -68.7% | **5** |
| 中度 | 大津→VTracer | fs=0 | -7.8% | -57.1% | 23 |
| 重度 | 古典 | median=3 | -4.9% | -62.5% | 43 |
| 重度 | VTracer | fs=0 | -28.9% | -86.0% | 171 |
| 重度 | 大津→VTracer | fs=0 | **-4.0%** | -68.7% | **18** |

参考: 重度で古典 median=1(ノイズ除去なし)を使うと、壁部 **+117.7%**、連結成分 **2,811個** になります。

壁部の誤差が全パイプラインで一律 -7〜-8% あるのは、正解値(壁の芯線の単純合計)が
壁の交点で重複を持つのに対し、細線化した芯線は交点を1点に潰すためで、**系統的な偏りです。
全パイプラインに等しく乗るので、手法間の比較には影響しません。**

### 分かったこと

1. **VTracer の内蔵二値化が弱点です。**グレースケールをそのまま入れると、軽度の劣化でも
   記号部の線を6割以上失います(-61.0%)。**先に大津の二値化をかけてから VTracer に入れる**と、
   同じ条件で **-6.0%** に改善しました。パイプラインの組み方だけで解消できる問題です
2. **重度劣化では VTracer が明確に勝ちます。**古典的画像処理だけでは
   「ノイズを残して偽の図形が2,811個」か「ノイズを消して記号も消す」の二択ですが、
   大津→VTracer なら偽の図形18個・壁部 -4.0% という、どちらも成立する点に着地します
3. **記号の読み取りには使えません。**どのパラメータでも、劣化した図面では
   開き戸の円弧や窓の細線を6〜7割失います。これは3×3のメディアンフィルタが
   1画素幅の線を消すのと同じ現象です(この性質はテストで固定してあります)

### パラメータの推奨

- `filter_speckle` は **0〜4**。8以上で記号が、16で図面そのものが消えます
- `mode` は `spline` / `polygon` のどちらでも差はほぼありません(0.1ポイント以内)
- `length_threshold` / `corner_threshold` は、今回の条件では結果に影響しませんでした
- **必ず先に二値化してから VTracer に渡すこと**

## 4. IfcOpenShellのcontainment APIの実装・検証結果

### 実装したもの

`axes/absolute_rule_axis/ifc_containment.py`。

- `SpatialModel` … `aggregate.assign_object()` で Project → Site → Building → Storey → Space を組み、
  `spatial.assign_container()` で物理要素(壁・戸・窓)を空間に収める
- `build_from_reading()` … 読み取り結果(部屋名と要素のリスト)から階層を一気に構築
- `audit()` … 階層上の異常を洗い出す

**IFC ファイルとして書き出し、読み直せることを確認済み**です(IFC4 形式)。

### 検出できる矛盾

| 種類 | 内容 | 根拠 |
|---|---|---|
| `orphan_element` | どの空間にも属していない物理要素 | IFC の構造そのものの破れ |
| `orphan_space` | どの階にも属していない部屋 | 同上 |
| `empty_storey` | 部屋も要素も持たない階 | 同上 |
| `door_without_space` | 部屋ではなく階に属している開き戸 | どの部屋の出入口か決まらない |
| `space_without_door` | 出入口を1つも持たない部屋 | 建築上の前提 |
| `space_without_window` | 採光開口を1つも持たない居室 | 建築基準法の採光規定 |

`space_without_window` は居室にしか適用できない(納戸・便所等には当てはまらない)ため、
`require_window=False` で切れるようにしてあります。

### 一気通しの効果測定

画像の読み取り → IFC 空間階層への登録 → 矛盾検出、を通しで走らせました。

**正直な制約**: Grounding DINO が使えないため、**記号の認識そのものは行っていません。**
代わりに「正解の記号位置に、前処理後のマスクでインクがどれだけ残っているか」を測り、
正解のインク量の50%を下回ったものを「読めなかった」と扱っています。つまりここで
測っているのは認識器の性能ではなく、**前処理が記号を消したかどうかと、消えたことを
絶対ルール軸が検出できるか**です。

| 劣化 | 前処理 | 読めた戸 | 読めた窓 | 見落とし | 検出した矛盾 |
|---|---|---|---|---|---|
| なし | 古典(median=1) | 4 | 4 | 0 | 0 |
| なし | 古典(median=3) | 4 | 0 | 4 | **4** |
| なし | 大津→VTracer | 4 | 4 | 0 | 0 |
| 軽度 | 古典(median=1) | 4 | 4 | 0 | 0 |
| 軽度 | 古典(median=3) | 4 | 0 | 4 | **4** |
| 軽度 | 大津→VTracer | 4 | 4 | 0 | 0 |
| 中度 | 古典(median=1) | 4 | 3 | 1 | **1** |
| 中度 | 古典(median=3) | 4 | 0 | 4 | **4** |
| 中度 | 大津→VTracer | 4 | 0 | 4 | **4** |
| 重度 | 古典(median=1) | 4 | 4 | 0 | 0 |
| 重度 | 古典(median=3) | 4 | 0 | 4 | **4** |
| 重度 | 大津→VTracer | 4 | 0 | 4 | **4** |

**見落とした記号25件のうち、25件すべてが矛盾として表に出ました(検出率100%)。**

### この100%をそのまま信じてはいけない理由

今回の図面は**各室に戸1つ・窓1つ**という構成です。この条件では、記号を1つでも落とせば
必ずどこかの部屋が「戸なし」または「窓なし」になるため、**検出率が100%になるのは
ほぼ自動的です。**

**1つの部屋に窓が2つある図面で、そのうち1つを読み落とした場合、このルールでは検出できません。**
つまり今回測れたのは「このルールが機能すること」であって、「このルールで十分なこと」ではありません。
数量の正確さ(窓が何個あるか)を守るには、別の独立した証拠が必要です。

なお、開き戸は4段階すべての劣化条件で1つも失われませんでした(戸の線は窓より長く、
壁から離れているため)。**今回発火した矛盾はすべて窓の読み落としによるものです。**

## 5. 3リソース導入による全体への効果

### 導入前後の変化

**精度について。**壁のような太い線の幾何は、重度劣化で **+117.7% → -4.0%** に改善しました
(古典 median=1 → 大津→VTracer)。一方、記号の線はどのパイプラインでも劣化とともに失われ、
**VTracer では改善しませんでした。**

**効率について。**測れていません。今回は自動化率・監査コストといった運用側の指標を
扱う段階まで到達していないためです(トライアル8・9の指標系には接続していません)。

**「劣化に気づけるかどうか」については、はっきり改善しました。**従来は記号が消えても
読み取り側からは分からず、v8 の「穴1: 情報の欠落」がそのまま「穴2: 尤もらしい誤り」に
転化していました。IFC の空間階層に載せると、**消えたことが `space_without_window` という
明示的なフラグになります。**これは精度の改善ではなく、**沈黙した誤りを、人に確認を
仰ぐべき要素(v8 の階層3)に変換する**という改善です。

### 3リソースの役割分担(実測から分かったこと)

段階Aの3つは競合せず、**補完関係**にあることが実測で確認できました。

| リソース | 担当 | 担当しない |
|---|---|---|
| VTracer | 壁など太い線の幾何を、絶対ルール軸に渡せる形に整える | 記号の読み取り(むしろ壊す) |
| Grounding DINO | ⚠️ ~~記号の検出(未検証)~~ → **担当できない**(9-3・9-4) | 線の幾何 |
| IfcOpenShell | 読み取り結果の包含関係の検証と、欠落の顕在化 | 読み取りそのもの |

**VTracer を記号検出の前段に置いてはいけない**というのが、今回いちばん実務に効く知見です。

### v8 設計への反映提案

1. **画像軸を「線の幾何」と「記号の認識」の2系統に明示的に分け、前処理を別々にする。**
   同じ前処理を共有すると、片方に最適な処理がもう片方を壊します
2. **絶対ルール軸に「空間包含の健全性チェック」を正式に位置づける。**読み取り漏れを
   沈黙させず階層3へ回す経路として機能することが確認できました
3. **記号数の正確さを守るルールを別途設計する。**「各室に戸1・窓1」型のルールは
   「1つもない」ことしか検出できず、個数の誤りは素通りします(v8 の「穴2」そのもの)

## 9-2. 測り方

積算で効くのは「記号がどこにあるか」よりも**「何個あるか」**(建具の個数がそのまま

比較する2つ:

1. **古典的画像処理(テンプレートマッチング)** — 記号のテンプレートを**正解の図形そのもの

   メディアンカーネル(1/3/5)と判定しきい値(0.20〜0.98)を振って、**各条件での最良 F1 を
   古典側の成績としました。**つまり古典側には「探すべき図形の正確な形・寸法・向き」を
   事前に与えています。ベースラインとしてはかなり有利な条件です
2. **Grounding DINO(ゼロショット)** — 図形の形は一切教えず、テキストプロンプトだけ。

## 9-4. 根本原因: スコアが正解と逆相関している

しきい値の調整で救えるかどうかを確かめるため、既定プロンプトでの生スコアを、
**正解記号と重なる検出**と**重ならない検出**に分けて見ました。

| 劣化 | 種別 | 生の検出数 | うち正解と重なる | 重なる検出の最高スコア | **重ならない検出の最高スコア** |
|---|---|---|---|---|---|
| なし | 戸 | 78 | 6 | 0.039 | **0.317** |
| なし | 窓 | 89 | 10 | 0.061 | **0.297** |
| 軽度 | 戸 | 80 | 6 | 0.038 | **0.388** |
| 軽度 | 窓 | 58 | 9 | 0.086 | **0.361** |
| 中度 | 戸 | 91 | 16 | 0.057 | **0.314** |
| 中度 | 窓 | 81 | 7 | 0.074 | **0.292** |
| 重度 | 戸 | 96 | 28 | 0.085 | **0.322** |
| 重度 | 窓 | 87 | 1 | 0.024 | **0.298** |

**全8条件で、正解に当たっている検出の最高スコアが、外している検出の最高スコアを
一度も上回っていません。**差は 3〜10 倍あります。

これは単に精度が低いのではなく、**モデルの確信度が正しさと逆を向いている**という
ことです。結果として:

- **しきい値を上げるほど成績が悪くなります。**高スコア側に残るのは外している検出だからです
- 実際、最良成績が出るしきい値は**全条件で 0.05〜0.10**という、ほぼ「切っていない」値でした

高スコアの正体を見ると、**図面全体を囲む1つの大きな矩形**でした
(例: 劣化なし・戸、スコア 0.317、箱 =(56, 57, 705, 461) — 図面の外周そのもの)。
Grounding DINO は建築記号という概念を持たず、**図面という画像の中でいちばん
「物体らしい」矩形、すなわち間取りの外形や部屋の矩形を掴んでいます。**

本文 2 章で提案した対応づけを、そのまま実データに適用しました。

| 劣化 | 種別 | count_range | 正解 | レンジが正解を含むか | status |
|---|---|---|---|---|---|
| なし | 戸 | (0, 1) | 4 | **×** | low_confidence |
| なし | 窓 | (0, 0) | 4 | **×** | abstained |
| 軽度 | 戸 | (0, 1) | 4 | **×** | low_confidence |
| 軽度 | 窓 | (0, 1) | 4 | **×** | low_confidence |
| 中度 | 戸 | (0, 1) | 4 | **×** | low_confidence |
| 中度 | 窓 | (0, 0) | 4 | **×** | abstained |
| 重度 | 戸 | (0, 1) | 4 | **×** | low_confidence |
| 重度 | 窓 | (0, 0) | 4 | **×** | abstained |

**8条件すべてでレンジが正解を外しました。**しきい値 0.30 を超える検出は各条件で
ちょうど1件しか残らず、**その1件は8条件すべてで偽陽性(図面外形の矩形)**でした。

読み取り方は2つあり、どちらも設計に効きます。

**評価できる点: 実装は正しく動いています。**`confident` を一度も名乗らず、
3条件では `abstained` を返しました。「0個」と断定もしていません。
v8 の「分布外の軸はレンジを主張せず棄権する」がそのとおりに発火しています。
**規則の側に欠陥はありません。**

**評価できない点: その棄権は「偶然」です。**スコアが全体に低いから棄権しているだけで、
**「自分が外している」ことを検知して棄権しているのではありません。**現に、
しきい値を超えた唯一の検出は毎回間違いでした。つまり**この軸は、口を開けば必ず嘘を言う**
状態です。スコアの絶対値がたまたま低かったおかげで助かっているにすぎません。

**設計上の含意: 閾値方式は「スコアが正しさと同じ向きを向いている」ことを暗黙の前提に
しています。**Grounding DINO は図面ドメインでこの前提を満たしません。
**閾値の調整では直せません。**モデルを替えるか、図面で学習させるか、
軸そのものを外すかのいずれかです。

## 9-7. v8 設計への反映提案(追加)

本文 5 章の3点に加えて、次を提案します。

4. **記号認識の第一候補を「汎用ゼロショット検出モデル」から降ろす。**
   実測上、テンプレート照合という古い手法に全条件で負けます。ただし**テンプレート照合は
   「探すべき形を事前に知っている」ことが前提**で、図面ごとに凡例の違う実物件には
   そのまま使えません。**汎用ゼロショットが駄目でテンプレートが良い、という話ではなく、
   「記号の形を何らかの形で与える経路」が必須だという話です。**現実的な次の手は
   (a) 凡例表から記号テンプレートを自動抽出する、(b) 図面データで検出器を微調整する、
   のいずれかになります
5. **軸を採用する前に「スコアと正しさの向きが揃っているか」を必ず実測する。**
   これは精度の測定とは別の検査です。精度が低い軸は棄権させれば無害ですが、
   **スコアが逆を向いている軸は、確信度階層そのものを壊します**(自信満々に間違える)。
   9-4 の表(正解と重なる検出 / 重ならない検出のスコア分布)が、その検査の雛形です
6. **「個数が合っている」ことを正しさの証拠にしない。**9-3 のとおり、個数がぴったり
   合いながら中身が全滅する事象が実際に起きました。整合性軸で個数を突き合わせる際は、
   **個数だけでなく位置の一致も条件に入れる**必要があります

## 9-9. 追記後の結論

**段階Aの3リソースは、3つとも実測で検証が完了しました。採用の可否は次のとおりです。**

| リソース | 判定 | 理由 |
|---|---|---|
| VTracer | **条件付き採用** | 壁など太い線の幾何に限る。必ず大津の二値化を先にかけ、記号検出の前段には置かない |
| IfcOpenShell | **採用** | 読み取り漏れを明示的な矛盾に変える経路として機能。ただし個数の誤りは素通り |
| Grounding DINO | **不採用** | 全16条件で古典的テンプレート照合に負け、確信度スコアが正しさと逆相関。閾値調整では直らない |

**アダプタの実装(`grounding_dino_adapter.py`)は捨てません。**バックエンドを差し替え
可能にしてあるので、図面で微調整した検出器や凡例由来のテンプレート照合を
同じインターフェースの裏に入れられます。**捨てるのは「汎用ゼロショットモデルを
そのまま記号検出に使う」という選択肢の方です。**

次に進むべきは**段階B(OR-Tools / Z3 による整合性軸)**です。ネットワーク制約は
受けません。加えて、9-7 の 5(スコアと正しさの向きの検査)は、段階B以降で軸を
追加するたびに実施する検査として設計に組み込むことを勧めます。

# 追記(2026年9月21日): トライアル12を受けた、VTracer の位置づけの訂正

本報告書は VTracer を **「壁など太い線の幾何に有効」「記号検出の前段に置いてはいけない」**
という2分類で位置づけてきました(3章・5章・8章・9-9)。**この括り方は粗すぎました。**

Codex 側のトライアル12の追加検証で、**同じ「線の幾何」でも、そこから何の数量を出すかで
VTracer の成績がまったく違う**ことが分かっています。

- **配管ルート延長**: 大きな問題は出ないが、VTracer・スプライン近似・自作の古典的処理
  (robust)の**どれが勝つかは条件によって入れ替わる**
- **床面積**: 劣化が重なる現実的な条件(heavy・realistic)で **VTracer の誤差が
  62.49% まで悪化**。同条件では自作の古典的処理(robust方式相当)の方が一貫して安定

**本報告書が実測したのは、合成図面での「壁部の線長」「記号部の線長」「連結成分数」だけで、
配管ルート延長も床面積も測っていません**(`benchmarks/run_vtracer_eval.py`)。
線が少し欠けても総延長の誤差は線形にしか効きませんが、**面積は境界が1か所途切れただけで
領域が外へ漏れる**ため、壊れ方の大きさが違います。**壁の線長の数値から床面積の信頼性を
外挿していたのが誤りでした。**

したがって次のとおり読み替えてください。

| 本報告書の記述 | 訂正後 |
|---|---|
| 「VTracer は壁の幾何専用の前処理として採用する」(8章1) | **壁など太い線の総延長については**この記述のまま有効。**床面積には適用しない** |
| 9-9 の「VTracer: 条件付き採用 / 壁など太い線の幾何に限る」 | 「太い線の**総延長**に限る」。床面積は**単独でのハードな確定に使わない** |
| 5章「VTracer の担当: 壁など太い線の幾何」 | 同上。配管ルート延長は**単独の採用手法を決めず、複数手法を並行して多軸レンジ収束で統合する** |

**大津の二値化を先にかける前提と、記号検出の前段に置かないという結論は変わりません。**

詳細と既存実装への影響の実測は **v8設計書 12章**を参照してください。
トライアル12の数値は Codex 側の結果であり、**本リポジトリでは再現していません。**
