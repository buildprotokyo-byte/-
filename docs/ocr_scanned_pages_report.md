| 確かめたこと | 現物 | 結果 |
|---|---|---|
| 図面の文字を読む経路は、全部 PDF の埋め込み文字から来ているか | `pdf_vector_symbols.extract_scale` / `find_area_labels`、`pdf_tables.find_tables` | **そのとおり。** どれも `page.get_text()` か `page.find_tables()` で、スキャンのページからは何も返さない |

## 2. 実測(**この報告のいちばん大事な所**)

合成したスキャン(下の 4 節)に、本物の OCR を掛けて測った。
再現手順は `benchmarks/run_ocr_synthetic_eval.py`。元図に 29 語が書かれている。

| 紙の状態 | モデル | 読めた語 | **元図の語がそのまま出てくる** | 時間 |
|---|---|---|---|---|
| きれい | 中国語・英語(既定) | 22 | 22/29 (75.9%) | 4.6秒 |
| きれい | 日本語 | 22 | 15/29 (51.7%) | 3.0秒 |
| 傾き0.7度+粒状 | 中国語・英語 | 22 | 21/29 (72.4%) | 2.3秒 |
| 傾き0.7度+粒状 | 日本語 | 22 | 16/29 (55.2%) | 2.0秒 |
| 傾き1.5度+粒状 | 中国語・英語 | 22 | 21/29 (72.4%) | 2.2秒 |
| 傾き1.5度+粒状 | 日本語 | 22 | 14/29 (48.3%) | 2.2秒 |

### 2-1. モデルによって、強いところが正反対だった

- **中国語・英語のモデル**(RapidOCR の既定)は、数字と記号を全部正しく読んだ
  (`1650` `2000` `780` `WD-01` `1/50`)。一方**日本語の語を中国語の字に化けさせた。**
  出てこなかった語は毎回この 7 つ: `専有延床面積` `施工床面積` `種別` `高さ` `引戸` `折戸` `開き戸`。
  実際の読みは `種別`→`种别`、`引戸`→`引户`、`折戸`→`折户`、`開き戸`→`開老户`、
  `専有延床面積 95.54`→`専有延床面95．54`(**`積` が落ちている**)。
- **日本語のモデル**(PP-OCRv3 japan)は、語を全部正しく読んだ(`種別` `引戸` `折戸`
  `開き戸` `専有延床面積` `施工床面積`)。一方**数字を壊した。**
  `1650`→`16.0`、`2000`→`２ｏｏ`、`95.54`→`ｓｓ・ｓ４`、`1/50`→`１50`。

**片方だけでは足りない。** そして悪いことに、

### 2-2. 確信度は文字化けの見張りにならない

`種別`→`种别` は**確信度 0.99**、`引戸`→`引户` は **0.97** で返ってきた。
確信度の足切りを上げても、この種の化けは 1 件も止まらない。
**「確信度が高いから正しい」と扱ってはいけない。**

### 2-3. 語が丸ごと消える

見出しの `高さ` は、**全部の条件・全部のモデルで 1 度も返ってこなかった。**
数量の `1` が消えた回もある。**「読めた語の一覧」は「書いてあることの一覧」ではない。**

### 2-4. 2 つのモデルを突き合わせると、誤りは 0 件になったが 7 割が落ちる

両方のモデルが同じに読んだ語だけを通した場合:

| 紙の状態 | 通った語 | **そのうち元図に無い読み** | 食い違いとして落ちた語 |
|---|---|---|---|
| きれい | 7 | **0** | 15 |
| 傾き0.7度+粒状 | 8 | **0** | 14 |
| 傾き1.5度+粒状 | 7 | **0** | 15 |

**通った語に誤りは 1 件も無かった。** 代わりに、片方しか正しく読めなかった語
(数字も日本語も)は全部落ちる。29 語のうち通るのは 7〜8 語である。

この結果をそのまま設計にした。`recognize_page(backends=[...])` に
2 つ渡すと、**両方が同じに読んだ語だけ**が通り、食い違いは
`OcrPage.conflicts` に残る(どちらも採らない)。1 つだけ渡すこともできるが、
その読みには「突き合わせていない」ことが証拠に残る。

> **但し書き。** 上の 0 件は**合成した紙・29 語・3 条件**の結果で、
> 誤り率の測定ではない。実図面のスキャンには紙の折れ・かすれ・手書きの
> 書き込み・押印が乗る。**実案件での率は、実図面を持っている側で測る必要がある**(7節)。

## 3. どのエンジンを選んだか

**RapidOCR(`rapidocr-onnxruntime`)**。理由:

- **pip だけで入る。** モデルが wheel に同梱で、実行時にモデルを取りに行かない
- **CPU で動く**(この環境は GPU 無し・4 コア)。A3 のスキャン 1 枚で 2〜5 秒
- PyTorch を要求しない。この環境では `download.pytorch.org` が 403 で、
  PyTorch 系(EasyOCR・manga-ocr)は入れにくい

**採らなかったもの**:

| 候補 | 採らなかった理由 |
|---|---|
| Tesseract + `pytesseract` | **この環境で動かして確かめられなかった。** `apt-get` が 403 で遮断されていて本体を入れられない(`archive.ubuntu.com` が 403)。確かめていないものを「使える」と書かない。apt が通る場所では選択肢になる |
| EasyOCR / manga-ocr | PyTorch が要る。`download.pytorch.org` が 403。素の PyPI から入る CUDA 入り wheel は 2GB 級で、CPU 4 コアの環境には現実的でない |
| PaddleOCR 本体 | `paddlepaddle` の wheel が重く、モデルを実行時に取りに行く |

**日本語モデルの入れ方**(既定は中国語・英語なので、上の 2-1 のとおり語が化ける):

```
huggingface.co/tobiichioriguchi/japan_PP-OCRv3_mobile_rec_onnx の
inference.onnx (9.7MB) と inference.yml を取り、yml の
PostProcess.character_dict を1行1文字のテキストにして渡す
RapidOcrBackend(name="ja", rec_model_path=..., rec_keys_path=...)
```

**このコードがモデルを勝手に取りに行くことはしない。** 取得は人がやる。

### 3-1. 追記（2026-09-22、おーちゃんの質問への実測）

「この環境と CI に入れられるか」を実測した。**入れられる。**

| 測ったこと | 結果 |
|---|---|
| このクラウド環境に `pip install` できるか | **できる**（PyPI から。HuggingFace への取得は不要。既定のモデルは wheel 同梱） |
| 入れたあとの全件テスト | **871 件パス・skip 0 件**（入れる前は 870 パス・1 skip） |
| 全件テストの時間 | 177 秒 → **185 秒**（+8 秒） |
| 追加のダウンロード | **約 40MB**（onnxruntime 23.5MB + rapidocr 14.9MB + pyclipper 1.0MB） |
| 仮想環境の増加 | **約 83MB** |

**下の「415MB」は、`opencv-python`（画面を出す版）まで一緒に入れた場合の数字である。**
rapidocr-onnxruntime は `opencv-python` を要求するが、このリポジトリは既に
`opencv-python-headless` を使っている。素直に入れると**両方入り、どちらも同じ `cv2` を
提供する状態になる**（実測で 116MB 増）。**headless だけで OCR の試験が通ることを
実測した**ので、`--no-deps` で入れて依存を `requirements-ocr.txt` に並べる形にした。

**ただし、CI で走るのは「エンジンが口に収まっていること」と「位置がページの中に
収まっていること」の 2 つだけである**（この試験の冒頭のとおり）。
**日本語モデルは相変わらず人が HuggingFace から取ってくる必要があるので、
2 つのモデルを突き合わせる経路は CI では動かない。** そこは 2 節の合成ベンチマーク
（`benchmarks/run_ocr_synthetic_eval.py`）と、実図面を持っている側（7 節）で確かめる。

### requirements.txt に入れていない理由

エンジン一式で仮想環境が **415MB** 増える。全員のテスト実行と CI に毎回これが
乗るのは割に合わない。**エンジンが無くても経路の振る舞いは全部試験できる**
(次節)ので、`requirements.txt` にはコメントで書き方だけ残した。
Grounding DINO と同じ扱いである。

## 4. テストのやりかた(**実図面は使わない**)

`tests/scan_fixtures.py` が、実物と同じ順序で合成する。

1. ベクターの PDF を組む(文字は PyMuPDF 内蔵の日本語フォント。
   **システムに日本語フォントが無い CI でも同じ絵になる**)
2. ラスター画像にする(= 紙に出して読み取った状態)。傾きと粒状ノイズを足せる
3. その画像 1 枚だけを貼った PDF を作る

3 の PDF は `rasterize()` が `raster` と判定し、`page.get_text()` は空を返す。
**P011 の 34 ページと同じ形である**(`test_synthetic_scan_has_no_text_and_is_raster` で固定)。

OCR の試験体は、2 の段階で捨てた「どこに何と書いてあったか」から組み立てる
(`traced_backend`)。位置は本物と同じで、文字は `mutate` で自由に壊せるので、
**上で実測した化け方をそのまま再現できる。**
本物のエンジンを通す試験(`tests/test_ocr_rapidocr_integration.py`)もあるが、
エンジンが入っていなければ skip する。

## 5. 何をどうつないだか

```
スキャンのページ
  → recognize_page()            … 画像にして OCR。位置はページ座標(pt)で返す
      ├ 確信度の足切り → 落とした読みは OcrPage.dropped に残る
      └ エンジン 2 つなら突き合わせ → 食い違いは OcrPage.conflicts に残る
  → read_scale() / read_area_labels()   … **埋め込み文字と同じ正規表現**に掛ける
  → intake/drawing_intake.py            … 証拠として仲裁層へ
```

守っていること:

1. **OCR を渡さないときの振る舞いを変えていない。** `IntakeConfig.ocr` が None なら、
   ラスターのページは今までどおり `unsupported_raster` として記録される
   (`test_without_ocr_a_scanned_page_is_still_recorded_as_unsupported`)。
2. **手法IDを分けた。** 埋め込み文字は `pdf_text_area` / `pdf_text_scale`、
   OCR は `ocr_text_area` / `ocr_text_scale`。**同じ対象の別々の読み**として
   仲裁層へ行き、そこで突き合わされる。1 本のレンジに溶かさない。
3. **どちらも未校正(`calibrated=False`)、上限 `weak`** で登録した
   (`arbitration/method_policies.py`)。`pdf_text_area` の上限が `strong` なのは
   「印字をそのまま読む手法は原理的にハード制約になりうる」からだが、
   **OCR は印字をそのまま読めていない**(2節)ので、その理由が当てはまらない。
   結果として **OCR の読みだけでは自動確定しない**
   (`test_nothing_is_auto_confirmed_from_ocr`)。
4. **どのページのどこから取ったかを必ず残す**(おーちゃんの指示、2026-09-22)。
   ページ番号・ページ座標の矩形・読んだままの行・エンジン名・各エンジンの読み・
   確信度・突き合わせたかどうかを `provenance` に載せる。
5. **意味の 4 欄を必ず付ける**(`axes/reading/meaning.py`、おーちゃんの回答9)。
   `what` / `where` / `phase` / `purpose_link`。**空では作れない。**
   人がページの種類を宣言していれば `phase` にその区別が入り、無ければ `不明`。
   `purpose_link` は目的の受け取り口がまだ無いので `目的未確立`。
   どちらも「埋め忘れ」ではなく「まだ決まっていない」という記録である。
6. **スキャンのページからは長さ(実寸)を出していない。** 止めているのではなく、
   スキャンには図形データが無いので**出す対象が無い**。印字の縮尺は、
   人が入れた基準点との突き合わせにだけ使い、合わなければ警告を残して
   どちらも採らない(原則 3-1 の検算)。
7. **文字化けを直さない。** 全角→半角の幅寄せだけを行い、`户`→`戸` のような
   字の寄せはしない(本当に `户` と書いてある図面を壊すため)。
   `専有延床面`(`積` が落ちた読み)は**面積として拾わない。**

### 5-1. 壊し試験(テストが本当に検出するか)

新しいテストが「通っているだけ」でないことを確かめるため、実装を 8 通りに壊して
**全部が落ちることを実測した**(`rm -rf __pycache__` と
`PYTHONDONTWRITEBYTECODE=1` を毎回かけている。バイト数が変わらない壊し方だと
古いバイトコードが残るため)。

| 壊し方 | 落ちたテスト |
|---|---|
| 1. エンジンが食い違っても先頭の読みを採る | 突き合わせの 2 件 |
| 2. OCR の手法を校正済み・strong にする | 自動確定しない 1 件ほか |
| 3. 画素をそのままポイントとして返す | 位置の 2 件ほか |
| 4. 確信度の足切りを素通りさせる | 足切りの 1 件 |
| 5. 落ちた字(`専有延床面`)を寄せて面積として拾う | 寄せない 1 件 |
| 6. 意味の欄が空でも作れるようにする | 意味の 3 件 |
| 7. OCR を渡していないのに読んだことにする | 既存の振る舞いの 1 件 |
| 8. 宣言が無くても `phase` を「計画」と決めつける | 意味の 2 件 |

## 6. できていないこと(**ここが次の段**)

- **スキャンの建具表・内装仕上表を表として読めない。** 罫線を画像から見つけて
  升目を組む実装が無いので、`pdf_tables.find_tables()` はスキャンでは 0 個を返す。
  **P011 でいちばん効くのはここ**(建具の数量が拾える)なので、次の作業として推す。
  `schedule_tables._as_door_schedule()` は `TableRegion` を受け取る純粋な関数なので、
  **画像から `TableRegion` を作れれば、意味づけの側はそのまま使える。**
- **傾き補正・二値化・ノイズ除去をしていない。** 前処理の効き目を測る手立てが
  今は無いので、素のグレースケールをエンジンに渡している。
- **手書きの書き込み・押印は読めない**(そもそも今回のエンジンの対象外)。
- **ベクターとラスターが混在するページは、貼られた画像の中身をまだ読んでいない。**
  今回 OCR を掛けるのは `raster` のページだけにした。
- **引戸・折戸は相変わらず図形からは拾えない。** これは OCR の話ではなく、
  円弧を描かないため(建具表が読めるようになれば拾える)。

## 8. 判断待ち

1. **「何に基づくか」の 4 値(確定/推論に基づく/仮説に基づく/現地確認が必要)を、
   この経路で名乗るかどうか。**
   今回の新しい経路は、既存の 2 値(`derivation` の read/assumed)のまま出している。
   4 値の欄と、今の 2 値からの写像は
   [queue3_redesign.md](./principles/queue3_redesign.md) 8節の 2 番として
   別に設計が進む予定で、**こちらで別の形を作ると二重になる。**
   **推奨: 4 値はそちらで 1 か所に作り、この経路はできた後に乗り換える。**
2. **突き合わせを既定にするかどうか。**
   エンジンを 2 つ用意するのは手間で、時間も 2 倍になる。一方 1 つだけだと
   **誤りが黙って通る**(2-1)。
   **推奨: 2 つを既定にする。** 7〜8 語しか通らなくても、誤りが 0 件のほうが、
   22 語のうち 7 語が化けているより扱いやすい。落ちた語は
   `conflicts` に残るので、人に見せる材料にはなる。
3. **日本語モデルの置き場所。** モデル(9.7MB)はリポジトリに置かず、
   パスを設定で渡す形にしてある(実図面と同じ扱い)。置き場所をどこにするか。
4. **確信度の足切りの値(既定 0.5)。** 実測では、この足切りは文字化けを
   1 件も止めない。**上げても安全にならない**ので、既定を触っていない。
   実図面で「屑の読み」がどれだけ出るかを見てから決めるのがよい。
