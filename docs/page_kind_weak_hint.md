## 5. 残っていること

- **現況/計画/解体の宣言(`phase`)は手を付けていない。**
  突き合わせなしに対象名へ入る点(`principle_conformance_review.md` の 10)は

  「円弧が出たか」と「建具表が表として読めたか」の 2 つだけである。

  P011 は 34 ページ全部スキャンなので、この経路(ベクターの円弧)はそもそも動かない。

  (原則5の末尾「人の負担は、質問の数ではなく、操作の回数と時間で測る」)。
  実図面での件数は Codex 側で測るのが筋である。

## 6. 所見: ページの種類の宣言に「確かさ」を付けられるか(実装していない)

おーちゃんが加える原則の第2層に「人の入力には確かさ(確か/たぶん/分からない)を
付けられるようにする。未入力は『分からない』と同じに扱う」がある。
**いまの作りに自然に入るかどうかだけ見た。実装はしていない。**

**入る。** 見た範囲では、次の 3 つがすでにそろっている。

1. **置き場所がある。** `PageDeclaration` は `page_number` / `kind` / `phase` の
   3 つだけを持つ凍結したデータクラスで、`confidence` を既定値つきで足せば
   既存の呼び出しは 1 つも壊れない(`__post_init__` の検算も同じ形で書ける)。
2. **「未入力＝分からない」の前例がある。** 現況の把握の状態が同じ考えで、
   `AWARENESS_UNKNOWN` を既定にして**「分かっている」に倒さない**ようにしてある
   (`intake/start_kit.py`)。`phase` の `"不明"` も同じ形である。
   ページの種類だけ別の書き方にする理由は無い。
3. **使う先ができている。** この修正で、宣言は**食い違いの判定にだけ**使う形に
   なった。判定は `_door_arc_findings()` の `conflict` 1 箇所に寄っているので、
   確かさを効かせるならそこ 1 箇所である。

**ただし「何に効かせるか」は決めないと入らない。** 素直に思いつくのは 2 つで、
どちらを採るかで意味が変わる。

- **食い違いを立てるかどうかを変える** … 「たぶん」の宣言と食い違っても
  人に聞かない、という動きになる。**勧めない。** 確かでない宣言ほど
  食い違いが大事なので、向きが逆である。
- **食い違ったときに何を疑うかを変える** … 「確か」なら円弧のほうを疑い、
  「たぶん」なら宣言のほうも疑う。判断待ちの文面と、`assumed` に落とすかどうかが
  変わる。こちらのほうが筋が通るが、**判定のしかたを変える話**になるので、
  別の PR で、この PR とは分けて出すべきである。

**心配な点が 1 つある。** 確かさを付けられるようにすると、
**「確か」と言われた宣言を無条件の正解に戻す**入口になりうる。
原則5の「人の入力を無条件の正解にせず、単一の根拠では自動確定させない」は
確かさが付いても変わらないので、そこを先に書き留めてから実装するのが安全である。
