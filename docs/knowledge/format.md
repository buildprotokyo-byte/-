# 知識の表の形式(format_version 1)

**この形式は先に確定させる。**中身は後から差し替えるが、**列を後から足すと作り直しになる。**

読み込みは `knowledge/table.py`。見本は `knowledge/examples/synthetic_knowledge.json`
(**架空**)。**実在の会社のルールや、実案件から作った表はリポジトリに置かない。**
パスを設定で渡す。

---

## 1. ファイル全体

```json
{
  "format_version": 1,
  "table_id": "synthetic-example",
  "description": "この表は架空である。...",
  "synthetic": true,
  "entries": [ ... ]
}
```

| 列 | 意味 |
|---|---|
| `format_version` | **1 だけを読む。**違えば読まない(半分だけ効いた表を作らないため) |
| `table_id` | 表の名前。一意 |
| `description` | 人が読む説明 |
| `synthetic` | **その表が架空かどうか。**リポジトリに置いてよいのは `true` だけ |
| `entries` | 知識 1 件ずつの並び。空は不可 |

## 2. すべての知識に共通の列

| 列 | 必須 | 意味 |
|---|---|---|
| `entry_id` | ✓ | 一意の名前 |
| `kind` | ✓ | `数え方` / `波及` / `問い` のどれか |
| `statement` | ✓ | **人が読む一文。**これだけ読んで意味が通ること |
| `source` | ✓ | 出どころ(下記)。**空は許さない** |
| `confidence` | ✓ | `一次資料`(明文がある) / `慣行` / `見立て` |
| `scope` | ✓ | そのまま当てはめてよい範囲。`公共工事` / `住宅改修` / `自社` |
| `applies_to` | ✓ | どこに掛かるか(下記)。1 つ以上 |
| `overridden_by` | | **これより優先されるもの。**例: `特記`。空でよい |
| `needs_human_check` | ✓ | **この案件にそのまま当てはめてよいかを人に確かめる必要があるか** |
| `detail` | ✓ | 種類ごとの中身(下記) |
| `note` | | 補足。空でよい |

### 2-1. `source`(出どころ)

| 列 | 必須 | 意味 |
|---|---|---|
| `document` | ✓ | 文書の名前 |
| `clause` | ✓ | 条項。**「どこに書いてあるか」を必ず書く** |
| `url` | | あれば |
| `read_directly` | ✓ | **その文書を直接読んだか。**孫引きなら `false` |

**出どころの無い知識は入れない。**後から「なぜそう決めたか」を辿れなくなるためである。

### 2-2. `applies_to`(掛かる先)

| 列 | 意味 |
|---|---|
| `work_kinds` | 工種(`内装改修` `建具改修` `電気設備` …) |
| `parts` | 部位(`壁` `天井` `床` `建具` `配線器具` …) |
| `axes` | 軸(`image` `text` `rules` …)。問いを出す先を決めるのに使う |

3 つとも空の知識は受け付けない。**どこにも掛からない知識は、使いようがない。**

**`axes` の定義(2026-09-23 追記、おーちゃんの K-04 6 番):**
`axes` は **その知識を当てはめる軸** である。その軸の読み取りを、この知識で
数え直したり、この知識から問いを立てたりする。**問いを出す先も、この軸で決める**
(上の表の「問いを出す先を決めるのに使う」はこの意味)。
**知識の根拠になった軸ではない。**根拠は `source` に書く。
例: 「コンセントは記号ごとに 1 個と数える」は図面の記号を数える知識なので `["image"]`。
出どころが国の基準の文書でも `text` にはしない。

**`confidence` の定義(2026-09-23 追記、同):**
`confidence` は **出典の状態**(明文があるか・慣行か・見立てか)を書く欄で、
**その知識を採用してよいかどうかではない。**`一次資料` でも、この案件や自社に
当てはめてよいとは限らない(それは `scope` と `needs_human_check` で書く)。
採用してよいかを決めるのはおーちゃんで、AI がこの欄を根拠に採否を決めてはいけない。

## 3. `kind` ごとの `detail`

### 3-1. `数え方`

| 列 | 必須 | 意味 |
|---|---|---|
| `unit` | ✓ | 何で数えるか(`個` `組` `箇所` `㎡` `m` …) |
| `method` | ✓ | 数え方の一文(「記号ごとに個数を数える」) |
| `threshold` | | しきい値。`{"value": 0.5, "unit": "㎡", "comparison": "以下", "then": "控除しない"}` |
| `excluded` | | **計測の対象外にするもの**の並び |

### 3-2. `波及`

| 列 | 必須 | 意味 |
|---|---|---|
| `trigger` | ✓ | 何が起きたら効くか(「間仕切壁を撤去する」) |
| `affected` | ✓ | どこへ波及するか(`["天井", "床", "隣接壁"]`) |
| `extent` | ✓ | どれだけ。`{"value": 600, "unit": "mm", "basis": "壁面から両側"}` または `{"text": "壁厚程度"}` |
| `symmetric` | ✓ | **逆向きにも波及するか。**天井→壁は起きない、のような非対称を書けるようにする |

### 3-3. `問い`

| 列 | 必須 | 意味 |
|---|---|---|
| `question` | ✓ | 人に聞く一文 |
| `answer_options` | ✓ | 答えの選択肢(2 つ以上) |
| `what_changes` | ✓ | **答えによって何が変わるか。**変わらない問いは聞かない |

## 4. この読み込みが守ること

1. **知らない列があったら断る。**黙って読み飛ばすと、半分だけ効いた表になる。
2. **出どころが無ければ断る。**
3. **知らない `kind` は断る。**
4. **`format_version` が違えば読まない。**
5. **読み込むだけで、判定のしかたには一切つながない。**
   知識が判定に効くようにするのは別の周である。

## 5. 書くときの注意(Codex-B 向け)

- **`statement` は 1 文で完結させる。**箇条書きを詰め込まない。1 件 1 行。
- **「特記がなければ」という既定値は、必ず `overridden_by` に `特記` と書く。**
  これを書かないと、図面に明示があるときも既定値で上書きしてしまう。
- **公共工事の基準から採った知識は `scope` を `公共工事` にし、
  `needs_human_check` を `true` にする。**住宅の改修にそのまま当てはまるとは限らない。
- **1 件に 2 つのことを書かない。**「AかつB」は 2 件に分ける。

## 6. **いまの形式に欄が無い 2 つのこと(`note` に文章で書く)**

2026-09-23 に候補 25 項目で試したところ、**2 項目だけ欄に収まらなかった。**
**欄はまだ足さない**(おーちゃんの判断。実際に使う段で必要性がはっきりしてから足す)。
**それまでは `note` に文章で書いて、失わないようにする。**

1. **「波及しない」向き。**
   「壁を撤去すると天井に波及する。だが天井を撤去しても壁には波及しない」という
   **非対称**を書く欄が無い。`symmetric` は false にできるが、
   **波及しないという知識そのもの**は書けない。
   → `note` に「**逆向きには波及しない**」と書く。
2. **知識どうしの参照。**
   「新設側の数量は別の規則集(新築用)をそのまま使う」のような、
   **他の知識を指す**書き方が無い。
   → `note` に「**参照: <どの文書のどの条項>**」と書く。

**この 2 つは `note` に書いてあれば後から欄に移せる。書いていなければ失われる。**
