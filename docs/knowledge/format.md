# 知識の表の形式(format_version 2)

**この形式は先に確定させる。**中身は後から差し替えるが、**列を後から足すと作り直しになる。**

読み込みは `knowledge/table.py`。見本は `knowledge/examples/synthetic_knowledge.json`
(**架空**)。**実在の会社のルールや、実案件から作った表はリポジトリに置かない。**
パスを設定で渡す。

**変更履歴**
- 2026-09-23 版 2: `source` に発行元・出典の版・年・確認日・拘束力、各知識に採否の状態を足した
  (おーちゃんの K-04 6 番)。`数え方` の単位は 1 つだけにし、複合は単位ごとに 1 件へ分ける
  (K-06 1 番)。**版 1 の表は読まない。**足す列は 7 節。
- 2026-09-23 版 2 のまま: `checked_on`(確認日)に `null`(不明)を許した(K-06 の決定)。
  確認した日の記録が無いときは推して埋めずに `null` と書く。列そのものは必須のまま。
- 2026-09-23 版 2 のまま: **確認日が `null` の知識は、採用の判断に進めない**(K-07 5 番)。`adoption_status` は `候補` のままでしか読めず、`採用` / `不採用` と書くと断る。

---

## 1. ファイル全体

```json
{
  "format_version": 2,
  "table_id": "synthetic-example",
  "description": "この表は架空である。...",
  "synthetic": true,
  "entries": [ ... ]
}
```

| 列 | 意味 |
|---|---|
| `format_version` | **2 だけを読む。**違えば読まない(半分だけ効いた表を作らないため)。版 1 の表には、足す列を名指しして断る |
| `table_id` | 表の名前。一意 |
| `description` | 人が読む説明 |
| `synthetic` | **その表が架空かどうか。**リポジトリに置いてよいのは `true` だけ |
| `entries` | 知識 1 件ずつの並び。空は不可 |

## 2. すべての知識に共通の列

| 列 | 必須 | 意味 |
|---|---|---|
| `entry_id` | ✓ | 一意の名前 |
| `kind` | ✓ | `数え方` / `波及` / `問い` のどれか |
| `statement` | ✓ | **人が読む一文。**これだけ読んで意味が通ること |
| `source` | ✓ | 出どころ(下記)。**空は許さない** |
| `confidence` | ✓ | `一次資料`(明文がある) / `慣行` / `見立て` |
| `scope` | ✓ | そのまま当てはめてよい範囲。`公共工事` / `住宅改修` / `自社` |
| `applies_to` | ✓ | どこに掛かるか(下記)。1 つ以上 |
| `overridden_by` | | **これより優先されるもの。**例: `特記`。空でよい |
| `needs_human_check` | ✓ | **この案件にそのまま当てはめてよいかを人に確かめる必要があるか** |
| `detail` | ✓ | 種類ごとの中身(下記) |
| `note` | | 補足。空でよい |
| `adoption_status` | ✓ | **採否の状態。**`候補` / `採用` / `不採用` のどれか。**新しく書く知識は `候補`**(2-3) |

### 2-1. `source`(出どころ)

| 列 | 必須 | 意味 |
|---|---|---|
| `document` | ✓ | 文書の名前 |
| `clause` | ✓ | 条項。**「どこに書いてあるか」を必ず書く** |
| `url` | | あれば |
| `read_directly` | ✓ | **その文書を直接読んだか。**孫引きなら `false` |
| `publisher` | ✓ | **発行元。**例: `国土交通省官庁営繕部`。空は不可 |
| `edition` | ✓ | **出典の版・年。**例: `令和4年版` `2023`。空は不可 |
| `checked_on` | ✓ | **確認日。**`YYYY-MM-DD`、または `null`(不明。確認した日の記録が無いとき。推して埋めない)。例: `2026-09-23`。`2026/09/23` や実在しない日付(`2026-02-30`)は断る。**不明の書き方は `null` だけ**(空文字 `""` や `"不明"` は断る)。列を消すのも断る。**`null` の知識は採用の判断に進めない**(`adoption_status` は `候補` だけ) |
| `binding` | ✓ | **拘束力。**`法令` / `行政基準` / `業界指針` / `任意資料` / `社内見立て` / `案件の凡例` のどれか |

**出どころの無い知識は入れない。**後から「なぜそう決めたか」を辿れなくなるためである。

`binding` の目安: `法令` は法律・政令・省令・条例。`行政基準` は国や自治体が定めた基準で、
法令ではないもの(公共建築数量積算基準など)。`業界指針` は業界団体のガイドライン。
`任意資料` はそれ以外の社外の資料(メーカー資料・解説書など)。
`社内見立て` は、公開の基準でも社外の資料でもなく、**社内で案件の突き合わせなどから起こした見立て**
(例: ある案件の正解と図面を突き合わせて起こした波及の組)(K-10 5 番)。
会社として決めたもの(社内規程)とは今は分けない。そういうものが出てきたら値を足して分ける。
`案件の凡例` は、**その案件の図面が自分で名乗っている意味**(例: 凡例のページの「撤去=既存を取り除く」)
(K-20 2 番)。**確かさは高いが、ほかの案件には使えない**ので、強さの順ではいちばん後ろに置く。
中身は図面から写したものなので**共有フォルダに置き、リポジトリには入れない**。
**値を足すのは `knowledge/table.py` の `BINDINGS` の 1 か所だけ**で、読み込みの検査とテストはそれに付いてくる。
`binding` も `confidence` と同じく**出典の性質を書く欄で、採用してよいかどうかではない。**

### 2-2. `applies_to`(掛かる先)

| 列 | 意味 |
|---|---|
| `work_kinds` | 工種(`内装改修` `建具改修` `電気設備` …) |
| `parts` | 部位(`壁` `天井` `床` `建具` `配線器具` …) |
| `axes` | 軸(`image` `text` `rules` …)。問いを出す先を決めるのに使う |

3 つとも空の知識は受け付けない。**どこにも掛からない知識は、使いようがない。**

**`axes` の定義(2026-09-23 追記、おーちゃんの K-04 6 番):**
`axes` は **その知識を当てはめる軸** である。その軸の読み取りを、この知識で
数え直したり、この知識から問いを立てたりする。**問いを出す先も、この軸で決める**
(上の表の「問いを出す先を決めるのに使う」はこの意味)。
**知識の根拠になった軸ではない。**根拠は `source` に書く。
例: 「コンセントは記号ごとに 1 個と数える」は図面の記号を数える知識なので `["image"]`。
出どころが国の基準の文書でも `text` にはしない。

**`confidence` の定義(2026-09-23 追記、同):**
`confidence` は **出典の状態**(明文があるか・慣行か・見立てか)を書く欄で、
**その知識を採用してよいかどうかではない。**`一次資料` でも、この案件や自社に
当てはめてよいとは限らない(それは `scope` と `needs_human_check` で書く)。
採用してよいかを決めるのはおーちゃんで、AI がこの欄を根拠に採否を決めてはいけない。

### 2-3. `adoption_status`(採否の状態)

**新しく書く知識は、必ず `候補` と書く。**読み込みは既定値で埋めない(書いていなければ断る)。

- **`候補` から `採用` / `不採用` に変えるのは、おーちゃんだけ。**
  **AI はこの欄を変えない。**書き写すときも、書かれていた値をそのまま写す。
- **AI は、この欄も `confidence` も、採否を決める根拠に使わない。**
- 読み込みは**値を読むだけ**で、判定には一切つながない(4節の 5)。
  `採用` になった知識を判定に効かせるのは、判定につなぐ別の周で決める。

コードがこの欄を書き換えていないことは、テストで見張っている
(`tests/test_knowledge_table.py`)。見ているのは次の 3 つ。

1. `adoption_status` という名前を書いているコード(`tests/` を除く `.py`)が
   `knowledge/table.py` だけであること
2. `knowledge/table.py` の中で `採用` / `不採用` の文字列が、読める値の一覧
   (`ADOPTION_STATUSES`)にしか出てこないこと、`adoption_status` に既定値を埋める
   書き方(`.get("adoption_status", …)` `setdefault`)が無いこと
3. リポジトリにある知識の表(JSON)の `adoption_status` が全件 `候補` であること

**見ていないもの:** 列の名前を文字列の組み立てで作るコード、Python 以外(シェル・
手作業)での書き換え、**リポジトリの外にある表**(共有フォルダなど)の書き換え。
これらは決まりとして守る。

## 3. `kind` ごとの `detail`

### 3-1. `数え方`

| 列 | 必須 | 意味 |
|---|---|---|
| `unit` | ✓ | 何で数えるか(`個` `組` `箇所` `㎡` `m` …)。**単位は 1 つだけ**(下記) |
| `method` | ✓ | 数え方の一文(「記号ごとに個数を数える」) |
| `threshold` | | しきい値。`{"value": 0.5, "unit": "㎡", "comparison": "以下", "then": "控除しない"}`。`unit` を書くなら 1 つだけ |
| `excluded` | | **計測の対象外にするもの**の並び |

**単位は 1 つだけ書く(2026-09-23、おーちゃんの K-06 1 番)。**
書き方は今のまま、**自由な言葉**(`個` `組` `箇所` `㎡` `m` …)でよい。
ただし `個・組` `個、組` `個,組` `個/組` `個等` `個 組` のように**複数の単位を並べたものは断る。**
**単位ごとに 1 件へ分けて書く**(5節「1 件に 2 つのことを書かない」)。
`threshold.unit` と、波及の `extent.unit` も同じ。

**この `unit` は `AxisEvidence.unit` の正規形(`count` / `mm` / `cm2` / `yen`、
v8 10章13項・K-02 34 番)とは別の欄である。**読み込みは書かれた言葉をそのまま持ち、
正規形には直さない。知識を判定につなぐ周で、**正規形への対応を 1 箇所で作る。**

### 3-2. `波及`

| 列 | 必須 | 意味 |
|---|---|---|
| `trigger` | ✓ | 何が起きたら効くか(「間仕切壁を撤去する」) |
| `affected` | ✓ | どこへ波及するか(`["天井", "床", "隣接壁"]`) |
| `extent` | ✓ | どれだけ。`{"value": 600, "unit": "mm", "basis": "壁面から両側"}` または `{"text": "壁厚程度"}`。`unit` を書くなら 1 つだけ |
| `symmetric` | ✓ | **逆向きにも波及するか。**天井→壁は起きない、のような非対称を書けるようにする |

### 3-3. `問い`

| 列 | 必須 | 意味 |
|---|---|---|
| `question` | ✓ | 人に聞く一文 |
| `answer_options` | ✓ | 答えの選択肢(2 つ以上) |
| `what_changes` | ✓ | **答えによって何が変わるか。**変わらない問いは聞かない |

## 4. この読み込みが守ること

1. **知らない列があったら断る。**黙って読み飛ばすと、半分だけ効いた表になる。
2. **出どころが無ければ断る。**
3. **知らない `kind` は断る。**
4. **`format_version` が違えば読まない。**
5. **読み込むだけで、判定のしかたには一切つながない。**
   知識が判定に効くようにするのは別の周である。
6. **5 つの列(発行元・出典の版・年・確認日・拘束力・採否の状態)が無ければ断る。**
   採否の状態を既定値で埋めない。
7. **単位が 2 つ以上並んでいたら断る。**

## 5. 書くときの注意(Codex-B 向け)

- **`statement` は 1 文で完結させる。**箇条書きを詰め込まない。1 件 1 行。
- **「特記がなければ」という既定値は、必ず `overridden_by` に `特記` と書く。**
  これを書かないと、図面に明示があるときも既定値で上書きしてしまう。
- **公共工事の基準から採った知識は `scope` を `公共工事` にし、
  `needs_human_check` を `true` にする。**住宅の改修にそのまま当てはまるとは限らない。
- **1 件に 2 つのことを書かない。**「AかつB」は 2 件に分ける。
  **単位も同じ。**「個・組」なら、個で数える 1 件と組で数える 1 件に分ける。
- **`adoption_status` は `候補` と書く。**`採用` / `不採用` にしない(2-3)。
- **`checked_on` は、その出典を実際に確かめた日を書く。**分からない日を埋めない。
  確かめた日の記録が無ければ `null`(不明)と書く。**コミットの日付などから推して埋めない。**

## 6. **いまの形式に欄が無い 2 つのこと(`note` に文章で書く)**

2026-09-23 に候補 25 項目で試したところ、**2 項目だけ欄に収まらなかった。**
**欄はまだ足さない**(おーちゃんの判断。実際に使う段で必要性がはっきりしてから足す)。
**それまでは `note` に文章で書いて、失わないようにする。**

1. **「波及しない」向き。**
   「壁を撤去すると天井に波及する。だが天井を撤去しても壁には波及しない」という
   **非対称**を書く欄が無い。`symmetric` は false にできるが、
   **波及しないという知識そのもの**は書けない。
   → `note` に「**逆向きには波及しない**」と書く。
2. **知識どうしの参照。**
   「新設側の数量は別の規則集(新築用)をそのまま使う」のような、
   **他の知識を指す**書き方が無い。
   → `note` に「**参照: <どの文書のどの条項>**」と書く。

**この 2 つは `note` に書いてあれば後から欄に移せる。書いていなければ失われる。**

## 7. 版 1 の表を版 2 にするとき

版 1 の表は読まない(読み込みが、足す列を名指しして断る)。次を足して
`format_version` を `2` にする。

1. 各知識の `source` に `publisher` `edition` `checked_on` `binding` を足す
2. 各知識に `adoption_status` を足し、**`候補` と書く**
3. `数え方` の `unit`(と `threshold.unit`・`extent.unit`)に単位が 2 つ以上
   並んでいたら、単位ごとに 1 件へ分ける
